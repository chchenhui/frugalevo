# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns
- **LP-based radius optimization over heuristic scaling is the decisive win**: The current best program (`lp_refined_hex_rows`, sum_radii 2.37, combined 0.90) and `vectorized_lp_multistart_refine` (2.34, 0.89) both solve the LP exactly via scipy `linprog` (method="highs"), dramatically outperforming greedy proportional-scaling approaches (Gen-0 rings: 0.96; Gen-2 repulsion: 1.60; Gen-7 uniform shrink: 1.52). LP roughly doubles sum_radii versus any heuristic radii method.
- **The `ensure_valid` hard-clipping safety pass guarantees validity 1.00**: Both top scorers (`lp_refined_hex_rows`, `vectorized_lp_multistart_refine`) use wall-distance clipping plus pairwise proportional shrinking post-pass. All correct programs achieved validity 1.00; this pattern never produced a false result when applied.
- **Staggered hex-row layouts (5,6,5,6,4) are a reliable seed**: The correct LP-based programs all use hex-staggered initial centers, giving good coverage of the unit square before optimization.
- **Local center refinement adds ~0.3–0.35 over static layouts**: `hex_lattice_lp_radii` (LP on fixed lattice, no refinement) reached 2.02/0.77, while adding hill-climb or annealing refinement on centers lifted scores to 2.34–2.37/0.89–0.90.

## Ineffective Approaches
- **Fixed concentric ring layouts (Gen-0, sum 0.96)**: outer ring radius 0.7 forced boundary circles into heavy clipping; fixed rigid geometry wastes space and cannot approach 2.635.
- **Greedy pairwise proportional scaling as the primary radius method**: order-dependent and suboptimal; caps scores at ~1.5–1.6 even with valid packings (Gen-2: 1.60; Gen-7: 1.52).
- **Buggy or broken LP/pipeline implementations scored 0.00 entirely**: Gen-9 assigned `wd4` (min of x/y distances) to all four wall blocks plus dead constraint construction → crash/invalid. Gen-10's LP failure triggered a degenerate greedy fallback collapsing radii to ~0. Gen-4 double-applied the hex stagger offset. Gen-5 used row counts [5,4,5,4,5,3] where the last row of 3 sat directly under a 5-circle row with insufficient separation — real overlaps the unused repair function couldn't fix.
- **Short local relaxation cannot escape lattice configurations**: Gen-2's 400-iteration repulsion with small step (0.002) and Gen-7's uniform spacing s=0.17 both left large gaps; single-center hill-climbs (Gen-8, 350 steps) plateau at ~2.34, short of 2.635.

## Implementation Insights
- **Current best program structure (Gen-1, `lp_refined_hex_rows`)**: clean three-stage pipeline — build_initial_centers (hex rows 5,6,5,6,4 with half-spacing stagger on odd rows), solve_radii_lp (dense A_ub with 4n wall rows + n(n-1)/2 pairwise rows, c=-ones, bounds (0,None)), refine_centers (250-step hill-climb, decaying step 0.03→1e-4, perturbing one center, LP re-solve each step), then final `ensure_valid`. Its LP code is correct per-wall (uses x, y, 1-x, 1-y individually) — exactly what Gen-9 got wrong.
- **Fallback robustness matters**: the greedy fallback in `solve_radii_lp` should never be the primary path; when LP fails and fallback degenerates (Gen-10), the whole score collapses to 0.00.
- **Multi-seed/multi-start (Gen-8's four seed layouts: hex, diagonal, staggered grid, ring+rows) matched single-seed performance (0.89 vs 0.90) at 2.2× the runtime (3.03s vs 1.35s)** — multi-seeding alone doesn't pay off; better moves within annealing do.
- **Vectorization of the LP assembly is an open efficiency lever**: the best program builds constraint rows element-wise in Python loops; Gen-8's "vectorized LP" kept eval at 3.03s with more seeds, suggesting per-step LP re-solve is the runtime bottleneck.

## Performance Analysis
- **Score trajectory across generations**: 0.36 (rings) → 0.90 (LP+hill-climb, Gen-1) → 0.61 (repulsion heuristic) → 0.00 (broken hex) → 0.00 (broken hex) → 0.58 (uniform shrink) → 0.89 (multi-seed annealing+LP) → 0.00 (broken LP) → 0.00 (broken LP) → 0.77 (static hex+LP) → **0.90 (current best, Gen-1 architecture)**.
- **LP presence is the single strongest predictor of high scores**: all four LP-based correct programs scored 0.77–0.90; all non-LP correct programs scored 0.36–0.61; all broken-LP/pipeline programs scored 0.00.
- **Remaining gap to AlphaEvolve's 2.635 is ~10% (target_ratio 0.90)**: both top programs attribute the shortfall to local search getting stuck — single-center moves and short annealing schedules plateau around 2.34–2.37. Gen-8's feedback explicitly suggests longer annealing, joint multi-circle moves, or finer post-annealing local search.
- **Runtime does not strongly correlate with score**: the best program (1.35s) beats the slower multi-seed variant (3.03s, 0.89), while fast heuristic programs (0.13–0.28s) score far lower — correctness and optimizer quality dominate runtime within the ~3s budget.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Vectorize the LP constraint assembly with numpy broadcasting.** Replace the element-wise Python loops in `solve_radii_lp` with vectorized construction: build pairwise rows via index arrays (`np.triu_indices(n,1)`) using a sparse `scipy.sparse.csr_matrix` instead of a dense `(4n + n(n-1)/2) × n` array, and compute all distances with `np.linalg.norm(centers[i_idx] - centers[j_idx], axis=1)` in one call. This should cut per-LP-solve cost significantly, allowing more hill-climb steps within the same ~1.35s runtime — the identified bottleneck is per-step LP re-solve, so speeding this up directly buys more refinement.

2. **Add simulated annealing with reheating instead of pure greedy hill-climbing.** The current 250-step hill-climb with only-improvement acceptance plateaus at 2.37; global insights note local search getting stuck is the key gap to 2.635. Add a temperature-based acceptance (`exp((s_new - s_cur)/T)`, T decaying geometrically from ~0.01 to 1e-4) and reheat (reset T to its starting value 2–3 times) when no improvement occurs for ~50 steps, keeping step count ~400–500 within the runtime freed by vectorization (recommendation 1).

3. **Add joint multi-circle moves to the refinement move set.** Gen-8's feedback and global insights explicitly point to joint moves as an untried lever beyond single-center perturbation. Implement moves that perturb 2–3 adjacent centers simultaneously (e.g., all centers within distance 0.25 of a randomly chosen one, shifted by a common small delta), plus occasional row-shift moves that translate an entire hex row horizontally. Alternate move types probabilistically (60% single, 30% pair, 10% row) so the search can escape local optima where single-circle moves create new overlaps.

4. **Use coordinate-wise targeted moves instead of isotropic Gaussian perturbation.** The current move perturbs both x and y of one center; instead, compute each center's "slack" (distance to nearest wall and nearest neighbor minus current radii contribution) and perturb preferentially along the direction of maximum slack (e.g., 70% of the step along that direction, 30% random). This makes each of the ~250–500 LP re-solves more informative, since moves along slack directions have a higher acceptance probability rather than wasting evaluations on rejected candidates.

5. **Wrap the entire pipeline in a short multi-start over perturbed initial layouts with a strict runtime budget.** Global insights show multi-seeding alone didn't pay off (Gen-8: 0.89 at 2.2× runtime), but the real lesson is that seeds must be cheap variants of a strong base — not diverse layouts. Run 3–4 starts where the hex-row layout (5,6,5,6,4) receives small random jitter (±0.01 per center) with a short 80-step anneal each, keep the best, then spend the remaining budget on a longer refinement of that winner. Cap total time at ~2.5s with a time-based cutoff (not fixed step count) so the budget never overruns.
