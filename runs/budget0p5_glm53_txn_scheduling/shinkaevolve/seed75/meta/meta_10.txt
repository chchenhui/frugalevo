# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

# Optimization Insights Analysis

## Successful Algorithmic Patterns
- **Randomized greedy construction + insertion local search + multi-restart is the winning combination**: The current best program (Gen 5, "Sampled Greedy Scheduler with Insertion-Based Local Search", combined score 3597.12, makespan 277.00) combines randomized greedy (10 candidates/step, 0.9 exploration rate), best-improvement insertion local search (up to 30 rounds), and up to 20 restarts under a 100-second budget — beating all other approaches.
- **Local search intensification matters more than construction purity**: Programs adding a local search refinement phase on top of greedy construction consistently outperform construction-only methods (Gen 5: 3597.12, Gen 7: 3412.97) vs. pure multi-restart greedy (Gen 8: 3115.26, Gen 2: 3236.25).
- **Multi-restart/multi-start diversification beats single greedy runs**: Gen 0's single greedy run scored 2702.70 (makespan 369.00) vs. multi-restart variants (Gen 2: 3236.25, Gen 8: 3115.26) — restarts from varied/random starting points reliably improve makespan by 50-80 points.
- **Beam search with restarts works but plateaus**: Gen 1 (beam width 4 + GRASP + adjacent swap) and Gen 9 (beam + windowed swap, both 3367.00, makespan 296.00) show hybrid metaheuristics are competitive but did not match insertion-based local search quality.

## Ineffective Approaches
- **Missing `import time` is a fatal, repeated bug**: Gen 4 and Gen 6 both scored 0.00 entirely because they called `time.time()` without importing `time`. Gen 6's otherwise sound multi-start greedy + pairwise-swap design was never evaluated. Time-budgeted code must verify imports.
- **Pure single greedy without restarts is weak**: Gen 0 (sample_rate=1.0, single random start) scored only 2702.70 — 895 points below the current best — showing local minima from a single construction severely limit quality.
- **Largely stochastic construction dilutes greedy signal**: Gen 7's 95% random-extension rate makes construction nearly random, capping it at 3412.97 (makespan 292.00), below Gen 5's balanced 0.9 greedy rate (makespan 277.00).
- **Small candidate samples limit greedy quality**: Gen 8's sample of 10 candidates per step with 200 restarts still only achieved makespan 320.00 — more restarts cannot compensate for limited per-step selection quality without a strong local search phase.

## Implementation Insights
- **Long time budget + capped restarts works**: The best program uses a 100-second deadline with a 20-restart cap — giving local search sufficient time per restart (up to 30 rounds of O(n²) insertion sweeps) rather than spreading compute thin. Contrast Gen 9's tighter budget with max 3 local-search rounds (makespan 296.00).
- **Best-improvement insertion beats windowed/adjacent swaps**: Gen 5's full-range insertion (each txn tried at every position) reached makespan 277.00, outperforming Gen 1's adjacent swaps (296.00) and Gen 9's ±5 window swaps (296.00). Broader move neighborhoods pay off despite higher query cost.
- **Exploration rate tuning**: The 0.9 sample rate (mostly greedy, occasionally random picks) in the best program balances diversification across restarts with cost-aware selection — better than 1.0 (Gen 0, no exploration) or 0.95 random-heavy (Gen 7).
- **Holdout/restore candidate sampling** (used in Gen 0, 5, 8) cleanly evaluates candidates without duplicates — a reusable pattern for sampled greedy selection.

## Performance Analysis
- **Score trajectory across generations**: 2702.70 (Gen 0) → 3367.00 (Gen 1) → 3236.25 (Gen 2) → 3311.26 (Gen 3) → 0.00 (Gen 4, crash) → **3597.12 (Gen 5, best)** → 0.00 (Gen 6, crash) → 3412.97 (Gen 7) → 3115.26 (Gen 8) → 3367.00 (Gen 9). Makespan improved 369.00 → 277.00 (25% reduction) from Gen 0 to Gen 5.
- **Local search type correlates with quality**: insertion (277.00) > swap+reinsertion (292.00) > windowed/adjacent swap (296.00) > no local search (308-320.00). The strength of the improvement neighborhood directly drives makespan gains.
- **Correlation between compute and quality**: The best program's 100-second budget with ~20 restarts plus deep insertion search outperformed both lighter-budget approaches (Gen 9's 3367.00) and higher-restart-count but shallower approaches (Gen 8's 200 restarts at 3115.26).
- **Correctness risk is real**: 2 of 10 programs (20%) failed entirely due to trivial import errors, showing runtime robustness checks are as important as algorithmic improvements in this evaluation setup.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

# Recommendations for Future Program Mutations

1. **Add simulated annealing or tabu acceptance to the insertion local search to escape local optima.** The current best program's insertion local search accepts only strict improvements (best-improvement descent), which gets trapped in local minima after ~30 rounds. Allow occasional sideways/worsening moves with a temperature parameter (e.g., accept moves within `current_cost * (1 + 0.01 * temp)`) that decays over the 100-second budget, keeping the best-so-far solution separately. This directly extends the proven winning neighborhood (insertion, makespan 277.00) with a stronger search strategy.

2. **Combine insertion with pairwise-swap moves in a hybrid local search neighborhood.** Insertion (277.00) beat swaps (296.00), but swaps and insertions explore different move types — exchanges of adjacent transactions may unlock improvements insertion cannot reach. Alternate between a full insertion sweep and a full swap sweep within each local search round, keeping the restart budget and 20-restart cap intact. Gen 6's (crashed) multi-start greedy + pairwise-swap design suggests this combination is untested and promising.

3. **Replace `get_opt_seq_cost` full-sequence recomputation with incremental cost evaluation during local search.** The insertion neighborhood is O(n²) per round with full O(n) cost recomputation per candidate, limiting rounds to ~30 within the time budget. Use the `get_incremental_seq_cost` API (commented out in the current code) or cache delta costs when relocating a single transaction, potentially enabling 10x more local search rounds or 100+ restarts within the same 100 seconds — the biggest lever since quality correlates strongly with search depth.

4. **Tune the greedy exploration rate between the proven extremes via a decay schedule.** Gen 0 (rate 1.0, no exploration) scored 2702.70, Gen 7 (95% random) scored 3412.97, and Gen 5's 0.9 greedy rate won at 3597.12 — the optimum lies near but likely not exactly at 0.9. Try rate 0.8 or 0.85, or start each restart at 0.95 greedy and decay toward 0.7 as restarts proceed, giving early restarts quality construction and later restarts diversification.

5. **Add a first-improvement insertion variant with random transaction ordering as a low-cost competitor to best-improvement.** Rather than always scanning i from 0 to n and j exhaustively, shuffle the transaction order each round and accept the first improving relocation. This reduces per-round cost dramatically, allowing many more restarts (e.g., 50-100) under the same deadline while keeping the full insertion neighborhood — addressing the trade-off Gen 8 showed (200 shallow restarts = 3115.26) without losing neighborhood strength. Also, explicitly verify `import time` appears at module top, since 2 of 10 programs (20%) scored 0.00 from this trivial crash.
