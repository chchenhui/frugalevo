# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

# Optimization Insights Analysis

## Successful Algorithmic Patterns
- **Sampled greedy construction + best-improvement insertion local search + capped multi-restart remains the winning combination**: The current best program (Gen 5, combined score 3597.12, makespan 277.00) uses randomized greedy (10 candidates/step, 0.9 exploration rate), full-range insertion local search (up to 30 rounds), and a 20-restart cap under a 100-second budget — still undefeated across all 19 generations.
- **Greedy + short-range 2-opt swap local search is the only newly-correct successful approach**: Gen 13 ("Greedy Construction with 2-opt Local Search", combined 3401.36, makespan 293.00, schedule 3.00, validity 1.00) confirms that greedy construction from multiple starting transactions plus nearby-swap refinement (Fibonacci position spans 1,2,3,5,8,13) with a cost cache produces valid, competitive schedules — but lands 196 points below the best, consistent with prior findings that swaps (293-296) trail insertion moves (277).
- **Cheap incremental cost oracle usage is a shared trait of all correct programs**: Both Gen 5 and Gen 13 rely on `workload.get_opt_seq_cost` evaluations structured around incremental construction and caching; every program that misused or over-queried the cost interface (Gens 10, 11, 12, 16, 17, 18) scored 0.0.

## Ineffective Approaches
- **Elaborate metaheuristics without correctness discipline produce zero score**: Gens 10-12, 16-18 (beam search + GRASP, GRASP + hybrid local search, beam + iterated local search, greedy + SA variants) all scored 0.0 despite sophisticated designs — beam search with truncated remaining lists, interface mismatches with `get_best_schedule`, and misused `get_opt_seq_cost` calls meant no valid schedules were returned. Complexity increased failure modes, not quality.
- **Missing `import time` is now the single most repeated fatal bug**: Gens 14, 15, and 19 all scored 0.00 purely because `time.time()` was called without importing `time` — the bug pattern has now appeared in 5 of 20 programs (Gens 4, 6, 14, 15, 19), each an instant NameError before any scheduling occurs. Gen 19's sound greedy + SA design (geometric decay, batched time checks, 25s budget) was never evaluated.
- **Expensive O(n²)-per-transaction insertion sweeps cause timeouts**: Gen 16's hybrid local search (full insertion sweeps each requiring a full `seq_cost` call, 20 GRASP restarts) was flagged as extremely slow — its failure indicates timeouts, in contrast to Gen 5's per-candidate incremental evaluation that stays within budget.
- **Heavy randomized construction dilutes greedy signal**: Gen 18's 95% exploration rate and 6-candidate sampling with convoluted reinsertion logic failed validation entirely, mirroring Gen 7's earlier finding that near-random construction caps quality.

## Implementation Insights
- **Import hygiene and minimal dependencies separate scoring programs from zero programs**: Gen 5 correctly places `import time` inside `get_best_schedule` before use; Gens 14, 15, 19 (which copied deadline/SA patterns from it) dropped the import and crashed. Any time-budgeted code must verify imports before adding annealing machinery.
- **Full-range insertion local search beats windowed/adjacent/2-opt swap neighborhoods**: Gen 5's insertion (each txn tried at every position, up to 30 rounds) achieved makespan 277.00, outperforming Gen 13's windowed 2-opt (293.00) and earlier adjacent/windowed swaps (296.00) — broader move neighborhoods pay off despite higher query cost.
- **Holdout/restore candidate sampling is the proven greedy pattern**: Gen 5 (and previously Gens 0, 8) evaluates sampled candidates by popping them into a holdout list and restoring them afterward, avoiding duplicates cleanly; Gen 13 achieved the same effect by evaluating marginal cost from multiple starting transactions.
- **Long budget + capped restarts beats many shallow restarts**: Gen 5's 100-second budget with a 20-restart cap gives deep local search time per restart; Gen 16's 20 GRASP restarts with heavy per-round work timed out, and Gen 8's 200 shallow restarts scored only 3115.26.

- **Score trajectory**: 2702.70 (Gen 0) → 3367.00 (Gen 1) → 3236.25 (Gen 2) → 3311.26 (Gen 3) → 0.00 (Gen 4) → **3597.12 (Gen 5, best)** → 0.00 (Gen 6) → 3412.97 (Gen 7) → 3115.26 (Gen 8) → 3367.00 (Gen 9) → 0.00 ×7 (Gens 10-12, 14-16, 18-19) → 3401.36 (Gen 13) → 0.00 (Gen 17-19). # META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

# Recommendations for Future Program Mutations

1. **Add a static `import time` at module top plus a defensive fallback inside `get_best_schedule`.** With 5 of 20 programs (25%) scoring 0.0 solely from missing `import time`, any mutation adding time-budget logic must guarantee the import. Write `import time` both at module level and at the top of `get_best_schedule` (as Gen 5 does), and before any new annealing/restart machinery, run a trivial sanity check (e.g., a 3-second-budget loop) to confirm no NameError occurs.

2. **Apply simulated annealing acceptance only to the insertion local search, preserving best-so-far separately.** Extend `local_search_insertion` to accept moves with `c < best_cost * (1 + temp * 0.01)` where temp decays geometrically (e.g., 0.99 per round) from 1.0 to 0.0 over ~40 rounds, while tracking `global_best_cost`/`global_best_seq` outside the loop. This keeps Gen 5's winning insertion neighborhood (makespan 277.00 vs 293 for swaps) but escapes the local minima where strict best-improvement descent stalls after ~30 rounds.

3. **Interleave a full pairwise-swap sweep after each insertion sweep in the same local search round.** Alternate: one pass of the existing i/j insertion loops, then one pass swapping `seq[i]`/`seq[j]` for all i<j (same O(n²) query pattern via `get_opt_seq_cost`, so no new API risk). Evidence: insertion (277) and swaps (293-296) explore different move types, and Gen 13 proved swap-based refinement validates reliably with a cost cache — the hybrid covers both move classes within the proven 20-restart/100-second structure.

4. **Tune the greedy exploration rate on a per-restart schedule: 0.95 → 0.85 across restarts.** Gen 5's 0.9 greedy rate is the known optimum region (Gen 0 at 1.0 scored 2702, Gen 7 at ~0.05 greedy scored 3413), but the optimum may vary by workload. Implement `sample_rate = 0.95 - 0.10 * (restart / 20)` so early restarts exploit greedy signal and later restarts diversify, with `num_samples` also varied (e.g., 8 early, 12 later) — this is a pure parameter mutation with zero structural risk.

5. **Implement a first-improvement insertion variant with shuffled transaction order as a cheaper inner loop.** Before each local search round, shuffle the iteration order of `i` and accept the first improving relocation immediately (breaking the inner j-loop), cutting per-round query count dramatically. Use the savings to raise the restart cap from 20 to 40-50 within the same 100-second deadline, since Gen 8 showed shallow search hurts but more deep restarts help — keep best-improvement for the final round of each restart to polish the result.
