# Analysis of Program Evaluation Results

## Successful Algorithmic Patterns
- **A new cost frontier of 705.09 (avg 141.02)** was achieved by Gen 29 ("Reuse-Discounted Dijkstra Steiner Broadcast Routing") — a **31% reduction below the previous 1021.03 frontier** and ~32% below the 1035.14 Dijkstra floor. This is by far the largest cost breakthrough recorded, and it breaks the earlier assumption that scoring-time-only reuse accounting (1021.03) was optimal.
- **The winning mechanism is guarded graph-mutation reuse**: Gen 29 rewrites paid trunk edges to REUSE_EPSILON (1e-9) in a mutable cost graph, but *accepts the reuse-discounted path only if it beats (or ties) the Dijkstra baseline* (`r_cost <= baseline_cost + SAFETY_MARGIN`). The earlier failure (Gen 25, cost 1618.37) mutated costs *without* this acceptance guard; Gen 29's guard converts the same mutation from catastrophic to a 31% win. The guard, not the mutation, is the differentiator.
- **Expensive-first ordering remains a consistent, validated component**: Gen 29 orders destinations by descending baseline cost (via a single shared `single_source_dijkstra` precomputation), so expensive destinations commit trunks first and cheaper ones latch on via near-free edges. This continues the Gen 27 validation of that ordering.
- **100% success (5/5) remains fully solved** across all 8 programs in this batch — every one kept the `BroadCastTopology` constructor untouched and used `append_dst_partition_path(dst, j, [s, t, G[s][t]])` per-partition edge emission.

## Ineffective Approaches
- **Greedy shared-edge reweighting without acceptance guards is flat**: Gens 31 and 34 (both 749.49, avg 149.90) — dynamic zero-cost reweighting of shared edges without a baseline comparison — landed 6% above Gen 29's 705.09, confirming the acceptance guard adds real savings beyond naive free-edge reuse.
- **Everything else in this batch was far worse**: Gens 32, 33, and 37 all cost 1035.14 (the plain-Dijkstra floor) — partial 0.3× discounts, None-cost median fallbacks, and "never exceed baseline" candidate selection all degenerated to Dijkstra. Gen 35's congestion-spreading (0.5/load penalties, reuse bonus 0.01) cost 1029.73, and Gen 36's lookahead-bonus k-shortest approach cost 894.13. The monotone ranking from previous insights (free > discounted > epsilon-rewritten) is now refined: **epsilon-rewriting is best *when guarded by baseline acceptance***.
- **Replicating one path into all partitions without trunk accounting inflates cost**: feedback for Gens 32/33/37 explicitly notes that duplicating identical full paths per partition dominates cost and leaves no savings room — Gen 29's edge-by-edge trunk commitment to `paid_edges` is what enables cross-destination reuse.

## Implementation Insights
- **Gen 29's key implementation pattern**: one shared `single_source_dijkstra` for baselines and ordering; a mutable `w = h.copy()` with None costs normalized to 1e9; per-destination `dijkstra_path(w, ...)` on the mutated graph; strict `r_cost <= baseline_cost` acceptance; then trunk edges of the *chosen* path get added to `paid_edges` and their cost set to 1e-9. Only accepted trunks are discounted — never speculative ones.
- **Cost normalization matters**: Gen 29's `DEFAULT_FALLBACK_COST = 1e9` for None-cost edges contrasts with Gen 31's 1e6 penalty (feedback flagged the 1e6 penalty as potentially undermining optimization). 1e9 makes None-cost edges effectively unreachable while keeping the cost landscape clean for the reuse comparison.
- **Robustness patterns remain cheap and effective**: Gen 29 handles missing costs, removes self-loops and src in-edges, falls back to baseline paths when a reuse route fails, and skips unreachable destinations with a warning — matching the batch-wide 100% success rate.
- **SAFETY_MARGIN = 0.0 is sufficient**: ties are accepted; the earlier insight that strict-improvement-only rules make heuristics inert (Gen 28) does not apply here because the reuse-discounted route is scored against a *different* (mutated) graph, not against its own minimal path.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add a one-step lookahead acceptance: commit the trunk that maximizes future reuse, not just the cheapest current path.** Gen 29's guard is the key differentiator, but it accepts only the first reuse path that beats baseline. Extend it: when a destination has multiple near-tie reuse candidates (e.g., via `shortest_simple_paths` capped at k=4), pick the one whose edges overlap most with the *union of baseline paths of remaining unprocessed destinations* — building trunk toward where future demand will go. Keep the same acceptance guard; only candidate *selection among ties* changes.

2. **Sweep SAFETY_MARGIN slightly negative vs positive to tune guard strictness.** Gen 29 uses SAFETY_MARGIN = 0.0 (ties accepted). Because reuse paths are scored on the mutated graph while baseline is on the true graph, accepting a tie means the trunk-building effect is free but never costs more — but a small *positive* margin (e.g., accept up to 2% over baseline) may pay a small premium now to unlock larger epsilon savings for later cheap destinations. Test margins ∈ {0.0, +0.02, +0.05} as single-variable mutations.

3. **Re-run the expensive-first ordering loop after convergence (two-pass trunk refinement).** After all destinations are routed and `paid_edges` is fully populated, do a second pass in the same descending-cost order recomputing each destination's path on the final mutated graph with the acceptance guard. First-pass early destinations (the expensive ones) couldn't exploit trunks that later destinations created; a second pass lets them latch onto the now-complete trunk. Cheap to implement — the loop body is identical, only reset `chosen` between passes.

4. **Try ordering heuristics beyond expensive-first: descending *path length* (hop count) and descending number of shared edges with other baselines.** Gen 27/29 validated expensive-first, but an untested alternative is ordering by descending baseline path *hop count* — longer paths commit more edges, creating a richer trunk for short-path destinations. Alternatively, order by descending overlap of the baseline path with other destinations' baseline paths (a proxy for trunk centrality). Keep the guard and epsilon mechanism untouched; only the sort key changes.

5. **Directional consistency check: enforce that committed trunks use a consistent edge orientation and also discount the reverse edge.** If two destinations route in opposite directions along a shared corridor (u→v and v→u), Gen 29's `paid_edges` treats them as distinct keys, potentially paying twice for symmetric capacity. Add the reversed pair `(v, u)` to `paid_edges` when committing `(u, v)` — but only if the reverse edge exists and its cost is also discounted — and verify each reuse path still passes the baseline guard. If the cost model is per-direction, this is a no-op; if symmetric, it's a direct saving.
