# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns
- **Robust candidate generation + fallbacks**: The current best program (Gen 5, "Load-Aware Multi-Path Broadcast Topology Search") uses `nx.shortest_simple_paths` with k=4 candidates plus Dijkstra fallback on `NetworkXNoPath`/`NodeNotFound`, achieving 100% success rate (5/5 configs, runs_successfully 1.00). This same pattern produced the two other fully-correct programs (Gen 2, Gen 9), all of which strip source in-edges and self-loops before searching — a necessary preprocessing step every correct program shares.
- **Per-edge appended tuples with original graph data**: All correct programs append edges as `[s, t, G[s][t]]` per partition via `append_dst_partition_path`. Programs that appended whole path lists, repeated edge tuples, or chained tree-growth segments (Gen 3, Gen 4, Gen 7) failed validation entirely.
- **Simple greedy Dijkstra baseline remains the correctness floor**: Gen 0 (Dijkstra per destination, identical paths across partitions) is 100% correct with total cost 1035.14 — all correct variants improve on this only modestly (Gen 5: 1002.43, Gen 2: 1015.93, Gen 9: 1005.13, Gen 6: 1034.51), and none achieved a nonzero cost_score.
- The best program is the lowest-cost correct variant (total 1002.43, avg 200.49) using half-best-path + spread-alternatives assignment with load-aware scoring `(cost + 1e-9) / (1 + load_penalty)`.

## Ineffective Approaches
- **Load balancing over cost minimization**: Every load-spreading heuristic (Gen 2, Gen 5, Gen 6, Gen 9) earned cost_score 0.00. Feedback consistently notes that spreading partitions onto more expensive parallel paths trades away the dominant scoring component (cost) for load balance, which the metric does not reward. Gen 9's edge_load counter was even computed but never used — pure overhead.
- **Complex structural approaches break validation**: Gen 4's Steiner-tree growth produced discontinuous paths (e.g., expected `gcp:asia-southeast1-a`, got `gcp:asia-south2-a`); Gen 7's multicast tree planner failed on edge data access issues (`G[s][t]` lookups, `None` cost additions); Gen 3's relay approach duplicated identical paths across all partitions and malformed structures. All scored 0.0 with runs_successfully 0.00.
- **Unverified capacity/throughput constraints**: Gen 1 failed validation because greedy sharing-discount assignment never checked edge throughput/capacity, and setting None costs to infinity eliminated valid routes entirely.
- **Over-engineering**: Gen 7's feedback is explicit — "A simpler correct baseline would outperform this over-engineered approach."

## Implementation Insights
- **Correct edge-append format is non-negotiable**: Correct programs iterate `for i in range(len(path)-1)` and append `[s, t, G[s][t]]` per partition. This is the proven structural pattern; deviating (Gen 3, Gen 4, Gen 7) guarantees validation failure regardless of routing quality.
- **The current best's cost reduction (~3.2% vs Gen 0's 1035.14)** came from assigning ~half of partitions to the cheapest candidate path and spreading the remainder across ranked alternatives with load-aware scoring — a cost-first-with-minimal-spreading hybrid, unlike Gen 2's pure round-robin (1015.93) or Gen 6's 1.5x-cost-filter cycling (1034.51).
- **Defensive coding pays**: None-cost handling, exception guards, Dijkstra fallback, and division-by-zero guards appear in every 100%-success program. The `or 0.0` cost default in the best program's `path_cost` is safer than Gen 1's `None → infinity` (which killed valid routes).
- **Load tracking is computed but structurally unused in the best program's assignment of the best half** — its marginal cost win over Gen 0 (1002.43 vs 1035.14) suggests the gains come from candidate diversity itself, not load metrics.

## Performance Analysis
- **Cost trend across correct programs**: Gen 5 (1002.43) < Gen 9 (1005.13) < Gen 2 (1015.93) < Gen 6 (1034.51) < Gen 0 (1035.14). All fail cost_score (0.00), indicating the scoring baseline is well below ~1000 total cost; incremental load-balancing tweaks (~3% improvement) are insufficient to move the needle.

- **Correlation**: More aggressive multi-path spreading (Gen 2 round-robin, Gen 6 cycling) yields higher cost than the best program's majority-cheapest assignment — the closer assignment stays to the cheapest path, the lower the total cost, yet still not enough for cost_score gains.
- **Load-aware scoring variants cluster tightly** (1002–1015), suggesting current heuristics have exhausted easy gains within the "per-destination independent k-shortest-path" paradigm; the cost_score baseline appears to require a fundamentally different cost structure (e.g., shared-prefix/edge-sharing exploitation, which Gen 1 attempted but implemented incorrectly).

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Exploit shared-prefix edge sharing across destinations (correctly this time)**. Gen 1 attempted sharing-discount but failed on format/capacity handling; the global insights explicitly flag shared-prefix exploitation as the likely key to cost_score. Add a mutation that, for each partition, builds a multicast structure where destinations sharing a common prefix path reuse the same edges — but still emits per-destination edge lists `[s, t, G[s][t]]` via `append_dst_partition_path` (the non-negotiable format). Compute cost as if shared edges count once for the routing decision, while keeping per-partition output structurally identical to Gen 5.

2. **Replace load-aware spreading with pure cost-first assignment**. The insights show cost increases monotonically with more aggressive spreading (Gen 5's half-spread 1002.43 < Gen 2's round-robin 1015.93 < Gen 6's cycling 1034.51). Mutate the best program to assign ALL partitions to the cheapest candidate path per destination (weights = [n]), keeping the k=4 candidate generation and Dijkstra fallback as pure robustness. This should shave cost toward Gen 0's floor while retaining the structural advantages.

3. **Increase k_paths and use true shortest-path ordering rather than scored re-sorting**. Gen 5's marginal gains appear to come from candidate diversity, not load metrics. Try k_paths=8 or 16 (with an early-exit on cost inflation so the generator stops once candidates exceed the best cost by e.g. 3x), and score candidates purely by `path_cost`. This explores whether cheaper second-paths exist that Gen 5's k=4 truncation misses.

4. **Joint optimization across destinations via per-partition edge-reuse aggregation**. Process destinations in decreasing path-cost order, and for each partition, prefer candidate paths that reuse edges already chosen for other destinations in that same partition (scored with a reuse bonus rather than a load penalty — inverting Gen 5's load penalty into a reuse reward). If cost is charged per unique edge or aggregate flow discounts apply, reuse lowers total cost; keep the `[s, t, G[s][t]]` append format untouched.

5. **Model throughput/capacity explicitly as a feasibility filter, not a cost factor**. Gen 1 failed for ignoring throughput; Gen 9 computed edge_load without using it. Mutate Gen 5 to filter candidate paths whose aggregate per-edge partition count would exceed edge throughput capacity (using `h[s][t]['throughput']`), falling back to the next candidate — this guards against hidden feasibility requirements that may gate cost_score, without adding load-spreading cost overhead beyond what capacity actually demands.
