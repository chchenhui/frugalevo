# Analysis of Program Evaluation Results

## Successful Algorithmic Patterns

- **Multi-candidate enumeration is the single biggest win**: The current best program (Gen 9, "Multi-Strategy Greedy Placement with KVPR Refinement", score **23.61**) builds placements from **five** sorting/scoring combinations (req_rate/slo desc with post-KVPR and current-KVPR scoring, model size desc, density desc, size asc) and keeps the best. This beat every single-strategy variant (Gen 3/4/6 at 22.34, Gen 8 at 22.44, Gen 7 at 22.52) by ~0.8–1.3 combined points — the largest observed jump across generations.
- **Greedy density ordering (req_rate/slo descending) as the reliable base**: Every successful program (Gen 0 at 21.89, Gen 3/4/6 at 22.34) uses this sort, following Algorithm 1 with post-placement KVPR (weighted load / remaining memory) as GPU selection criterion.
- **Local search refinement adds consistent incremental gains**: Gen 7 (22.52), Gen 8 (22.44), and Gen 9 (23.61) all add a strict-improvement move loop off the hottest GPU. Gen 8's use of the second-highest KVPR as a lower bound for provable improvement, and Gen 9's strict-improvement criterion (accept only when max KVPR decreases) guarantee termination with monotone quality gains at ~0.00s runtime.

## Ineffective Approaches

- **Division-by-zero on zero remaining memory**: Gen 1 and Gen 5 both scored **0.00** due to "float division by zero" when a GPU's remaining memory hit exactly 0 after placement (Placement 3 crash aborted all test cases). Note the current best guards this with `if self.remaining_mem <= 0: return float('inf')` in `kvpr()` — a critical fix these earlier versions lacked.
- **State-mutation bugs in local search**: Gen 2 scored **0.00** with "list.remove(x): x not in list" — in-place list mutation during iteration and stale bookkeeping after accepted moves crashed evaluation. Gen 7's fix (index-based revert instead of `list.remove`) restored success.
- **Single-candidate strategies plateau below ~22.5**: All single-sort greedy variants cluster at 21.89–22.34, showing the greedy heuristic alone saturates; only candidate diversity plus refinement breaks past this.

## Implementation Insights

- **The current best's two-phase architecture**: five greedy candidates (`build_placement` with a `use_post_kvpr` flag alternating post-placement KVPR vs. current-KVPR scoring) followed by a 50-round `refine` loop. The refinement computes `new_hot_kv` and `new_other_kv` analytically before committing the move, only executing if `max(new_hot_kv, new_other_kv) < kvs[hot] - 1e-12` (epsilon tolerance avoids float-comparison loops).
- **Defensive memory handling**: `GPUState.kvpr()` returning `inf` for zero/negative memory and `try_add` rejecting `model.model_size >= remaining_mem` cleanly prevent both division-by-zero and overcommitment — directly addressing the failure modes of Gen 1/2/5.
- **Correct move bookkeeping in refinement**: Gen 9 uses `models.pop(idx)` with symmetric updates to `remaining_mem` and `load`, then `break`s out to recompute KVPRs fresh each round — avoiding Gen 2's stale-state bug.

## Performance Analysis

- **Score progression**: Gen 0: 21.89 → Gen 3/4/6: 22.34 → Gen 7: 22.52 → Gen 8: 22.44 → Gen 9: **23.61**. Multi-candidate + refine (Gen 9) delivers a step change (+1.09 over best single greedy+local-search).
- **Crash = total failure**: Gen 1, 2, and 5 all scored 0.00 from a single runtime error on one placement, despite structurally correct algorithms. Robustness (epsilon guards, safe division, index-based list ops) is a precondition for any score.
- **Runtime is not a constraint**: All successful programs run in ~0.00s, meaning the 5× candidate enumeration and 50-round refinement are essentially free — there is ample headroom to add more candidate orderings or stronger search without time penalty.
- **Post-KVPR vs. current-KVPR scoring both contribute**: Gen 9 includes both variants (`use_post_kvpr` True/False) among its candidates; since the best candidate isn't reported per-strategy, keeping both hedges against workload variation that favored Gen 0's current-KVPR variant.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add swap-based local search to the refinement loop**: Extend `refine()` with a second move type that tries swapping a model from the hottest GPU with a smaller model on a cooler GPU (checking that both resulting KVPRs are below the current max). The current move-only refinement terminated quickly on many placements, meaning single-model moves can't escape local optima — swaps unlock improvements when memory fragmentation blocks relocation. Keep the same strict-improvement criterion (`max(new_hot_kv, new_other_kv) < kvs[hot] - 1e-12`) to guarantee termination.

2. **Expand the candidate pool with additional orderings**: Add more sorting keys to `candidates_specs`, e.g., density ascending, `req_rate` descending alone, `slo` ascending, and a random-tiebreak perturbation of the req_rate/slo sort (multiple shuffles with fixed seed). Since the 5-candidate enumeration produced the single largest score jump (+1.09) and runtime is ~0.00s, candidate diversity is nearly free and directly extends the proven winning pattern.

3. **Add a simulated-annealing or perturb-and-repair phase after refinement**: Take the best placement from the candidate pool, apply a random disruptive move (relocate a random model even if it worsens max KVPR), re-run `refine()`, and keep the result only if it improves the best score. This is a classic iterated local search wrapper around the already-successful refine loop, and the zero runtime cost means many restarts are affordable. Use a fixed RNG seed for determinism.

4. **Optimize refinement target selection beyond the single hottest GPU**: Currently `refine()` only moves models off the max-KVPR GPU; extend it to also try moves off the second-highest KVPR GPU when the hottest is stuck, or loop over GPUs in descending KVPR order each round. Some placements may have a near-tied hot pair where improving the second GPU becomes the binding constraint once the first improves — this generalizes the proven hot-GPU heuristic without changing its structure.

5. **Make greedy placement tie-aware with lookahead scoring**: In `build_placement()`, when multiple GPUs have near-equal post-placement KVPR (within a small epsilon), break ties by preferring the GPU with the largest remaining memory after placement (maximizing future flexibility). This addresses the greedy heuristic's known weakness — myopic tie-breaking that fragments memory — while preserving the req_rate/slo descending base sort that every successful program has used since Gen 0.
