# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **The current best program’s non-refined hierarchical pipeline is the strongest validated baseline.** It achieves `combined_score = 0.13`, `GPU balancedness = 0.66`, `expert balancedness = 0.25`, and the best reported `times_inference = 0.24`. Its sequence—cardinality-constrained group-to-node packing, node-local greedy replication, then physical-replica-to-GPU packing—has consistently preserved correctness while reaching the observed balance ceiling.

- **Greedy max effective-load replication is a stable and correct policy.** The current implementation selects redundant experts with `(weight / logcnt).max(dim=-1).indices`, assigns their rank from the current `logcnt`, and increments only the selected expert count. This policy was also successful in prior hierarchical generations and supports valid `phy2log`, replica-rank, and logical-count metadata without costly refinement.

- **Heap-based fixed-cardinality LPT packing remains preferable to repeated tensor scalar selection for the CPU path.** The current `balanced_packing` materializes each row once, sorts once, and uses a min-heap of `(load, pack_id, item_count)` entries. Generation 21’s heap-based LPT version likewise passed correctness and retained `GPU balancedness = 0.66`; its deterministic tuple ordering also preserves lowest-index tie-breaking. The current implementation’s leaner overall pipeline reaches the better inference result of `0.24`.

- **Avoiding post-placement swap refinement improves runtime without changing measured balance.** Generation 9 (`hierarchical_lpt_refine`), Generation 12, Generation 17 (`refined_hierarchical_packing`), and Generation 18 all retained the same `0.66/0.25` GPU/expert balancedness pattern but had worse inference times (`0.48`, `1.15`, `0.79`, and `0.50`, respectively). The current greedy-only implementation demonstrates that refinement was not responsible for the available balance quality.

## Ineffective Approaches

- **Tensorizing portions of packing did not overcome the sequential scheduling bottleneck.** Generation 20 (`tensorized_batched_packing`) removed heap/scalar overhead and incrementally updated selected replica loads, but still used a per-item Python loop in `balanced_packing`. It achieved only `times_inference = 0.35`, `times_algorithm = 0.01`, `speed_score = 0.01`, and `combined_score = 0.13`, trailing the current program’s `0.24` inference time while not improving either balance score.

- **CPU transfer plus Python list/row scheduling remains costly.** Generation 21’s implementation converted weights and indices to CPU/Python lists and ran heap scheduling per row; despite passing validation, it scored `times_inference = 0.42`, `times_algorithm = 0.11`, `speed_score = 0.00`, and `combined_score = 0.13`. The heap reduces least-loaded-pack lookup complexity, but conversion and Python-loop costs dominate the measured speed behavior.

- **Alternative water-filling and waterline policies did not improve the limiting expert metric.** Generations 10, 13, and 19 used discrete water-filling or waterline/top-k allocation but reached only `expert balancedness = 0.24`, below the current program’s `0.25`, with `combined_score = 0.12`. The changes added sorting, top-k, or allocation logic without improving the core imbalance outcome.

- **Local exchange or swap refinement consistently increased planning cost with no score gain.** Refined variants remained at the same `GPU balancedness = 0.66` and generally `expert balancedness = 0.25`, but their inference costs were materially worse than the current `0.24`. The evaluation evidence indicates that the hierarchy and initial greedy placement determine almost all measured balance, not subsequent local repair.

## Implementation Insights

- **The current program separates sequential placement decisions from tensorized map reconstruction.** `balanced_packing` computes pack IDs and within-pack ranks; `replicate_experts` computes logical-expert assignments and replica ranks; afterward, `inverse`, `gather`, `view`, and `scatter_` compose final mappings. This preserves correctness while avoiding Python-level construction of final physical/logical maps.

- **Fixed capacity is encoded directly in the heap lifecycle.** In `balanced_packing`, a heap entry includes `item_count`, and a pack is not reinserted after reaching `groups_per_pack`. This guarantees exactly equal cardinality across packs, rather than merely favoring low-load packs. The same constraint is essential for producing valid GPU slot layouts and is a shared trait of correct hierarchical implementations.

- **The current best program contains effective low-overhead special cases and deterministic behavior.** When `groups_per_pack == 1`, it returns expanded `arange` indices and zero ranks without sorting or heap operations. Elsewhere, heap tuple ordering `(current_load, pack_id, item_count)` provides deterministic low-index tie resolution, while the global fallback reuses the same hierarchical function with `(num_groups, num_nodes) = (1, 1)`.

- **CPU-side placement is intentionally isolated, while map operations remain tensorized.** `rebalance_experts` converts load statistics once using `weight.float().cpu()`, and the packing routine creates CPU integer tensors only after heap assignments finish. Although this CPU placement remains the dominant bottleneck, this structure avoids repeated device synchronization during sequential greedy decisions and helps explain the current program’s comparatively low `times_inference = 0.24`.

## Performance Analysis

- **The current best differentiates itself primarily through inference time, not balance.** Its `combined_score = 0.13`, GPU balance `0.66`, and expert balance `0.25` match the broader successful greedy-hierarchical family. Its `times_inference = 0.24` is better than Generation 20’s `0.35`, Generation 21’s `0.42`, Generation 14/15’s `0.40`, Generation 9’s `0.48`, Generation 18’s `0.50`, Generation 17’s `0.79`, and Generation 12’s `1.15`.

- **GPU balance is effectively invariant across correct hierarchical variants.** Heap LPT, tensorized batched packing, waterline allocation, and refinement-based approaches repeatedly reached `balancedness_score_gpu = 0.66`. This strongly associates the score with the hierarchy—group placement across nodes followed by intra-node GPU placement—rather than the particular implementation of local scheduling.

- **Expert balancedness is the persistent quality limit.** The current program’s `0.25` is the best reported expert score, while the water-fill/waterline variants fall slightly to `0.24`; neither heap scheduling nor tensorized batching exceeded `0.25`. Consequently, changes to packing mechanics affected runtime more than they affected the measured expert-distribution quality.

- **Algorithm and inference metrics are not tightly aligned, but Python-heavy/reﬁnement-heavy paths are consistently unfavorable for end-to-end timing.** Generation 21 reports a somewhat higher `times_algorithm = 0.11` than the current program’s `0.01` but worse inference (`0.42` versus `0.24`); Generation 20 has the same `0.01` algorithm score yet also slower inference (`0.35`). Across these results, the shared `speed_score` near zero (`0.00–0.01`) indicates that sequential CPU scheduling remains a broad limitation, while the current program minimizes its runtime impact better than the alternatives.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Preserve the exact three-stage greedy hierarchy and optimize only around it.** Keep fixed-cardinality group-to-node LPT packing, node-local max-effective-load replication, and fixed-cardinality physical-to-GPU packing unchanged, since this is the only family repeatedly reaching `0.66` GPU and `0.25` expert balancedness. Do not add swap, exchange, or refinement passes unless a mutation can prove it replaces—not follows—the initial placement, because all measured post-placement refinements increased inference time without improving balance.

2. **Fuse CPU materialization in `balanced_packing` to avoid duplicate full-row Python conversions.** Replace separate `cpu_weight.sort(...).indices.tolist()` and `cpu_weight.tolist()` calls with a single CPU sorted-value/index materialization, e.g. obtain `sorted_weight, sorted_indices = cpu_weight.sort(...)` and iterate paired row lists from those outputs. This retains the successful heap LPT semantics and deterministic ordering while removing the random-access `weights[group]` dependency and potentially reducing conversion/allocation overhead in the dominant sequential scheduling path.

3. **Add a direct no-replication fast path in `rebalance_experts`.** When `num_replicas == num_logical_experts`, bypass hierarchical grouping, replication, and physical packing entirely: return per-layer expanded `arange(num_logical_experts)` as both physical-to-logical and logical-to-physical identity mappings, with `logcnt = 1`. This extends the current program’s successful `groups_per_pack == 1` degenerate-case strategy and can eliminate nearly all planning work for common identity-replica configurations without altering skewed replication behavior.

4. **Special-case fully local topology configurations before constructing group maps.** If `num_nodes == 1`, skip Step 1 group-to-node packing and use the identity `mlog2log`; if `num_gpus == num_nodes`, skip Step 3 physical-to-GPU packing because each node has exactly one GPU and its physical layout is already GPU-local. These are correctness-preserving structural shortcuts that retain the validated hierarchy for general cases but avoid heap sorting, inverse permutations, and gathers when hierarchy levels are mathematically vacuous.

5. **Benchmark a batched GPU-resident LPT implementation only for large packing rows, retaining heap LPT for smaller ones.** Implement a threshold-based alternative that sorts on-device and uses masked tensor `argmin` over non-full pack loads for each assignment, while preserving exact capacity and lowest-index tie behavior; dispatch to it only when `num_groups` or physical experts per node is sufficiently large. Prior tensorization was slower when used universally, but a selective hybrid may avoid Python/CPU scheduling overhead on large layouts without sacrificing the current best heap path on the small or moderate cases where it is fastest.
