# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **The current best program’s simple hierarchical pipeline remains the strongest validated baseline.** It preserves the consistently successful sequence: cardinality-constrained group-to-node packing, node-local greedy replication, then replica-to-GPU packing. It attains `combined_score = 0.13`, `GPU balancedness = 0.66`, `expert balancedness = 0.25`, and the best reported current inference timing of `0.24`. This confirms the prior finding that hierarchy reliably produces the observed GPU-balance ceiling.

- **Greedy replication using maximum current per-replica load is a robust correctness pattern.** The current program’s `replicate_experts` repeatedly chooses `(weight / logcnt).max(dim=-1).indices`, assigns the next replica rank from `logcnt`, then increments the selected count. This same policy was used by Generations 9, 12, 14–18 and consistently passed validation, preserving valid replica metadata despite differing placement implementations.

- **Avoiding swap refinement is beneficial for runtime-facing performance without reducing measured balance.** The current program uses greedy heap packing only and reaches `times_inference = 0.24`. In contrast, refinement-heavy variants had slower inference while retaining the same balance: Generation 17 (`refined_hierarchical_packing`) reached `0.79`, Generation 9 (`hierarchical_lpt_refine`) reached `0.48`, and Generation 18’s exhaustive bottleneck-pack swap reached `0.50`. All still reported GPU/expert balancedness of `0.66/0.25`.

- **Tensorized mapping reconstruction is a successful shared implementation pattern.** The current program uses `scatter_` for inverse permutations and flattened indexed `scatter_` for `log2phy`. This avoids Python-level per-replica metadata construction after placement decisions are complete. Its `times_inference = 0.24` improves on Generation 14’s `0.40`, Generation 15’s `0.40`, Generation 17’s `0.79`, and Generation 12’s `1.15`.

## Ineffective Approaches

- **Local swap and exchange refinement added planning complexity with no measured balance improvement.** Generation 9’s bounded candidate exchanges, Generation 12’s bounded pairwise swaps, Generation 17’s up-to-eight heavy/light refinements, and Generation 18’s exhaustive single-swap refinement all remained at `GPU balancedness = 0.66` and `expert balancedness = 0.25`. Their combined scores stayed at `0.13` or lower, while inference time worsened substantially relative to the current program.

- **CPU heap/list scheduling remains a speed bottleneck regardless of heap-selection complexity.** The current implementation materializes `cpu_weight`, calls `.tolist()` on sorted indices and each weight row, then performs Python `heapq` operations for every group. Generation 15 similarly replaced repeated tensor selection with heap packing but still obtained only `speed_score = 0.01`, `times_algorithm = 0.10`, and `times_inference = 0.40`; Generation 16 likewise had `speed_score = 0.00` despite CPU-list packing. The theoretical advantage of heap selection is dominated by transfers and Python-loop overhead.

- **Water-filling/top-k variants did not solve expert-level imbalance.** Generation 10 (`waterfill_lpt_rebalance`) and Generation 13 (`waterline_slot_packing`) used discrete water-filling or waterline top-k allocation, but expert balancedness was `0.24`, slightly below the current program’s `0.25`, with combined score `0.12`. These changes did not improve the persistent weak expert-balance metric.

- **Additional sorting and metadata-oriented vectorization did not automatically improve speed.** Generation 13 used batched tensor operations, stable sorts, top-k selection, and inverse permutations, yet had `algorithm time = 0.00`, `speed = 0.01`, and combined score `0.12`. Its repeated sorting/top-k/permutation work and CPU metadata conversion offset the benefits of more tensorized placement logic.

## Implementation Insights

- **The current program cleanly separates placement decisions from map construction.** `balanced_packing` determines group/GPU pack IDs and ranks; `replicate_experts` determines logical replica assignments and ranks; then gather/scatter operations compose `log2mlog`, `mlog2log`, `phy2pphy`, and final `pphy2log`. This decomposition is central to its correctness and allows the output mapping phase to stay compact and tensor-based.

- **Fixed-cardinality packing is important for valid physical layout.** In `balanced_packing`, each heap entry contains `(current_load, pack_id, item_count)`, and a full pack is not reinserted. This guarantees exactly `groups_per_pack` items per pack rather than merely minimizing load. That constraint is consistently present in the validated hierarchical programs and supports valid GPU slot allocation.

- **The current best program contains a meaningful degenerate fast path.** When `groups_per_pack == 1`, it returns an expanded `arange` pack index and zero ranks directly, avoiding sort, CPU conversion, Python list construction, and heap work. This retains a low-overhead path for configurations that do not need actual load-aware packing.

- **The current output-map allocation is correct but less compact than the prior compact-allocation pattern.** It allocates `log2phy` with `maxlogcnt = num_redundant_experts + 1`, the theoretical maximum, rather than using the realized `int(logcnt.max().item())` described in prior successful implementations. Despite that allocation choice, its mapping generation is still fast enough to yield `times_inference = 0.24`, indicating that the dominant cost remains CPU-side placement rather than the final scatter.

## Performance Analysis

- **The current best is distinguished by inference timing, not by balance or combined score.** Its `combined_score = 0.13`, GPU score `0.66`, and expert score `0.25` match the broad greedy-hierarchical family, including Generations 9, 12, 14, 15, 17, and 18. Its main measured advantage is `times_inference = 0.24`, better than Generation 14/15 (`0.40`), Generation 9 (`0.48`), Generation 18 (`0.50`), Generation 17 (`0.79`), and Generation 12 (`1.15`).

- **GPU balance is highly stable across all correct hierarchical designs.** Every listed hierarchical variant reached `balancedness_score_gpu = 0.66`, including LPT, heap-based, water-filled, refined, and Python-row implementations. This demonstrates that the group-to-node locality hierarchy establishes most of the measured GPU balancing benefit; refinements did not raise the observed score.

- **Expert balance is the limiting quality metric across the evaluation set.** The current best reaches `0.25`, while water-filling variants Generations 10, 13, and 19 reach `0.24`; no evaluated correct implementation exceeds `0.25`. Thus, swapping, alternative packing orders, heap tie-breaking, and waterline allocation affected neither the fundamental expert-balance ceiling nor the combined score materially.

- **Algorithm-time and inference-time scores do not move together cleanly.** The current program reports `times_algorithm = 0.01` and `times_inference = 0.24`, while Generation 12 reports a much higher algorithm-time value of `0.83` but much worse inference at `1.15`; Generation 17 reports `0.52/0.79`. Across the programs, the repeated zero or near-zero speed scores indicate that CPU scheduling overhead remains substantial, while avoiding refinement is more strongly associated with better inference behavior.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Preserve the three-stage hierarchical policy and restrict mutations to implementation-level changes.** Keep group-to-node fixed-cardinality packing, node-local greedy replication, and physical-expert-to-GPU fixed-cardinality packing exactly intact, since this family consistently achieves the best observed `0.66` GPU and `0.25` expert balancedness. Do not add swap/refinement passes by default: every tested refinement retained the same balance while substantially worsening inference time.

2. **Implement a device-resident tensorized version of `balanced_packing`, with the current heap implementation retained as a fallback.** Replace the per-row `.cpu().tolist()` plus `heapq` schedule with descending tensor sort, tensor `pack_load`/`pack_count` state, and a masked `argmin` over non-full packs at each assignment step. This preserves the validated “heaviest group into currently least-loaded eligible pack” semantics and equal-cardinality constraint, while directly targeting repeated host transfers and Python object scheduling.

3. **Remove redundant CPU conversions and enforce a single placement-device policy end-to-end.** `rebalance_experts` currently performs `weight.float().cpu()`, and `balanced_packing` converts to CPU again; mutate this so weights are cast once but remain on their original device, with all resulting pack-index tensors allocated on that same device. The final gather/scatter map construction is already efficiently tensorized, so eliminating unnecessary device movement is the most compatible optimization with the current best design.

4. **Add safe no-replication and identity-layout fast paths before entering replication and packing.** When `num_replicas == num_logical_experts`, return `phy2log = arange`, zero replica ranks, unit logical counts, and construct `log2phy` directly; similarly retain and extend the existing `groups_per_pack == 1` shortcut through downstream stages where mappings are provably contiguous. This follows the best program’s successful degenerate-path pattern and can avoid sorting, replication loops, and packing work without changing skewed-input behavior.

5. **Compact the logical-to-physical allocation using the realized maximum replica count, while preserving the current flattened scatter reconstruction.** After `replicate_experts`, compute `maxlogcnt = int(logcnt.max().item())` rather than always allocating `num_redundant_experts + 1`, then use the same `phy2log * maxlogcnt + phyrank` flattened `scatter_` construction. This is a low-risk memory and map-initialization reduction that preserves the current program’s fast, validated tensorized metadata path; benchmark it separately because it introduces one scalar synchronization if executed on GPU.
