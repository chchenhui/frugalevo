# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Hierarchical group-to-node placement consistently produced the strongest GPU balance observed.** The current best program uses `tokens_per_group`, cardinality-constrained `balanced_packing`, and a node-local replication stage before GPU packing. It achieves `balancedness_score_gpu = 0.66`, matching every validated hierarchical variant (Generations 0–8 and 11). This indicates that assigning whole expert groups to nodes first, then packing node-local replicas across that node’s GPUs, is reliably effective for GPU-level balance.

- **Greedy replication by current per-replica load is a stable correct pattern.** The current best uses `redundant_indices = (weight / logcnt).max(dim=-1).indices` for each added replica. This same mechanism appeared throughout the evaluated programs and consistently passed validation. It preserves straightforward replica-rank construction through `rank[:, i] = logcnt[...]` and produces valid `phy2log`, `phyrank`, and `logcnt` metadata.

- **The current best program has the strongest reported inference timing.** Its `times_inference = 0.28` is better than the other listed variants: Generation 5 reported 0.39, Generations 2/3/11 about 0.40–0.41, Generation 6 at 0.43, Generation 8 at 0.46, Generation 7 at 0.59, and Generation 0 at 0.74. The successful pattern is retaining compact, tensor-based output-map construction rather than adding costly placement refinements.

- **Compact logical-to-physical allocation is a useful memory/output-shaping improvement.** The current best computes `maxlogcnt = int(logcnt.max().item())` and allocates only `[layers, logical_experts, maxlogcnt]`, rather than a larger theoretical replica bound. Generation 1 specifically identified this compact allocation as an improvement over unnecessarily large output mappings. While it did not improve the overall combined score alone, it is compatible with the current best inference result.

## Ineffective Approaches

- **Heap-based CPU packing did not improve the aggregate score despite reducing greedy selection complexity.** Generations 1, 2, 3, and 5 replaced repeated scans with heap selection, but all remained at `combined_score = 0.13`, `balancedness_score_gpu = 0.66`, and `balancedness_score_expert = 0.25`; speed was only 0.00–0.01. The evaluations attribute this to CPU sorting, `.cpu()` movement, `.tolist()` conversion, host-side tensor construction, and Python loops outweighing the theoretical `O(log P)` heap benefit.

- **Local swap refinements increased planning work without measurable balance gains.** Generations 4, 6, 7, 8, and 11 added strict heavy/light swaps, up to two or four swap passes, or exhaustive best-single-item swaps. They still scored GPU balance 0.66, expert balance 0.25, and combined score 0.13. In particular, Generation 7’s nested local-swap search had algorithm time 0.08 and inference time 0.59, while Generation 8’s exhaustive swap approach had inference time 0.46. The added refinement did not change the measured balance outcome.

- **All evaluated variants retained weak expert-level balance.** Every listed correct program, including the current best, has `balancedness_score_expert = 0.25`. Therefore, neither heap packing, swap refinement, nor packing-order adjustments improved the evaluator’s expert-balance metric. The common greedy `weight / replica_count` replication rule is valid but did not yield stronger measured per-expert balancing.

- **CPU-resident metadata processing is consistently associated with weak speed scores.** The current best explicitly executes `weight = weight.float().cpu()`, while `balanced_packing` calls `.cpu()` after sorting and then invokes `.tolist()` for each layer. The summary feedback across Generations 0–8 and 11 repeatedly identifies host transfers and Python heap/list loops as the likely reason speed remains 0.00–0.01.

## Implementation Insights

- **The current best’s mapping construction is largely tensorized after placement decisions are made.** It uses `scatter_` in `inverse`, `gather` for applying permutations, and a flattened indexed `scatter_` to construct `log2phy`. These operations provide compact, correct map construction and likely contribute to its leading `times_inference = 0.28`, even though planning remains CPU-bound.

- **The hierarchy is encoded with permutation transformations rather than per-expert Python remapping.** The sequence `log2mlog` → `mlog2log` → node-local `phy2mlog` → packed `pphy2mlog` → final `pphy2log` cleanly separates logical expert order, node-local order, and physical GPU placement. This is a successful correctness pattern shared with the validated hierarchical implementations.

- **The fast-path for one group per pack avoids Python heap work.** In `balanced_packing`, `groups_per_pack == 1` returns an expanded `arange` and zero ranks directly. This is a useful implementation detail because it bypasses sorting, CPU conversion, heap construction, and per-layer list processing for degenerate packing configurations.

- **The principal implementation bottleneck remains inside `balanced_packing`.** Although output mapping is tensorized, this function performs `weight.float().sort(...).indices.cpu()`, then for each layer creates Python lists with `weight[i].tolist()`, uses `heapq`, iterates sorted group IDs through `indices[i].tolist()`, and reconstructs tensors from Python nested lists. This exactly matches the repeated feedback for Generations 1–8 and 11 and explains why the current best has `times_algorithm = 0.01` and `speed_score = 0.01`.

## Performance Analysis

- **The current best is distinguished mainly by inference time, not by combined score or balance.** It has `times_inference = 0.28`, the best reported inference value, versus 0.39–0.74 among the other variants. However, its `combined_score = 0.13`, GPU balance 0.66, expert balance 0.25, and speed 0.01 remain essentially identical to the broader family of implementations.

- **GPU balancedness is insensitive to the tested packing refinements.** The baseline greedy hierarchical version (Generation 0), heap implementations (Generations 1–3 and 5), and swap-refined versions (Generations 4, 6–8, and 11) all report `balancedness_score_gpu = 0.66`. Thus, node-aware group placement plus subsequent GPU packing establishes a stable moderate GPU balance, while refinements did not produce incremental measured gains.

- **Expert balancedness is the persistent limiting quality metric.** Every program reports `balancedness_score_expert = 0.25`, including variants explicitly targeting improved assignments through incremental replica selection, heavy-partner swaps, and exhaustive local exchange. Since neither placement quality metric changed materially across variants, the combined score stayed fixed at 0.13.

- **Algorithm-speed changes do not correlate cleanly with the inference advantage.** Earlier summaries list algorithm-time values ranging from 0.08 to 0.43, yet most have speed score 0.00 and the same combined score. The current best reports the lowest stated algorithm-time score, 0.01, and a speed score of 0.01, but its main measurable advantage is inference at 0.28. This suggests that avoiding additional refinement passes helps the runtime-facing behavior, whereas CPU-side scheduling overhead prevents a substantial speed-score improvement.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Keep the existing hierarchical placement structure unchanged, and optimize only its implementation.** Preserve the sequence of group-to-node packing, node-local expert replication, and node-local GPU packing, since it is the only repeatedly validated pattern achieving the best GPU balancedness score of 0.66. Future mutations should avoid replacing this hierarchy with global-only placement or post-placement swap heuristics, which have not improved either balance metric.

2. **Replace Python/CPU heap scheduling in `balanced_packing` with a batched tensorized greedy assignment.** Keep the same descending-weight, least-loaded eligible-pack policy, but maintain pack loads and occupancy as tensors and select packs using masked `argmin` for each sorted group position across all layers. This directly targets the dominant bottleneck—`.cpu()`, `.tolist()`, `heapq`, and Python loops—while retaining the validated cardinality-constrained greedy packing semantics.

3. **Remove the unconditional `weight.float().cpu()` conversion and make placement device-preserving.** Let `rebalance_experts` retain `weight` on its original device, ensure `balanced_packing` returns tensors on that device, and use GPU tensor operations for sorting, indexing, and map construction. The current best already has efficient tensorized map construction and the best inference time; eliminating host transfers is the most direct extension likely to improve planning speed without altering placement quality.

4. **Vectorize replica selection in `replicate_experts` in blocks where possible, while preserving the current greedy rule.** The current `argmax(weight / logcnt)` replication rule is consistently correct, so do not replace it with an unvalidated heuristic; instead, reduce repeated allocation and indexing overhead by reusing buffers and considering a small fixed block of sequential replica assignments implemented with batched tensor updates. Benchmark carefully against the current per-replica loop, because replica choices depend on updated `logcnt` after every assignment.

5. **Add a strictly gated fast path for uniform or near-uniform weights and already-balanced replica configurations.** Detect cases where all groups have equal token load per layer, or where `num_physical_experts == num_logical_experts` and no replication is needed, then construct identity/group-contiguous mappings directly without sorting or greedy scheduling. This follows the successful existing `groups_per_pack == 1` fast path and can reduce overhead for common degenerate inputs without risking the current best behavior on skewed workloads.
