# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Hierarchical placement consistently produced the strongest validated balance profile.** The current best program uses group-to-node packing, replica allocation within each node, then physical-replica-to-GPU packing. This pattern matches Generations 0, 1, 4–8, and 10, which consistently reached **GPU balancedness 0.66** and combined score **0.13**. The hierarchy appears effective at distributing aggregate load across GPUs, even though it does not resolve expert-level imbalance.

- **Greedy per-replica-load replication was stable and correctness-preserving.** In the current program, `replicate_experts` repeatedly selects `argmax(weight / logcnt)`, assigning each redundant physical slot to the currently highest-load replica set. This same approach was used in Generations 0, 1, 4–8, and 10; all correct versions retained **expert balancedness 0.25**. It therefore provides a reliable baseline replica-count allocation under the evaluation constraints.

- **Heap-based equal-cardinality LPT packing is a favorable implementation detail relative to repeated linear pack selection.** The current best replaces per-item minimum scans with a heap whose completed packs are removed once full. Generation 1’s heap-based version improved algorithm-time score from Generation 0’s **0.43** to **0.12** and inference from **0.74** to **0.40**, while preserving the same combined score and balancedness. The current code retains this heap pattern and exact cardinality behavior.

- **Limited pairwise swap refinement preserved the best observed quality without breaking mappings.** The current program applies at most two swap passes only when `num_groups <= 64`, retaining swaps that reduce a pair’s load gap. Generation 10 similarly used bounded swap refinement and achieved the same **0.66 GPU / 0.25 expert / 0.13 combined** result, while reporting relatively stronger algorithm and inference time scores (**0.33** and **0.62**). The constrained refinement avoids unbounded optimization work and maintains exact per-pack occupancy.

## Ineffective Approaches

- **Fully CPU-oriented planning remains the central speed limitation.** The current best explicitly executes `weight = weight.float().cpu()` in `rebalance_experts`, and `balanced_packing` again performs CPU conversion, CPU sorting, and Python-list conversion. Its **algorithm-time score 0.01** and **speed score 0.01** show that the heap and bounded refinements do not overcome transfer and interpreter overhead. Generations 4, 5, and 8 show the same pattern: correct results and **0.13 combined**, but algorithm/speed scores near **0.01**.

- **More elaborate Python-side refinement did not improve the final objective.** Generation 7 added heavy/light local swaps and Generation 8 added limited pairwise swap refinement; both still produced **0.66 GPU**, **0.25 expert**, and **0.13 combined**, with speed scores of **0.00–0.01**. The current program’s bounded refinement avoids the worst-case cost, but evaluation evidence does not show an improvement in balancedness over plain greedy packing.

- **Dense vectorized water-filling did not translate into quality or speed gains.** Generation 2 used vectorized PyTorch packing and dense top-k marginal water-filling, but declined to **GPU balancedness 0.62**, **expert balancedness 0.13**, **inference 0.30**, and **combined 0.07**. Dense sorting/top-k work, CPU conversion, and residual loop/overflow handling apparently outweighed the intended vectorization benefit.

- **Integration correctness is non-negotiable even if the planner is plausible.** Generation 3’s CPU hierarchical planner was marked incorrect due to `NoneType` validation failure, receiving **0.00 across every metric**. This result provides no evidence for the quality of its LPT or water-filling heuristics because evaluation failed before scheduling performance could be measured.

## Implementation Insights

- **The current program’s correctness comes from explicit permutation inversion and scatter/gather mapping construction.** `inverse()` uses `scatter_` to invert placement permutations; later, `pphy2phy`, `pphy2mlog`, `pphy2log`, and padded `log2phy` are constructed through gather/scatter operations. This matches the validated mapping strategy in Generations 1, 4–6, 8, and 10 and is a clear successful structural pattern.

- **Exact cardinality is enforced efficiently in the heap packing routine.** In `balanced_packing`, each pack is removed from `available` after reaching `groups_per_pack`. This guarantees the required equal item count without post-hoc repair. The rank is then derived directly from each pack’s member order, allowing the later expression `pack_index * phy_experts_per_gpu + rank_in_pack` to produce valid physical GPU slots.

- **The current best’s swap refinement is deliberately bounded.** It only runs for at most two passes and only when there are at most 64 groups, unlike potentially broader nested local search. This is a safer implementation than Generation 7’s nested swap-oriented refinement and Generation 10’s up-to-four best-swap passes, although the current program still has poor measured algorithm speed because its dominant operations remain CPU/Python based.

- **The implementation has a useful fast path for one item per pack.** When `groups_per_pack == 1`, `balanced_packing` returns direct `arange` indices and zero ranks on the input device, bypassing sorting, heap construction, and CPU list processing. This preserves a low-overhead path for degenerate layouts, while larger layouts take the CPU planner path.

## Performance Analysis

- **The current best is tied on combined score but has the best reported inference-time value among the explicitly summarized correct CPU-heavy variants.** Its metrics are **0.13 combined**, **0.66 GPU balance**, **0.25 expert balance**, **0.01 algorithm-time**, **0.27 inference**, and **0.01 speed**. By comparison, Generation 4 reported inference **0.29**, Generation 5 **0.31**, Generation 6 **0.35**, Generation 1 **0.40**, Generation 7 **0.44**, and Generation 10 **0.62**. Thus, the current implementation’s practical inference metric is comparatively favorable despite identical final combined score.

- **GPU balance is effectively saturated across the successful hierarchical family.** Generations 0, 1, and 4–8 and 10 all converge on **0.66 GPU balancedness**, regardless of whether they use simple greedy selection, heaps, list conversion, vectorized batching, or local swaps. The changes mostly affect runtime behavior, not the GPU-balance score.

- **Expert balancedness is the persistent limiting quality metric.** Most successful hierarchical greedy variants, including the current best, remain at **0.25 expert balancedness**. Generation 2 fell further to **0.13**, showing that its vectorized water-filling approach was worse under this evaluator. No evaluated correct implementation exceeded **0.25**, so replica allocation quality—not merely GPU placement—is the shared ceiling.

- **Timing sub-scores do not map cleanly to the final combined score in this evaluation set.** Generation 10 reported much better algorithm and inference scores (**0.33**, **0.62**) than the current program (**0.01**, **0.27**) but still ended at the same **0.13 combined** and **0.00 speed score**. Conversely, Generation 0 had algorithm **0.43** and inference **0.74**, yet also scored **0.13 combined**. The repeated combined-score plateau indicates that the unchanged balancedness values and low/zero speed score dominate the aggregate outcome.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Keep the three-level hierarchy, but make only the packing routine device-native.** Preserve group→node, within-node replication, and physical-replica→GPU placement exactly as implemented, since this is the repeatedly validated route to `0.66` GPU balancedness and `0.13` combined score. Replace the CPU/list/`heapq` branch in `balanced_packing` with a batched tensor implementation only for common small layouts, retaining the current heap implementation as a fallback for large or irregular cases; this targets the dominant `.cpu()`, `.tolist()`, sorting, and Python-loop overhead without discarding the successful scheduling structure.

2. **Remove the unconditional CPU transfer at the entry point and preserve output-device locality.** Change `weight = weight.float().cpu()` to `weight = weight.float()` and ensure `balanced_packing` returns tensors on `weight.device`, including its nontrivial packing branch. The current planner is correct but pays for at least one guaranteed host transfer and subsequent CPU-side mapping work; avoiding this transfer is the clearest incremental speed experiment while leaving replica allocation, hierarchy, and scatter/gather mapping semantics unchanged.

3. **Use a cheaper deterministic greedy packer as the default, with bounded swap refinement only behind a measured threshold.** The heap LPT packing is a validated baseline, but the pairwise swap phase did not improve the observed `0.66` GPU balance over plain greedy variants and can add substantial Python work for `num_groups <= 64`. Gate refinement more aggressively—for example, only run one pass when the initial max-minus-min pack load exceeds a relative imbalance threshold—and retain a swap only if it improves the global pack-load range, not merely an individual pair’s gap.

4. **Experiment with replica allocation tie-breaking that accounts for physical-slot placement while retaining max `weight / logcnt` as the primary criterion.** Maintain the proven greedy replica-count rule, but when several experts have equal or near-equal marginal replica load, choose the candidate whose group/node currently has lower aggregate assigned load or fewer replicas. This is a low-risk way to attack the persistent `0.25` expert-balancedness ceiling without replacing the validated replication mechanism with the previously weaker dense water-filling approach.

5. **Add specialized fast paths for structurally simple layouts before invoking hierarchical packing.** In addition to the existing `groups_per_pack == 1` fast path, directly bypass Python packing when there is one node, one GPU per node, no redundant experts, or exactly one physical expert per GPU partition, constructing the identity/permutation mappings with tensor `arange`, `view`, `gather`, and `scatter_`. These cases do not need LPT or swaps, and exploiting them preserves the current program’s explicit validated mapping construction while reducing planner overhead on common degenerate configurations.
