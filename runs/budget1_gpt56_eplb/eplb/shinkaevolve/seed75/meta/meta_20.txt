# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **The current best preserves the strongest validated quality profile through hierarchical placement.** It first packs logical expert groups to nodes, performs replication within each node, and then packs physical replicas across GPUs. This repeatedly yields **GPU balancedness 0.66** and **expert balancedness 0.25**, matching the successful hierarchical family in Generations 9, 11, 12, 14, 15, 17, 18, and 20. No newly evaluated correct variant exceeded this balance profile.

- **Exact-cardinality LPT packing remains a reliable correctness-preserving primitive.** In the current program, `balanced_packing` sorts groups by descending weight, assigns each to the least-loaded available pack via `heapq`, and permanently removes packs after `groups_per_pack` assignments. Generation 16 and Generation 18 used related heap-based LPT packing and retained the same **0.66 GPU / 0.25 expert / 0.13 combined** outcome. The technique reliably satisfies fixed GPU/node occupancy constraints while preserving moderate GPU balance.

- **Greedy marginal replication is the stable baseline for expert replication.** The current `replicate_experts` repeatedly assigns a redundant slot to the expert maximizing `weight / logcnt`. Generations 9, 11, 12, 14, 15, 17, 18, and 20 used the same basic policy and all reached **0.25 expert balancedness**, rather than the weaker **0.13** seen in Generation 13’s discrete marginal water-filling/top-k implementation.

- **The current best’s constrained swap policy is safer than broad refinement.** Its heavy/light exchange is limited to layouts with at most 64 groups and only two passes. This preserves the validated **0.66 GPU balancedness** without introducing the more substantial refinement costs reported for Generation 14’s quadratic searches, Generation 15’s item-pair tensors, or Generation 13’s repeated exchange rounds. Among the newly listed CPU-heavy variants, the current program’s **0.27 inference metric** is better than Generations 9 (**0.33**), 11 (**0.37**), 12 (**0.29**), 13 (**0.35**), 14 (**0.30**), 15 (**0.31**), 16 (**0.42**), 17 (not separately improved beyond the plateau), and 18 (**0.41**).

## Ineffective Approaches

- **More elaborate local-search refinement did not improve the combined objective.** Generation 11 added four vectorized high/low-pack swap refinements, Generation 12 used up to four tensorized swap rounds, and Generation 14 used bounded pairwise swaps. Despite the extra work, all remained at **0.66 GPU balance, 0.25 expert balance, 0.13 combined**, with low speed scores of **0.01** or **0.00**. The evidence indicates that swap refinement may preserve placement quality but does not break the balance plateau.

- **Dense marginal water-filling/top-k worsened expert balance and total score.** Generation 13’s dense `topk` marginal allocation plus iterative fallback dropped expert balancedness to **0.13**, GPU balancedness to **0.65**, and combined score to **0.07**, versus the current program’s **0.25**, **0.66**, and **0.13**. Repeated sorting/top-k temporaries did not yield better allocation quality and added runtime overhead.

- **Device-side mapping construction alone does not eliminate planning cost.** Generation 15 built mappings with device-side tensor operations, but still had **algorithm time 0.02**, **inference 0.31**, **speed score 0.01**, and **combined 0.13**. Its Python loops for LPT and replica selection, plus quadratic refinement tensors, remained dominant. This aligns with the current implementation: efficient scatter/gather mapping construction is necessary for correctness but is not the primary timing bottleneck.

- **Removing costly refinement does not materially improve the score when CPU/Python planning remains.** Generation 18 explicitly removed costly packing refinement, yet reported **algorithm time 0.11**, **inference 0.41**, and **speed score 0.00**, while keeping the same **0.13 combined** score. This shows that refinement is not the only, or necessarily largest, source of overhead; CPU sorting, heap operations, and per-layer Python scheduling are sufficient to keep runtime metrics poor.

## Implementation Insights

- **The current program’s mapping construction is a key validated structural strength.** It computes inverse permutations with `scatter_`, transforms group-level placements through `log2mlog` and `mlog2log`, and builds padded `log2phy` using a single flattened scatter index, `phy2log * maxlogcnt + phyrank`. This is consistent with the correctness-preserving forward/inverse mapping strategy noted in Generations 11, 15, 17, and 20.

- **The heap implementation enforces cardinality during assignment rather than repairing it afterward.** `available` contains only non-full packs; once a pack receives `groups_per_pack` members, it is not pushed back onto the heap. This ensures every pack has exactly the required size and makes `rank_in_pack` directly usable to form GPU-local physical indices:
  `phy2pphy = pack_index * phy_experts_per_gpu + rank_in_pack`.
  This exact occupancy behavior is one reason the current program remains validation-correct.

- **The program has an effective degenerate-layout fast path.** When `groups_per_pack == 1`, `balanced_packing` returns `arange` pack indices and zero ranks directly, bypassing CPU sorting, heap management, Python lists, and swaps. Generation 20 similarly emphasized degenerate-layout fast paths and retained correct behavior, although its broader CPU planning still limited it to **0.13 combined** and **0.01 speed**.

- **The dominant cost remains explicit host-side planning.** The current entry point immediately executes `weight = weight.float().cpu()`, and nontrivial `balanced_packing` then performs CPU sorting, `.tolist()` conversion for indices and weights, Python heap operations, nested member lists, and optional nested swap loops. This implementation detail is consistent with the current **times_algorithm 0.01** and **speed_score 0.01**, and with the same poor speed pattern in Generations 9, 12, 14, 16, 17, and 18.

## Performance Analysis

- **The current best is tied on combined score and balance but has the strongest newly reported inference value among the directly comparable later variants.** It records **0.13 combined**, **0.66 GPU balancedness**, **0.25 expert balancedness**, **0.01 algorithm**, **0.27 inference**, and **0.01 speed**. Generations 9, 11, 12, 14, 15, 16, 17, 18, and 20 all retained the same **0.13 combined** ceiling, while their reported inference metrics ranged from **0.29** to **0.42** where supplied. Thus, the current bounded-refinement heap variant is comparatively favorable on inference despite unchanged aggregate score.

- **GPU balancing is saturated across the successful hierarchy-aware implementations.** Heap packing (Generations 16 and 18), vectorized swap packing (Generations 11 and 12), device-local mapping approaches (Generations 15 and 20), and the current best all converge at **0.66 GPU balancedness**. The evaluator does not show a GPU-balance gain from more complex swapping, top-k allocation, or mapping-device changes.

- **Expert balancedness is the persistent quality bottleneck.** The dominant greedy replication family, including the current program, stabilizes at **0.25 expert balancedness**. Generation 13 demonstrates that changing replication to dense discrete marginal water-filling can be worse, reaching only **0.13**. Since no correct evaluated implementation exceeded **0.25**, the combined-score plateau is more strongly associated with replica-allocation quality than with GPU pack refinement.

- **Runtime-oriented implementation changes have not translated into higher combined scores.** Generation 11 modestly improved its algorithm metric to **0.04**, while Generation 16 and 18 were substantially worse at **0.15** and **0.11** respectively; nevertheless, all scored **0.13 combined**. Earlier global results also showed that even variants with substantially higher timing submetrics could remain at the same combined score. Across the evidence, balance metrics and the near-zero speed score dominate the final outcome, while CPU/Python planning prevents meaningful speed-score separation among the correct hierarchical designs.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Preserve the hierarchy and greedy replica policy, but eliminate the unconditional host transfer.** Change `weight = weight.float().cpu()` to keep `weight` on its original device, and make `balanced_packing` return device-resident indices in every branch. The group→node packing, per-node replication using `weight / logcnt`, and GPU packing sequence should remain unchanged because it is the only repeatedly validated family reaching `0.66` GPU and `0.25` expert balancedness.

2. **Split `balanced_packing` into layout-specialized fast paths before using Python LPT.** Keep the existing `groups_per_pack == 1` path, then add tensor-only paths for small fixed common cases such as `groups_per_pack == 2` and/or small `num_packs`, using descending sort plus paired or blocked assignment and `scatter_` to construct `pack_index` and ranks. Retain the exact-cardinality heap LPT implementation as a correctness fallback for irregular shapes, since its permanent removal of full packs is a proven occupancy-preserving mechanism.

3. **Disable or sharply gate pairwise swap refinement based on measured initial imbalance.** Run at most one swap pass only when the LPT result has a meaningful relative load range, such as `(max_pack_load - min_pack_load) / max_pack_load > threshold`; otherwise immediately materialize the mapping. Existing evidence shows broad refinement does not exceed the `0.66` GPU-balance plateau, while the current best’s limited swaps are safer than prior quadratic approaches, so this mutation should target planning latency without changing baseline placement behavior.

4. **Add deterministic replica-allocation tie-breaking using node-local and GPU-pack-aware load state.** Continue selecting the maximum `weight / logcnt` expert as the primary rule, but for ties or near-ties select the candidate belonging to the least-loaded local group/node, using a stable lexicographic criterion such as `(marginal_load, -local_load, -global_expert_id)` with tolerance-aware ties. This retains the successful greedy marginal replication policy that reaches `0.25` expert balancedness, while exploring a low-risk way to improve the persistent expert-balance bottleneck without adopting the unsuccessful dense top-k water-filling design.

5. **Fuse mapping construction and avoid unnecessary inverse-permutation materialization where possible.** In the hierarchical path, directly scatter physical positions into the final padded `log2phy` representation from `phy2log` and `phyrank`, and investigate composing `phy2pphy`, `phy2mlog`, and group offsets through gathers rather than storing every intermediate inverse permutation. The current flattened-scatter mapping scheme is validated for correctness, so the mutation should preserve its exact indexing semantics while reducing temporary tensor allocation, reshaping, and memory traffic during per-layer planning.
