# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Global batched water-filling plus global LPT is the strongest evaluated design.** The current best, **Batched Water-Filling LPT Expert Balancer** (Generation 1), achieved the top combined score of **0.14**, GPU balancedness **0.76**, expert balancedness **0.27**, algorithm time **0.02**, and inference time **0.33**. It allocates all extra replicas by taking top-k marginal reductions in a tensor operation, then globally schedules all physical replicas over GPU slots. This clearly outperformed the hierarchical variants, which consistently reached only GPU balance **0.66** and expert balance **0.25**.

- **Vectorizing replica allocation is materially better than iterative “replicate hottest expert” loops.** In the current program, `_allocate_replica_counts` constructs candidate marginal loads `weight / (k + 1)`, flattens expert/extra-copy candidates, and selects the best `num_extra` with batched `topk`. This removes the per-extra-replica decision loop present in the hierarchical designs. The resulting expert balance of **0.27** is the best observed, versus **0.25** for Generations 0, 2–4, and 6–9, and **0.23** for Generation 5.

- **Ignoring node/group hierarchy improved placement quality under this benchmark.** The current best explicitly discards `num_groups` and `num_nodes` and globally optimizes across all GPU slots. Its **0.76 GPU balancedness** is substantially above the **0.66** repeatedly achieved by hierarchical capped-LPT approaches such as Generation 2 (*Hierarchical Expert Replica Load Balancer*), Generation 4 (*Hierarchical Expert Replica Rebalancer*), and Generation 9 (*Hierarchical Capped-LPT Expert Rebalancing*).

- **Scatter-based construction of inverse placement metadata is a successful correctness-preserving pattern.** The current best materializes `physical_to_logical`, `physical_rank`, and `logical_to_physical` through `scatter_` rather than Python-side map construction. This aligns with the fully validated vectorized hierarchical implementations, while retaining the better global balance scores of the non-hierarchical strategy.

## Ineffective Approaches

- **Hierarchical group-to-node packing consistently reduced both GPU and expert balance.** Generations 0, 2, 3, 4, 6, 7, 8, and 9 all use group/node hierarchy or a global fallback and clustered at combined **0.13**, GPU balance **0.66**, and expert balance **0.25**. Relative to the current best’s **0.76/0.27**, enforcing intermediate node-level placement appears to constrain the final GPU scheduler enough to hurt load distribution.

- **Swap-refinement did not improve the benchmark result.** Generation 5 added up to four best-improving cross-pack swaps but fell to GPU balance **0.54**, expert balance **0.23**, combined **0.12**, and algorithm time **0.03**. Generation 7 and Generation 8 used bounded heavy/light or max-load-reducing swap refinements but only returned to the common **0.13** combined score. The feedback specifically identifies repeated pairwise swap evaluation and quadratic candidate tensors as costly.

- **Tensorization alone did not solve scheduling cost when the core algorithm remained sequential.** Generations 2–4 and 6–9 described batched PyTorch operations, but their algorithm and speed scores were almost uniformly **0.01**. Their remaining per-group, per-item, per-pack, or per-physical-replica loops dominated runtime despite tensorized bookkeeping.

- **CPU planning is a common unresolved bottleneck rather than a differentiator.** Every major approach, including the best one, converts routing weights to CPU float32. The current program still has a speed score of only **0.01**, while hierarchical CPU planners also received **0.01**. Thus, CPU planning does not explain the quality gain of the current best; the gain comes from global placement and batched allocation, while CPU-side execution keeps overall speed poor.

## Implementation Insights

- **The current best’s replica-count allocation exactly captures discrete greedy water-filling in bulk.** `_allocate_replica_counts` evaluates each potential additional copy’s resulting load and uses a single per-layer `torch.topk`. Because candidate copy loads decrease monotonically for each expert, selecting the largest marginal values produces the same allocation objective as repeatedly selecting the highest load-per-copy expert, but without one Python iteration per added replica.

- **The current program separates allocation, replica materialization, and physical placement cleanly.** `_make_replicas` produces valid logical-expert IDs, replica ranks, and equalized loads with masked candidate entries and `argsort`; `_lpt_pack_to_gpus` then schedules those physical copies. This decomposition supports the best measured placement quality: **0.76 GPU** and **0.27 expert** balancedness.

- **Global LPT is effective for quality even though its slot loop remains expensive.** `_lpt_pack_to_gpus` sorts replicas by load, then for each replica selects the least-loaded non-full GPU using `masked_fill(..., inf)` and `argmin`. Scheduling all layers simultaneously is better than layer-by-layer Python scheduling, consistent with the current best’s algorithm score of **0.02**, which is above the **0.01** seen in most hierarchical vectorized variants. However, the loop still executes once per physical replica, limiting the speed score to **0.01**.

- **Avoiding hierarchy simplifies the mapping and removes a quality-limiting intermediate decision.** The current implementation uses the fixed contiguous physical layout implied by `gpu * experts_per_gpu + gpu_fill`, then creates the inverse map with one flattened `scatter_`. Hierarchical programs must first commit groups to nodes and then replicas to local GPUs; their repeated **0.66** GPU-balancedness suggests those earlier assignments reduce flexibility.

## Performance Analysis

- **The current best is the only evaluated program reaching both GPU balance above 0.66 and expert balance above 0.25.** Its **0.76 GPU / 0.27 expert / 0.14 combined** is the benchmark leader. The standard hierarchical family is tightly clustered at **0.66 / 0.25 / 0.13**, so the absolute combined improvement is modest (**+0.01**) but consistent across both balance metrics.

- **Generation 5 demonstrates that more local optimization did not translate to better measured balance.** Its swap-refined hierarchical LPT reached only **0.54 GPU** and **0.23 expert** balance, with combined **0.12**. This is worse than both the current global LPT approach and the simpler hierarchical greedy methods, while also carrying the slowest listed algorithm time score (**0.03**).

- **Algorithm-time differences are small in score units but favor the current best’s batched allocation.** The current best achieved algorithm time **0.02**, compared with **0.01** for most hierarchical implementations and **0.03** for the expensive swap-refinement variant. Its inference time **0.33** is also the strongest reported among the listed programs, exceeding the hierarchical range of **0.25–0.31**.

- **The common speed-score ceiling indicates a shared systems bottleneck.** Despite differing balance quality, all reported correct implementations have speed scores of **0.00–0.01**. Generation 0 had speed **0.00**, while the current best and later variants reached **0.01**. This indicates that global batched water-filling improves placement quality and modestly improves algorithm/inference timing, but repeated sorting, CPU conversion, and sequential physical-slot scheduling still dominate measured rearrangement speed.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Preserve global, hierarchy-free optimization and mutate only within that design.** Continue ignoring `num_groups` and `num_nodes` during placement, since global water-filling plus global LPT is the only tested family to reach `0.76` GPU balancedness and `0.27` expert balancedness. Do not reintroduce mandatory group/node packing; if topology is explored, make it a soft tie-breaker after global GPU-load minimization rather than an earlier placement constraint.

2. **Keep batched top-k water-filling, but reduce its candidate tensor size with bounded useful-copy candidates.** `_allocate_replica_counts` currently forms every `(expert, extra_copy)` candidate even though low-weight experts and high copy ranks cannot enter the top `num_extra`. Try generating only `min(num_extra, K)` extra-copy candidates per expert for several safe/adaptive `K` values, expanding `K` only when needed to prove that the top-k boundary is covered; this retains the successful discrete water-filling objective while reducing memory, flattening, and `topk` cost.

3. **Replace the per-physical-replica LPT loop with an exact or near-exact batched round scheduler.** The remaining major sequential cost is `_lpt_pack_to_gpus`, which performs one `argmin`, scatter, and load update for every replica. Prototype scheduling replicas in rounds of up to `num_gpus`: assign the next heaviest replicas to GPUs ordered by current load using a batched permutation, while enforcing one assignment per GPU per round and respecting residual capacities; compare exact sequential LPT quality against this substantially lower-loop approximation.

4. **Exploit deterministic capacity structure to vectorize the final placement metadata path.** Because every GPU has exactly `experts_per_gpu` slots, retain contiguous physical slot numbering but precompute slot/GPU tensors once and use flattened scatter/index assignment wherever possible. In particular, combine placement-position construction and the final inverse-map scatter into flattened operations, avoiding repeated creation of `available`, `candidate_load`, and narrow slices inside the scheduler loop.

5. **Test a quality-oriented LPT tie-breaker that favors spreading replicas of the same logical expert without using hierarchy.** When multiple GPUs have equal or nearly equal current load, choose the GPU with the fewest existing replicas of that logical expert, then fall back to GPU index. This builds on the current global scheduler and may improve expert balancedness beyond `0.27` while leaving the primary least-loaded-GPU rule intact; implement the replica-presence/count state as a compact per-layer tensor rather than Python maps.
