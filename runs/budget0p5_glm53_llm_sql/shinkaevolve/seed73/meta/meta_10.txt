# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns
- **Multi-candidate generation + exact Trie-LCP scoring** is the dominant winning pattern. Gen 2 (0.58), Gen 4 (0.70), Gen 7 (0.35), and Gen 8 (0.71, current best) all use 3 candidates (global frequency/length-weighted, conditional partition tree, classic stats/original order) scored exactly by sum of adjacent LCPs over sorted serialized rows. Gen 8 is the top performer (hit rates 0.44–0.84, 100% success, 5.01s).
- **Conditional partition tree on factorized integer codes** (Gen 8's Candidate B, depth caps 5–12 scaled by column count and row count) captures per-row orderings that fixed global orders miss — key to its 0.83–0.84 hit rates on repetitive datasets.
- **Length-weighted pair-repetition scoring** (`len(value)² × count(count-1)` via `np.bincount` on factorize codes, as in Gen 8's `_make_pair_scorer`) as the ordering heuristic — fast and aligned with prefix-cache reuse.
- **Serializing cells exactly as the scorer does** (NaN→"", str(v)) before scoring, as in Gen 7 and Gen 8, keeps the internal objective faithful to the evaluator.

## Ineffective Approaches
- **Correctness crashes kill scores instantly** (0.00): Gen 0 (int64 dtype assignment TypeError), Gen 1 (renamed `__col_{k}` columns breaking schema contract), Gen 5 (unhashable list in factorize/dict keys), Gen 6 (`np.char.str_len` on object array — fixed by `.astype(str)`), Gen 9 (swapped `pd.factorize` tuple unpacking causing int() on strings). Type-safety on object/list/dtype handling is the single largest failure mode.
- **Per-row Python loops are slow without score gains**: Gen 2's per-row loops produced 18.66s runtime at only 0.58, versus Gen 8's vectorized scoring at 5.01s with 0.71.
- **Over-engineered machinery with dead code**: Gen 7 (0.35) had a representative-length loop contributing zero, weakening the partition-tree candidate and dropping hit rates to 0.057 on worst datasets.
- **Over-pruning candidates hurts**: Gen 3 dropped to 0.09 (hit rates 0.004–0.146) despite 1.86s runtime, showing the Trie objective itself aligns imperfectly with the evaluator — candidate diversity matters more than scoring precision alone.

## Implementation Insights
- **Gen 8's defensive serialization** (`_to_str` with NaN checks via `v != v` and `pd.isna` fallbacks) plus object-dtype output materialization (`np.empty(dtype=object)`, values copied verbatim) avoids every dtype crash that killed Gens 0/5/6/9.
- **Factorize codes as the partition key** (Gen 8): `pd.factorize` returns (codes, uniques); using codes for grouping/partitioning and uniques only for length stats avoids Gen 9's unpacking bug.
- **Safe col_merge handling** (Gen 8): keep merged groups contiguous in the initial order, attempt the base-class `merging_columns` API inside try/except — graceful degradation preserved 100% run success.
- **Deterministic row sort by serialized string** after selecting column order yields cache-friendly output without extra cost.

## Performance Analysis
- Score trajectory across generations: 0.00 → 0.00 → 0.58 → 0.09 → 0.70 → 0.00 → 0.00 → 0.35 → 0.71 (Gen 8, best). All ≥0.35 scorers are correct Trie-LCP multi-candidate implementations; all 0.00 scorers are runtime crashes, not algorithmic failures.
- Gen 8 beats Gen 4 (0.70) marginally and Gen 2 (0.58) substantially, mainly by fixing runtime (5.01s vs 18.66s) and adding per-row conditional orders.
- Consistent bottleneck: the same 0.44/0.45 hit-rate "hard dataset" appears in Gen 4 (0.44), Gen 8 (0.444), and Gen 2 (0.09) — fixed heuristic candidate pools fail on sparse/low-redundancy data; wider or locally-searched orderings are the headroom.
- Best-to-worst dataset spread for Gen 8 is 0.44→0.84, mirroring Gen 7's 0.057→0.826, confirming the approach generalizes well to structured/repetitive data but poorly to low-redundancy data.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add a 4th candidate: "unique-first for low-redundancy data" to attack the 0.44 hard-dataset floor.** The persistent 0.44–0.45 hit rate on the hard dataset (seen in Gens 4 and 8) indicates that all three current candidates are biased toward repetition-heavy orderings. Generate a candidate ordering that sorts columns by descending unique-count ratio (nunique/n) first — placing highly distinguishing columns early tends to help when few values repeat — and score it with the same exact Trie-LCP evaluation so the scorer picks it only when it wins.

2. **Introduce a greedy local-search refinement (column-swap hill climbing) on the winning candidate.** After selecting the best of A/B/C, run a bounded pass (e.g., ≤ 30 adjacent-column swaps or full pair swaps for ≤ 20 columns) that keeps a swap only if the exact LCP score improves, with an early time budget check (≤ 1s). Gen 3 showed the Trie objective aligns imperfectly with the evaluator, so hill climbing from multiple diverse starting points retains diversity while improving the internal score where the gap is large.

3. **Vectorize `_score_candidate` to cut runtime and enable more candidates.** Replace the per-row Python `"".join` loop with `np.add.reduce` / `np.char.add` on a sorted matrix of serialized columns, or compute LCP totals via sorting codes once per column pair. Gen 8's win over Gen 2 came precisely from vectorization (5.01s vs 18.66s); halving scoring cost again would allow evaluating 5–6 candidates per dataset at the same wall time, directly increasing hit rates on the hard dataset where candidate diversity is the bottleneck.

4. **Deepen the conditional partition tree adaptively using score gain rather than fixed depth caps.** Gen 8 caps depth at 5–12; instead, continue recursing while `pair_score(best, rows) / total_rows` exceeds a threshold (e.g., top-quartile of column scores) and the partition reduces rows by ≥ 2×. This lets repetitive datasets get deeper, more row-specific orderings (where 0.83–0.84 hit rates suggest headroom remains) while cutting wasted recursion on sparse data, improving both quality and runtime.

5. **Add mutation-aware candidate generation using `one_way_dep` and `distinct_value_threshold`.** The current program ignores these inputs entirely. When `distinct_value_threshold` is low, weight the pair-scorer toward low-cardinality columns (functional-dependency ordering: put determiner columns before determined ones); use `one_way_dep` pairs (a→b) to force `a` before `b` in Candidate A's tie-breaking. These are free structural hints about the evaluator's data that none of Gens 0–9 exploited, and they slot cleanly into Gen 8's existing candidate-generation framework without new machinery.
