# Updated Global Insights

## Successful Algorithmic Patterns
- **The 3-candidate + exact Trie-LCP scoring recipe remains the proven ceiling-breaker**, now confirmed across Gens 8–22. The current best (Gen 20/22 line, 0.72, 3.48–3.73s) and Gen 22's "Multi-Candidate Column Ordering" (0.72, **2.05s** — the fastest yet) both use: original/global-frequency (or pair-score) order, conditional partition-tree order, and a length-weighted order, each scored exactly by sum of adjacent LCPs over sorted serialized rows.
- **Cheap candidate enumeration is now decisive on runtime**: Gen 22 achieves the same 0.72 at 2.05s (vs current best's 3.73s) by serializing all cell values once and reusing across candidates — beating Gen 12's 11.66s at identical quality. Quality is saturated at 0.72; runtime is the remaining optimization axis.
- **Conditional partition tree with `distinct_value_threshold` filtering** consistently delivers the 0.83–0.84 peak hit rates (current best: 0.8424, 0.8257 on two cases) via per-row adaptive ordering on repetitive datasets.
- **Duplicate-pair scoring `len(v) × count × (count−1)`** remains the effective primary ranking heuristic (current best's candidate 1; also drives the tree's split-column gain function).

## Ineffective Approaches
- **Stale/dead lines and never-executed code paths are the dominant crash mode**: Gen 21 scored 0.00 solely because `build_tree` retained a leftover line `rest_ids = [u for u in unit_ids if u != best]` referencing undefined `best` (the next line used `best_u`). Deleting one dead line restores a structurally sound pipeline — a recurring failure class alongside Gens 11, 15, 19.
- **The candidate pool cannot crack the 0.44-dataset**: current best hits 0.4444 on the fifth case while reaching 0.62–0.84 elsewhere; neither more candidates (Gen 14's 4), deeper trees, per-row orders, nor Gen 22's variants change it — a structural limit of global/trie heuristics on low-redundancy data.
- **Over-engineered candidate machinery doesn't pay**: Gens 12/13 spent 11–13s for ≤0.72; lean 3-candidate implementations match quality at 2–4s.

## Implementation Insights
- **Serialize once, reuse everywhere** is the key runtime lever: the current best's `ser_cols` dict feeds candidates, tree codes (integer factorization via sorted-value mapping), LCP scoring, and `rows_for` string assembly simultaneously. Gen 22 pushed the same pattern to 2.05s.
- **Object-dtype per-row assembly with explicit mapping** (`raw = work.to_numpy(dtype=object)`, `col_pos` dict, `row[col_pos[c]]` per permutation, `assert out_df.shape == (n, ncols)`) eliminates the shape/dtype crash classes that killed Gens 0/5/6/9/19.
- **Graceful col_merge degradation** (try/except around `calculate_col_stats`/`merging_columns` falling back to raw df) preserves the 100% run-success rate.
- **Stale-line hygiene in patched code**: Gen 21 shows that rename refactorings (best→best_u) leave dangerous dead references; the fatal line never affects logic but crashes at import/execution.

- **Trajectory Gens 10–22**: 0.72 → 0.00 → 0.72 → 0.70 → 0.72 → 0.00 → 0.72 → 0.72 → 0.71 → 0.00 → 0.72 (Gen 20) → 0.00 (Gen 21) → 0.72 (Gen 22). # META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add a 4th candidate: unique-first ordering to attack the 0.44 hard dataset.** All three current candidates (pair-score, partition tree, length-weighted) favor repetition-heavy columns, and the persistent 0.4444 case likely has low redundancy where distinguishing columns should come first. Build a candidate sorted by descending `len(code_str[c])/n` (nunique ratio, free from existing `code_str`), score it with the same `_trie_score`, and let the max pick it only when it wins — the cheapest diversity increase at the settled 0.70–0.72 plateau.

2. **Vectorize `rows_for` with a prebuilt object matrix to double the candidate budget.** Replace the per-row `"".join` loop with `np.char.add`-style array concatenation over an object matrix `raw_sorted[i][j] = ser_cols[order[i]][j]` assembled once per candidate. Gen 10's runtime edge (3.73s vs Gen 12's 11.66s) came exactly from serialization reuse; halving scoring cost again allows 5–6 candidates at the same wall time, which is the most direct lever on the hard dataset given Gen 22 proved 2.05s headroom exists at equal quality.

3. **Add bounded adjacent-swap hill climbing on the winning global order.** After candidate selection, run ≤30 adjacent column swaps on `order1`/`order3`, keeping each swap only if the exact `_trie_score` strictly improves, under a ~1s budget. This exploits the known imperfect alignment between heuristics and the Trie objective while keeping the diversified multi-candidate pool and 100% run success intact.

4. **Exploit `one_way_dep` as tie-breaking constraints.** The program currently ignores these inputs entirely. When building `order1`, enforce via stable insertion that determiner column `a` precedes dependent `b` for each `(a, b)` pair (do not re-sort, which would break pair-score ranking), and in `_tree_orders`, prefer splitting on determiner columns before their dependents. These are free structural hints about evaluator data requiring no new machinery.

5. **Add a guarded duplicate-row-chain candidate with fallback.** Compute full-row duplicate density via one Counter pass over joined strings from existing `ser_cols`, then greedily chain columns by pairwise value-overlap `sum((cnt_a[v] == cnt_b[v]) for v)` so columns with the most duplicate co-occurrence are adjacent — a direct fit to the sorted-row LCP objective. Wrap the whole construction in try/except falling back to `order1` (Gen 8/10's graceful-degradation pattern), and keep the `col_pos` per-row assembly plus the strict shape assert untouched to avoid the crash classes that killed Gens 11/15/19/21 — especially stale-line hygiene after any renaming.
