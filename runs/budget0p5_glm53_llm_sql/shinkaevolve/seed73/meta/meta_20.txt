# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns
- **Multi-candidate ordering + exact Trie-LCP scoring remains the dominant pattern**, now confirmed across Gen 8 (0.71), Gen 10/current best (0.72, 3.73s), Gens 12–14, 16–18 (all 0.70–0.72). The current best uses exactly 3 candidates (pair-score global, conditional partition tree, length-weighted) scored by sum of adjacent LCPs of sorted serialized rows — same quality ceiling as 4 candidates (Gen 14, 0.72 at 1.95s).
- **Cheap candidate enumeration is the differentiator**: Gen 10 wins on runtime (3.73s) vs Gen 12 (11.66s, same 0.72) and Gen 13 (12.87s, 0.70) because it serializes each column once and reuses the serializations across all candidates, avoiding repeated string slicing/binary search LCP costs that forced Gen 12's conservative >8M-char fallbacks.
- **Conditional partition tree (depth ≤12, ≤8 split columns, skipping near-unique columns via `distinct_value_threshold`)** delivers the per-row adaptive orderings that fixed global orders miss, driving 0.83–0.84 hit rates on repetitive datasets (Gen 10, 16, 18).
- **Duplicate-pair scoring `len(v) × count × (count−1)`** as the primary ranking heuristic is consistently effective (Gen 10, Gen 17, Gen 18), fast via `Counter`, and aligned with prefix reuse.

## Ineffective Approaches
- **Never-run-end-to-end code and identity-based unit removal are the top crash modes**: Gen 11 (0.00, undefined `order_b`), Gen 15 (0.00, pandas `.loc` integer bounds after insert/drop in col_merge path, masked by try/except), Gen 19 (0.00, `u is not prefix_unit` identity removal dropped a column causing (23,) vs (22,) broadcast error). All 0.00 scores are correctness crashes, not algorithmic failures.
- **Defensive try/except masking bugs**: Gen 15's extensive exception handling hid the true failure point; Gen 19's recursion removed merged units by identity after list copies. Permutation assembly must guarantee every column appears exactly once per row.
- **Per-row variable ordering risks shape/schema violations** (Gen 11, 19 feedback) — must return per-row permutations with consistent total length; the current best handles this correctly with `col_pos` mapping and an explicit shape assert.
- **Bigger/over-engineered candidate machinery doesn't pay**: Gens 12/13 with more elaborate scoring cost 3–4× runtime (11.66s, 12.87s) for equal or lower scores than Gen 10's lean 3-candidate approach.

## Implementation Insights
- **Serialize once, reuse everywhere**: Gen 10's `ser_cols` dict (fillna("")→astype(str)→tolist) feeds candidates, scoring, and per-row joins simultaneously — the key runtime edge (3.73s) over Gens 12/13 (11–13s) at equal 0.72/0.70 quality.
- **Integer factorization for the tree**: Gen 10 maps serialized values to sorted-int codes for grouping (`codes[c]`), avoiding string hashing in partitioning — consistent with Gen 8's lesson about factorize codes vs uniques (Gen 9's fatal tuple-unpack bug).
- **Object-dtype output with explicit column-position mapping**: `raw = work.to_numpy(dtype=object)`, `np.empty(dtype=object)`, per-row `row[col_pos[c]]` assembly, plus `assert out_df.shape == (n, ncols)` — eliminates the dtype/crash classes that killed Gens 0/5/6/9 and the shape-mismatch class that killed Gen 19.
- **Graceful col_merge degradation**: wrap the base-class `calculate_col_stats`/`merging_columns` calls in try/except falling back to the raw df — preserved 100% run success (also Gen 8's pattern).

## Performance Analysis
- **Trajectory (Gens 10–19)**: 0.72 → 0.00 → 0.72 → 0.70 → 0.72 → 0.00 → 0.72 → 0.72 → 0.71 → 0.00. Every correct implementation lands at 0.70–0.72 — a hard plateau; all 0.00s are crashes (Gen 11 undefined var, Gen 15 pandas indexing, Gen 19 shape mismatch).
- **The persistent 0.44-dataset bottleneck**: the same dataset scores ~0.444 in Gens 10, 12, 13, 14, 16, 17, 18 while others reach 0.79–0.84. Neither more candidates (Gen 14's 4), deeper trees (Gen 10's depth 12), nor per-row orders crack it — indicating structural limits of the current heuristic candidate pool on low-redundancy data.
- **Runtime vs score tradeoff is settled**: at equal 0.72, Gen 10 (3.73s) and Gen 14 (1.95s, single global order) beat Gen 12 (11.66s); the extra partition-tree candidate mainly buys the 0.83–0.84 peak datasets, so candidate cost should stay cheap (Gen 17's budget-bounded single-order at 1.74s also hit 0.72).
- **Current best (Gen 10, 0.72, 3.73s)** combines Gen 8's algorithmic recipe with leaner serialization reuse, matching the quality ceiling of all peers while keeping runtime among the fastest correct full-candidate implementations.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add a 4th candidate: "unique-first" ordering to attack the 0.44 hard dataset.** All three current candidates (pair-score, partition tree, length-weighted) are biased toward repetition-heavy columns; the persistent 0.44 dataset likely has low redundancy where distinguishing columns first helps. Add a candidate sorted by descending `nunique/n` ratio (computed from the already-built `codes[c]` lengths — free, no new serialization), score it with the same `_trie_score`, and let the scorer pick it only when it wins. This is the cheapest possible diversity increase given the settled quality plateau of 0.70–0.72.

2. **Vectorize `rows_for` and `_trie_score` to double candidate budget.** Replace the per-row Python `"".join` loop with a numpy object-matrix assembled once (`raw_sorted = [[ser_cols[c][i] for c in order] for ...]`) and use `np.char.add` / array-based concatenation, keeping the exact LCP-by-sort evaluation. Gen 10's runtime edge (3.73s vs Gen 12's 11.66s) came exactly from serialization reuse; halving scoring cost again allows 5–6 candidates at the same wall time, which is the most direct lever on the hard dataset.

3. **Refine the winning candidate with bounded adjacent-swap hill climbing.** After the 3-candidate (or 4-candidate) selection, run ≤30 adjacent column swaps on the winning global order (or per-row for small trees), keeping a swap only if the exact `_trie_score` improves, under a ~1s time budget. This exploits the observed imperfect alignment between heuristics and the Trie objective while keeping the diversified multi-candidate pool intact.

4. **Exploit `one_way_dep` as tie-breaking constraints in candidate A and the tree.** The current program ignores these inputs entirely. When generating `order1`, enforce that determiner column `a` precedes determined column `b` for each `(a, b)` pair (stable insertion, not a re-sort that would break the pair-score ranking); in `_tree_orders`, prefer splitting on determiner columns before their dependents. These are free structural hints about evaluator data with no new machinery.

5. **Add a guarded duplicate-row-first candidate that orders by exact duplicate-row density.** Compute full-row duplicates via a Counter over joined strings from the existing `ser_cols` (cheap: one join pass), and build an ordering that places columns with the most row-wise duplicate overlap (measured with pairwise `sum((cnt_a[v]==cnt_b[v]))` on codes) adjacent to each other — a chain-assembly heuristic for the sorted-row LCP objective. Wrap any failure with a fallback to `order1` (Gen 8/Gen 10's graceful-degradation pattern) so run success stays 1.00; the strict shape assert and `col_pos` per-row assembly must remain untouched to avoid the Gen 11/15/19 crash classes.
