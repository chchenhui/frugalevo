# Analysis of Evaluated Programs

## Successful Algorithmic Patterns

- **Multi-candidate generation + exact adjacent-LCP Trie scoring remains the winning pattern, and the current best (Gen 13, serial_trie_reuse_rewrite) is its fastest realization.** It scores 0.72 at 2.72s with hit rates [0.79, 0.65, 0.83, 0.44, 0.84] — matching the 0.72 ceiling of Gens 16 (3.59s) and 18 (1.79s) while beating Gen 12/17's 0.11 (which used the same pattern but with weaker candidates). The two-candidate design (global frequency order + conditional partition tree) suffices when the tree is well-tuned.
- **The conditional partition tree with factorized integer codes is the highest-value candidate generator.** Gen 13's implementation — factorizing each column into codes with cached value lengths once, ranking top-16 candidate columns by repetition savings, and greedy splitting with budget 4096 / depth ≤ 8 — achieves up to 0.84 hit rate at 2.72s total runtime. Gens 16, 18 use similar factorized-code trees and also hit 0.72.
- **Exact evaluator-matched serialization is essential.** Gen 13 explicitly serializes with fillna→str matching the evaluator, and keeps LCP scoring cheap via binary search — this exactness lets candidate selection never regress below measured reuse.
- **Runtime can be cut without score loss through budget guards and fewer candidates.** Gen 18 (union-find block constraints, 3 candidates) achieved 0.72 in 1.79s, and Gen 13 in 2.72s — both faster than Gen 4's 8.00s at equal score, confirming previous insights that budget cutoffs are pure speed wins.

## Ineffective Approaches

- **Crashes from interface/typing fragility remain the dominant failure mode: 4 of 9 new programs scored 0.00.** Gen 11 (undefined `Algorithm` base class NameError), Gen 14 (`ncols` vs `n_cols` NameError), Gen 15 (unpacking `calculate_col_stats(df)` against the wrong parent API contract → TypeError), Gen 19 (raw float value reaching `len()` — NaN/col_merge serialization hole). None of these algorithmic ideas were ever evaluated.
- **Shallow/conservative tree parameters collapse the score.** Gen 12 and Gen 17 — structurally similar to the winners — scored only 0.11 (hit rates 0.004–0.144) because their tree parameters (depth ≤ 3, groups ≥ 4, top-candidate limits, aggressive guards like the 20M-cell scoring skip) fail to find structure the winner's deeper/broader tree (depth 8, top-16 columns, 4096-split budget) captures. Same pattern, vastly different tuning.
- **Fixed candidate sets plateau at 0.72 with a persistent 0.44 outlier.** Every 0.72 program (Gens 10, 13, 16, 18) shows the identical weak dataset (~0.44), confirming previous insights that frequency/length heuristics + conditional trees cannot capture certain data distributions.
- **Leftover refactoring dead code (Gen 10's dead `_conditional_tree_orders`) adds complexity without score effect** — a maintainability risk, not a scoring one.

## Implementation Insights

- **Gen 13's key strengths:** (1) one-pass column factorization into integer codes with per-code string lengths, making tree gain computation `(k−1)·len` O(1) per value; (2) a deterministic global-order suffix completing each partial tree order per row; (3) try/except around conditional-order generation and scoring so any internal failure degrades gracefully to the global candidate rather than crashing; (4) exact evaluator-matched serialization (`fillna("")→astype(str)`).
- **Gen 13's residual weaknesses worth noting for future work:** the `merged_cols_set` / dtype-restore loop in `reorder` is dead code (a `pass`-only body wrapped in try/except) — harmless but indicates the col_merge path is under-tested (Gen 19 crashed exactly there). The two-candidate set (global + tree) is minimal; Gens 16/18 with three candidates score the same, suggesting the third candidate is not the binding constraint.
- **Defensive validation guarantees survive crashes:** Gen 13 asserts output shape and fills per-row `orders[i]` with a base permutation for any unassigned rows, so the tree's budget exhaustion cannot produce invalid output — contrasting with Gens 14/15/19's total failures.
- **Budget guard placement matters:** Gen 13's 40M-char guard on the conditional tree plus a 4096-split budget keeps runtime at 2.72s; Gen 12/17's tighter guards (depth 3, 20M-cell scoring skips) caused the tree to be skipped or too shallow, directly explaining their 0.11 scores.

## Performance Analysis

- **Score ceiling remains exactly 0.72 across all five working programs** (Gens 10: 14.83s, 13: 2.72s, 16: 3.59s, 18: 1.79s) with near-identical hit-rate profiles ([0.79, 0.65, 0.83, 0.44, 0.84]). The binding constraint is confirmed to be the ~0.44 outlier dataset, not runtime or correctness.
- **Runtime spread at equal score is now 8.3×:** Gen 18 (1.79s) < Gen 13 (2.72s) < Gen 16 (3.59s) < Gen 10 (14.83s). Gen 13 is the best balance of speed and simplicity; Gen 18's union-find block handling is slightly faster but more complex.
- **Tuning, not structure, separates 0.72 from 0.11:** Gen 12 (0.11) and Gen 17 (0.11) share the multi-candidate + exact-LCP-scoring skeleton of the winners but with shallow trees (depth ≤ 3, group ≥ 4) and heavy budget guards. The winners' deeper trees (depth 8–12) with repetition-savings-based column ranking (top-16) and larger budgets (4096 splits) consistently capture the structure that Gen 12/17 miss (hit rate 0.004 vs 0.44 on the weakest dataset).
- **Crash-based 0.00 failures (Gens 11, 14, 15, 19) account for 44% of new evaluations,** all from NameError/TypeError at definition or serialization time — reinforcing previous insights that interface contract validation (base class import, variable naming consistency, parent API return shapes, NaN/float-tolerant serialization) must precede any algorithmic improvement.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add a greedy adjacent-swap local search candidate ("orderL") derived from the winning candidate set.** After computing `global_order` and the tree orders, run a hill-climb on the global order: for each column pair in the top ~8 positions, try swapping and re-score via `_score_orders` on a row subsample (≤50k rows); accept improving swaps and add the final order as a third candidate. The exact adjacent-LCP scorer already guarantees the candidate is only chosen if strictly better, so this can only raise the score — and it directly attacks the 0.44 outlier where fixed heuristics plateau.

2. **Diversify tie-breaking inside the conditional tree to break the 0.44 outlier.** Add a parallel tree candidate identical to `_conditional_orders` except that column gain uses within-group value-length entropy (or `(k-1)·len·depth_discount`) instead of raw `(k−1)·len` repetition savings, and raise `candidate_cols` from top-16 to top-24 for this variant. Since all 0.72-scoring programs share identical hit-rate profiles, the binding constraint is candidate diversity, not runtime — a second tree statistic is the cheapest way to capture the structure the current tree misses.

3. **Extend score-guided selection to large datasets via subsampled scoring instead of skipping the tree.** Currently the tree is skipped when `total_chars > 40M`. Instead, always build the tree (with a reduced 2048-split budget) and score all candidates on a 1M-cell random row subsample, then apply the winning order to all rows. Gen 12/17 showed that skipping/shallowing the tree collapses hit rates to 0.11, so guarding by subsampling rather than skipping preserves score-guided selection on large inputs while keeping runtime bounded near the 2.72s baseline.

4. **Harden the col_merge/serialization path before any logic mutation.** Replace the dead `merged_cols_set` try/except block with a real dtype-restore loop guarded by `if col_merge:`, and make `_serialize` robust to mixed float/NaN columns (e.g., pre-convert `float` columns with `.fillna("").astype(str)` semantics identical to the evaluator). Gens 14, 15, and 19 all scored 0.00 from exactly this class of crash — fixing it is the cheapest insurance that future algorithmic ideas actually get evaluated.

5. **Deepen the tree selectively using the 1.79s runtime headroom.** Gen 18 proved 0.72 is achievable in 1.79s, leaving ~1s of budget over the current 2.72s. Raise `max_depth` from 8 to 12 and the split budget from 4096 to 8192 only when `n_cols ≥ 8 and n_rows ≤ 200k` (where deeper trees found structure in Gens 13/16), keeping the 40M-char guard as an absolute cap. Gen 12/17's failure came from trees that were too shallow, so spending the spare runtime on depth is the most direct tuning improvement consistent with all winner evidence.
