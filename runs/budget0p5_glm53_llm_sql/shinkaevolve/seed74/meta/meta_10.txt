# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Multi-candidate generation + exact trie-reuse scoring is the dominant winning pattern.** Every correct high-scoring program (Gen 1 Trie-Prefix at 0.72/2.08s, Gen 3 Trie-Aware at 0.72/3.02s, Gen 4 at 0.72/8.00s, Gen 5 at 0.72/3.30s, Gen 6 at 0.72/3.87s) uses the same core: build 2–4 candidate column orderings, score each by the sum of adjacent LCPs over lexicographically sorted serialized rows, and return the best. This consistently yields 0.72 combined score with 100% success.
- **The conditional partition tree is the best-performing candidate generator.** The current best program (Gen 5, 3.30s) greedily builds a per-row tree (depth ≤ 12) choosing the column maximizing length-weighted duplicate-pair gain `len(v)*k*(k-1)` at each node, and combines it with two global orders (distinct-count-based and repetition-based). This achieves hit rates of 0.79–0.84 on strong datasets while the exact LCP scoring guarantees no candidate is picked worse than measured.
- **Budget guards keep runtime low without hurting correctness.** The best program's cutoffs (skip tree at >2M cells, skip scoring at >6M cells) achieve 3.30s total runtime vs. Gen 4's 8.00s at the same 0.72 score — 2.4× faster through budget limiting alone.
- **Row serialization with sorted-string adjacent LCP comparison at C speed** is the exact, cheap scoring function; NaN→"" normalization and binary-search LCP keep it both correct and fast.

## Ineffective Approaches

- **Global-only column ordering without candidates collapses on outlier datasets.** Gen 7's simple global length-weighted repetition ranking (score 0.63) scored as low as 0.02 hit rate on one dataset, versus the multi-candidate/tree programs' worst case of 0.44 — candidate diversity and per-row ordering are essential.
- **Fixed candidate sets plateau.** All four 0.72-scoring programs share the same weakness: the ~0.44 hit-rate dataset (and Gen 4's 0.45 case) shows that 3–4 fixed candidates + tree miss structure in data with less duplicate structure or high column diversity. No evaluated program broke past 0.72 via candidate set alone.
- **Fragile index/type bookkeeping causes total failure, not just score loss.** Gen 0 (TypeError from int64 `original_index` mixing with strings via concat/merge), Gen 2 (`NameError: block_lens` free variable), Gen 8 (off-by-one `IndexError` from `pairs`/`weights` array length mismatch), and Gen 9 (missing `Algorithm` base class) all scored 0.00 — crashes from parameter-passing omissions and mixed-dtype merges are the leading failure mode in this task.
- **Recursive DataFrame splitting with positional `result_df.loc[i]` under `as_completed`** (Gen 0) introduces nondeterministic-order correctness risks in addition to the dtype crash.

## Implementation Insights

- **The best program's key implementation strengths:** (1) factorized serialized column values held as lists (`col_vals[cidx[c]]`) for O(1) per-row string assembly; (2) candidate orders stored per-row, enabling mixed tree/global orders in one evaluation pass; (3) `assert len(order) == n_cols and set(order) == set(cols)` guarantees output validity before DataFrame construction; (4) explicit guard for duplicate column labels falling back safely.
- **Exact scoring must never be skipped for correctness, only for budget:** the best program falls back to candidate "A" (distinct-count order) rather than guessing when budget is exceeded, and retains 100% success rate.
- **Topological dependency handling** (Gen 5's iterative pairwise-swap topo ordering over `one_way_dep` pairs, with substring matching `dep[0] in c`) preserves constraints while appending locked columns at the end of each candidate order — none of the 0.00-failure programs successfully combined this with scoring.
- **Depth/threshold safeguards trade adaptivity for speed:** Gen 6's shallow tree (rows > 5000 or > 256 unique values → skip) noted this likely contributes to cross-dataset variance; Gen 5's deeper tree (depth 12) with gain-based `early_stop` shows the variance persists regardless, pointing to the candidate set as the bottleneck.

## Performance Analysis

- **Score ceiling is exactly 0.72 for all working multi-candidate programs** (Gens 1, 3, 4, 5, 6), with identical hit-rate profile shape: ~[0.79, 0.62, 0.83, 0.44, 0.84]. The binding constraint is the ~0.44 outlier dataset, not runtime or correctness.
- **Runtime varies 2.4× at equal score:** Gen 1's 4-candidate approach is fastest (2.08s), the current best Gen 5 is 3.30s, Gen 6 3.87s, Gen 3 3.02s, while Gen 4's 8.00s shows heavier scoring overhead with no score gain. Gen 5's budget cutoffs (2M/6M cells) are the best speed/complexity trade-off among tree-based programs.
- **Simple approaches are strictly worse:** Gen 7's global-order-only variant (0.63) is both slower (13.90s) and less robust (0.02 hit rate), confirming per-row tree orders and candidate scoring are jointly necessary.
- **The 0.00-failure programs (Gens 0, 2, 8, 9) demonstrate that crash bugs, not algorithmic weakness, are the primary risk** — four of ten generations failed on NameError/TypeError/IndexError/missing base class, reinforcing that defensive typing, explicit parameter passing, and preserving the `Algorithm` inheritance are prerequisites before any scoring improvements matter.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Break the 0.44 outlier with a diversified candidate generator targeting low-duplicate-structure data.** All 0.72 programs plateau on the same weak dataset, suggesting the fixed A/B/tree candidates miss its structure. Add a 4th candidate: a per-row adaptive order built from the tree but with a *different* tie-breaking statistic (e.g., rank columns by within-group value-length entropy or by position of first character divergence), since the exact LCP scorer already guarantees any new candidate can only be chosen if it scores strictly higher.

2. **Add an order-hybridization candidate via greedy adjacent-swap local search on the best global order.** After computing orderA/orderB, run a cheap hill-climb (pairwise column swaps, ~O(n_cols²) trie re-scorings on a row subsample of ≤50k rows) and score the result as candidate "L". The scoring function is exact and cheap; local search directly optimizes it and is orthogonal to the duplicate-pair gain heuristic the tree uses.

3. **Cap n_cols in scoring by evaluating candidate orders on a random row sample, not the full matrix, when budget is between 2M and 6M cells.** Currently scoring is skipped entirely above 6M cells (falling back to orderA, untested). Instead, score all candidates on a 1M-cell random subsample — the relative ranking of candidates is preserved with high probability, extending score-guided selection to large datasets while keeping runtime bounded.

4. **Harden against the dominant failure mode: crash bugs from bookkeeping.** Before mutating any algorithm logic, add defensive checks: verify `col_stop`/`row_stop` are numeric and clamp with `min(len(free_cols), max(1, int(...)))`, wrap `merging_columns` and the tree recursion in try/except with candidate "A" as fallback, and keep the existing `assert len(order) == n_cols` (converted to a soft check that falls back rather than raises). Four of ten generations scored 0.00 from crashes — this is the cheapest score-preserving improvement.

5. **Tune the tree's gain heuristic to include child-purity lookahead, and cache group value strings.** Modify `_assign_tree` to score each candidate column by the *post-split* adjacent-LCP gain of the prefix+column (i.e., `sum(len(v)*k*(k-1))` discounted by depth cost) instead of raw pair count, and hoist `len(v)` computations into a precomputed per-column value-length dict to cut tree build time — this can allow raising the 2M-cell tree budget toward 3–4M without runtime regression, improving tree coverage on larger datasets where the tree candidate currently helps most.
