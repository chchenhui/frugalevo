# Analysis of Evaluated Programs

## Successful Algorithmic Patterns

- **Multi-candidate generation + exact adjacent-LCP Trie scoring remains the winning pattern, and the current best (Gen 13, serial_trie_reuse_rewrite) remains its fastest strong realization at 0.72 in 2.72s.** Five new programs (Gens 20–24) all apply the same pattern and score 0.09–0.72, confirming its robustness — but none breaks the 0.72 ceiling.
- **The two-candidate design (global frequency order + deep conditional partition tree) is sufficient at the current ceiling.** Gen 13's factorized integer-code tree (depth 8, top-16 ranked columns, 4096-split budget) hits 0.72 at 2.72s. Adding more candidates does not help: Gen 24 (crossover_multistat_candidates) with global + edge-savings + two trees + flat clustering scored 0.71 at 26.13s; Gen 23 (conditional_partition_tree_candidate) with four global candidates plus tree scored 0.72 at 1.94s — marginal runtime win, no score gain.
- **Runtime can be cut without score loss through lean candidate sets.** Gen 23 achieves the same 0.72 at 1.94s with a slightly leaner candidate set than Gen 13 (2.72s), continuing the trend that Gen 18 (1.79s) established. Runtime spread at equal score is now 14.6× (1.79s to 26.13s).
- **Exact evaluator-matched serialization (`fillna("")→astype(str)`) is confirmed essential across all six working programs** — every scoring program matched the evaluator's serialization, while crash-failures (Gen 19 previously) occurred at serialization holes.

## Ineffective Approaches

- **Shallow/overly conservative tree tuning collapses the score.** Gen 20 (serial_trie_ordering_fix) scored 0.09 (hit rates 0.004–0.146) — its "bounded-depth" conditional partition tree and greedy global candidates failed to match optimal orderings, exactly reproducing the Gen 12/17 failure mode (0.11 with depth ≤ 3). The whole `_candidate_conditional` path was reported as dead/unused code — meaning the program effectively had only weak global candidates.
- **More candidates ≠ higher score.** Gen 24's five diverse candidates (0.71, 26.13s) and Gen 21's three candidates (0.72, 15.55s) do no better than Gen 13's two candidates, at 5.7–9.6× the runtime. Candidate diversity does not address the persistent 0.44 outlier.
- **Gating heuristics that disable the tree hurt.** Gen 23's tree only triggers when `col_merge` is empty and size limits are met; the 0.44 outlier persists whenever global orders dominate the tree's contribution.
- **The 0.44–0.444 hit-rate outlier is structural across all eight 0.70–0.72 programs (Gens 10, 13, 16, 18, 21, 22, 23, 24)** — frequency/length heuristics plus conditional trees consistently fail on this dataset; none of the new diversity attempts (edge-savings ranking, two-level clustering, multi-stat candidates) moved it.

## Implementation Insights

- **Gen 13's key strengths remain the reference implementation:** one-pass column factorization into integer codes with cached value lengths (making tree gain O(1) per value), a deterministic global-order suffix completing partial tree orders, try/except graceful degradation to the global candidate, and exact evaluator-matched serialization. Its trade-off of two candidates keeps runtime at 2.72s while matching all multi-candidate variants' scores.
- **Defensive validation guarantees survive partial failure:** Gen 13 fills unassigned `orders[i]` with a base permutation; Gen 22 (condprefix_tree_roworders, 0.70) similarly ensures per-row output consistency, but its feedback shows a residual weakness — rebuilding the frame in a single base order while emitting per-row orderings separately can limit gains when frame/order alignment matters. All working programs keep output shape and value-multiset assertions.
- **Budget guard placement is the score/runtime lever:** Gen 21 caps trees at 64 columns / depth 40 (15.55s), Gen 24 uses max_depth 40 / min_group 2 / n_cols≤64 gating (26.13s), while Gen 13's 40M-char guard + 4096-split budget runs at 2.72s at equal score. Deeper caps buy no score, only cost.
- **Dead code is recurring noise, not a scoring risk:** Gen 20's unused `_candidate_conditional`, Gen 13's pass-only dtype-restore loop. Gen 19's crash was in exactly the col_merge area Gen 13 leaves under-tested — a live fragility risk in the current best program.

## Performance Analysis

- **Score ceiling is exactly 0.72 across eight working programs** (Gens 10: 14.83s, 13: 2.72s, 16: 3.59s, 18: 1.79s, 21: 15.55s, 22: 20.28s, 23: 1.94s, 24: 26.13s) with near-identical hit-rate profiles ([~0.79, ~0.65, ~0.83, ~0.44, ~0.84]). The binding constraint is confirmed to be the ~0.44 outlier dataset, not runtime or correctness.
- **This generation's runtimes regressed:** four of five new programs (15.55s–26.13s) run 6–10× slower than the best at equal or lower score, showing that adding candidates/trees without score gains is pure cost. Gen 23 (1.94s) is the only one to slightly undercut Gen 13's runtime at the same 0.72.
- **Tuning remains the separator of 0.72 from 0.09:** Gen 20's weak/shallow candidates (0.09) versus Gen 21–24's deeper trees (0.70–0.72) repeat the Gen 12/17-vs-13 pattern — same architecture, order-of-magnitude score differences from depth, budget, and candidate strength.
- **No new crash-failures this generation** (all five new programs ran 100%), a positive trend for interface-fragility; the prior 44% crash rate (Gens 11, 14, 15, 19) is not repeated, but the col_merge path in Gen 13 remains the least-exercised correctness surface.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add a greedy adjacent-swap local search candidate ("orderLS") derived from the global order.** After computing `global_order`, run a hill-climb: for each pair in the top ~8 positions, swap and re-score with `_score_orders` on a subsample (≤50k rows), accept improving swaps, and append the result as a third candidate. Since the exact scorer only selects a candidate when strictly better, this is score-safe and directly attacks the ~0.44 outlier where fixed heuristics (Gens 10–24) all plateau; Gen 13's 2.72s leaves ample runtime budget for a bounded swap search.

2. **Diversify tree gain statistics with a parallel entropy-based tree candidate.** Add a second `_conditional_orders` variant identical to Gen 13's factorized implementation but scoring column gain as within-group value-length entropy (e.g., `(k-1)*len*depth_discount`) instead of raw `(k-1)*len`, with `candidate_cols` raised from top-16 to top-24.
