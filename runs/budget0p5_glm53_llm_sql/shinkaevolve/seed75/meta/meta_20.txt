# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Dual global heuristics + bounded conditional partition tree, scored exactly, is the new best**: Gen 11 ("Trie-Scored Column Reorder with Frequency and Partition Tree", 0.73 @ 2.15s) and Gen 18 ("Trie-Reuse Column Reordering with Candidate Selection", 0.73 @ 3.83s) both tie for the top score, beating the previous best simple global-order approach (Gen 7, 0.72 @ 2.19s). This shows the dual-frequency-score + partition-tree candidate pool is the first method to break the long-standing 0.72 ceiling.
- **Two complementary global scores add real value over one**: Gen 11 and Gen 18 rank columns by both `len(v)*n*(n-1)` and `len(v)*(n-1)` variants, generating two distinct global orders. This contrasts with Gen 14 (0.71), which used only global candidates and plateaued.
- **Cheap conditional partition trees help structured datasets but are bounded enough to stay fast**: Gen 11's tree (node-budget 4000, ≤8 candidate columns per split) and Gen 18's tree (depth ≤10, cand_cap 12) both kept total runtime under 4s while pushing high-end hit rates to 0.825–0.842.
- **Exact LCP-based candidate scoring remains reliable and consistent**: every correct program in this batch (Gens 10–14, 16–19) used sum-of-adjacent-LCPs over sorted serialized rows for candidate selection with 100% run success — the scoring objective is mature and never the failure point.

## Ineffective Approaches

- **Small heuristic candidate pools remain the binding constraint**: Gen 16 ("Candidate-Based Column Reordering", 0.07, hit rates 0.004–0.146) shows that heuristic candidates whose ranking metric is decoupled from true LCP reuse can catastrophically fail even with correct exact scoring — echoing Gen 6's earlier 0.05.
- **Pandas API misuse causes total failure**: Gen 15 (score 0.00) crashed on `pd.factorize(col.tolist(), ...)` rejecting a plain Python list; the fix is trivial (`pd.factorize(pd.Series(...))` or passing the Series directly). The current best program uses `pd.factorize(pd.Series(cellstr[c], dtype=object), sort=False)` — the correct pattern.
- **Constraint fixes applied after scoring can degrade the optimal order**: Gen 19's feedback explicitly notes that applying col_merge/one-way_dep adjacency constraints post hoc may damage the best-scored ordering; Gen 11's dependency insertion was likewise called out as a weak sequential placement. Constraints should be built into candidate generation (as Gen 18 does via merge handling during evaluation) rather than patched afterward.
- **Excess runtime without score gain**: Gen 12 (0.67 @ 61.41s) and Gen 10 (0.70 @ 28.23s) show heavy per-row serialization and repeated global scoring calls waste 10–30x runtime for equal or worse scores versus the ~2–4s leaders.

## Implementation Insights

- **The current best program (Gen 18, 0.73 @ 3.83s) combines all proven patterns**: two global orders (length-weighted `len(v)*n*(n-1)` and pair `len(v)*(n-1)` scores), a bounded recursive partition tree (depth ≤10, cand_cap 12, group_cap 2) that greedily splits on the column maximizing weighted repetition savings, exact trie scoring of each candidate, merge-group contiguity enforced before scoring, and `astype(object)` output. Its hit rates (0.794, 0.693, 0.825, 0.444, 0.842) match Gen 11's exactly — both converge on equivalent orderings.
- **Serialize once, reuse everywhere**: Gen 18 serializes every cell exactly once into `cellstr[c]`, then builds codes, lengths, row strings, and scores from that single representation — a key reason its 3.83s runtime is 16x faster than Gen 12's 61.41s.
- **Serialization must exactly match the evaluator**: NaN→"" and `str(v)` (as in Gen 14's explicit note and Gen 18's `_cell_str` with defensive `pd.isna` try/except) is prerequisite for the exact-trie objective to correlate with the real metric.
- **Bounded trees with fallback tails are essential for robustness**: Gen 18's tree falls back to a global-score tail order at depth/size limits and wraps recursion in try/except with a global-order fallback — this guaranteed 100% success across all runs.

## Performance Analysis

- **The 0.72 plateau has been broken — narrowly**: 0.73 (Gen 11, Gen 18) vs the prior cluster of 0.69–0.72. The gain is driven by identical per-dataset hit rates, suggesting a slightly better tree configuration or dual-score candidate diversity, not a fundamentally new ordering.
- **Runtime is now decoupled from score at the top end**: Gen 11 achieves 0.73 at 2.15s and Gen 18 at 3.83s — both faster than every 0.70–0.72 multi-candidate predecessor (7–28s). Slow programs (Gen 12: 61s for 0.67) confirm extra compute does not help.
- **The ~0.44 dataset remains the universal, unsolved weakness**: every program in this batch (and Gens 1–9 previously) shows hit rates 0.44–0.45 on this dataset. Conditional partition trees at depths 8–12 with caps of 8–24 candidates did not improve it, confirming that qualitatively different search (e.g., local swap search or dependency-aware ordering) is needed there.
- **Failure is binary and easily triggered**: Gen 15's single `pd.factorize` argument error produced 0.00 despite sound algorithm logic; correctness robustness (object dtype, defensive serialization, fallbacks) is mandatory before any scoring gains matter.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

# Recommendations

1. **Add a bounded adjacent-swap hill-climb refinement on top of the best candidate order.** After the candidate evaluation loop selects `best_orders`, run up to ~20 iterations of trying all adjacent column-pair swaps on the winning flat order (or per-tree-node tail orders), accepting a swap only if the exact `_trie_reuse` score improves; cap the loop at ~2s using the existing fast serialization. This directly attacks the stuck 0.44 dataset, where the heuristic + tree has plateaued, and the exact scoring machinery is already fast enough (3.83s) to absorb it.

2. **Fix the `_apply_merges` behavior inside tree orders, which currently breaks contiguity semantics and can destroy scored quality.** The merge forcing is applied per-row after tree assignment, whereas Gen 18's feedback shows constraints must be built into candidate generation: instead, treat merge groups as atomic "super-columns" from the start (score groups by summed `len(v)*n*(n-1)` over member columns, bincount on the group's serialized tuple), so both global orders and the tree split only on whole groups. This preserves the "constraints in generation, not post hoc" insight and may reveal new orderings for constrained datasets.

3. **Handle `one_way_dep` constraints natively in the tree and global orders rather than ignoring them.** Currently `one_way_dep` is accepted but unused; enforce it as an ordering constraint (dependency column must precede dependent column) by excluding dependent columns from the candidate set until their dependency is placed — either in the tail order or as a pre-pass that topologically sorts groups. This is free score improvement on any dataset where the constraint fires, and costs nothing otherwise.

4. **Add a greedy pair-based candidate order via marginal adjacent-LCP gain.** As the third (or fourth) flat candidate, build the column order left-to-right: seed with the best `gscore` column, then at each step append the column that maximizes the sum of adjacent LCPs of the sorted serialized prefixes of rows (reuse `cellstr`, computing on prefix strings only). This captures conditional dependencies that independent frequency scoring misses, is O(k²) scoring calls within budget, and slots directly into the existing candidates list evaluated by exact `_trie_reuse`.

5. **Add a cheap duplicate/prefix-aware candidate that appends a group-id column first.** For the stuck ~0.44 dataset, interleaving of structurally different rows is the suspected cause; generate one candidate where rows are grouped by a hash of their 2–3 rarest serialized cells (using the lowest-`gscore` columns as "class markers"), and the tree (or flat order) places the class-marker column first followed by the global tail order. This targets the one unsolved dataset while leaving the other four candidates intact — the max-over-candidates evaluation guarantees no regression risk.
