# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

# Analysis of Program Evaluation Results

## Successful Algorithmic Patterns

- **The current best program (Gen 18, 0.73 @ 3.83s) confirms the "dual global heuristic + bounded partition tree + exact scoring" recipe is the top performer**. Its hit rates (0.794, 0.693, 0.825, 0.444, 0.842) exactly match Gen 11's (0.73 @ 2.15s), showing both programs converge on equivalent orderings — this is a stable, reproducible pattern worth preserving.
- **Multi-candidate selection with exact trie scoring remains the winning backbone**: all four correct programs in this batch (Gens 21–23 plus Gen 18) use it, scoring 0.70–0.73 with 100% success. Gen 21 (0.71) and Gen 23 (0.70) show that adding more candidates (up to 4, including length-ranked and class-marker groupings) does not beat Gen 18's 3-candidate setup.
- **One-time factorization and budgeting keep trees fast**: Gen 21's single-pass integer factorization plus candidate caps/node budgets kept it at 11.74s; Gen 18's depth ≤10, cand_cap 12, group_cap 2 plus a 3M-cell tree gate is even faster at 3.83s. Bounded trees with global-order fallback tails guarantee robustness.
- **Merge constraints handled before scoring (as in Gen 18's `_apply_merges` applied per candidate before evaluation) preserve the selection validity**, unlike Gen 19's post-hoc constraint patching that degraded orderings.

## Ineffective Approaches

- **A single int-unpacking bug causes total failure**: Gen 20 scored 0.00 via `TypeError: 'int' object is not iterable` in its candidate/tree expansion — echoing Gen 15's `pd.factorize` list-argument crash. This batch confirms correctness robustness is a binary gate; Gen 18's try/except-wrapped tree recursion with global-order fallback is the proven defensive pattern.
- **Adding extra candidate types yields no gain**: Gen 22's deadline-bounded adjacent-swap hill-climb over the exact objective (0.72 @ 20.64s) and Gen 23's class-marker grouping candidate (0.70 @ 2.55s) both fail to beat Gen 18's 0.73. The hill-climb's 2-second budget and 4M-cell gate consumed 5x Gen 18's runtime for a slightly worse score, confirming diminishing returns from more compute/candidates.
- **Tree depth/cap variation doesn't move the score**: Gen 21's tree seeded from multiple bases still hits the same hit-rate profile (0.44–0.84) as Gen 18, indicating the candidate pool composition is saturated at this level.

## Implementation Insights

- **Gen 18's effectiveness comes from minimal-but-diverse candidates**: exactly two global orders (`len(v)*n*(n-1)` and `len(v)*(n-1)` scores) plus one bounded tree, each scored with the exact sorted-adjacent-LCP objective via a chunked `_lcp` (64-char step) — 3.83s total.
- **Serialize once, reuse everywhere**: Gen 18 serializes each cell once into `cellstr[c]` (NaN→"", defensive `pd.isna` try/except), then derives codes, lengths, row strings, and scores from it — the same pattern Gen 21 credits for its manageable runtime. Gen 20's crash shows the tree/candidate code paths need the same defensive care.
- **Correct factorize pattern is settled**: `pd.factorize(pd.Series(cellstr[c], dtype=object), sort=False)` (Gen 18) is the safe form; passing a raw list crashes (Gen 15).
- **Tree robustness pattern to copy**: Gen 18's `rec()` falls back to a gscore-ranked tail order at depth/size/candidate limits and the whole tree is wrapped in try/except with a per-row global fallback — this is why it never fails while Gen 20's unguarded tree pipeline crashed to 0.00.

## Performance Analysis

- **Score plateau at 0.73 holds**: Gen 18 (0.73) remains best; this batch's new programs landed at 0.70 (Gen 23), 0.71 (Gen 21), and 0.72 (Gen 22), with Gen 20 at 0.00. No new candidate type (length-ranked, class-marker, hill-climb) broke the ceiling.
- **Runtime is now the differentiator among near-equal scores**: at 0.72–0.73, runtimes range from 2.15s (Gen 11) and 3.83s (Gen 18) to 20.64s (Gen 22). Gen 22's hill-climb bought nothing for 5x the cost, reinforcing that extra search time does not convert to score.
- **The ~0.44 dataset remains universally unsolved**: every correct program in this batch hits 0.44–0.45 there (Gen 18: 0.444; Gen 21/22: 0.44/0.45; Gen 23: 0.44). Gen 22's hill-climb over the exact objective — the most direct local-search attempt yet — still failed to improve it, suggesting the needed structure is not reachable by adjacent-swap local moves or these tree splits.
- **Hit-rate profiles are nearly identical across all correct programs** (0.79/0.69/0.83/0.44/0.84), indicating all approaches find the same effective orderings and further gains require a qualitatively different ordering mechanism rather than candidate shuffling.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

# Recommendations

1. **Build merge groups as atomic "super-columns" from the start instead of post-hoc `_apply_merges`.** Score each merge group by summing `len(v)*n*(n-1)` over member columns, bincount on the concatenated serialized tuple of member cells in the tree, and let global orders and tree splits place whole groups only. Gen 19 showed post-hoc patching degrades orderings; Gen 18's "constraints in generation" principle is the proven recipe, and group-atomic trees may also unlock new orderings on constrained datasets without any runtime penalty.

2. **Enforce `one_way_dep` as a topological ordering constraint.** Currently the parameter is ignored. Pre-sort groups/columns so a dependency column always precedes its dependent (e.g., exclude dependent columns from the tree candidate set until their dependency is placed, or topologically sort the gscore tail order). This is free improvement on any dataset where the constraint fires and zero cost otherwise — the max-over-candidates evaluation means it can be added as a 4th candidate with no regression risk.

3. **Add a greedy pair-based candidate order via marginal adjacent-LCP gain.** As a 3rd/4th flat candidate, build the order left-to-right: seed with the best-`gscore` column, then repeatedly append the column maximizing adjacent-LCP of the sorted serialized row prefixes (reusing `cellstr`, scoring prefix strings only). This captures conditional dependencies that independent frequency scoring misses and is O(k²) fast scoring calls — well within Gen 18's 3.83s budget.

4. **Target the stuck 0.444 dataset with a class-marker-first candidate.** Generate one candidate where rows are grouped by a hash of their 2–3 rarest serialized cells (lowest-`gscore` columns as class markers), placing the class-marker column(s) first followed by the global tail order, and/or seeding the tree from these marker columns. All programs plateau at 0.44 there, so the needed structure likely requires a qualitatively different split — but keep it as an extra candidate so the max-over-candidates guarantee prevents regressions on the other four datasets.

5. **Keep runtime discipline: cap any new refinement at the existing candidate loop, do not add hill-climbing.** Gen 22 proved a 2s adjacent-swap hill-climb over the exact objective costs 5x runtime for a slightly worse score (0.72), so mutations should prioritize cheap, structurally diverse candidates (as above) rather than more local search. Also wrap any new candidate-generation code in try/except with a global-order fallback per Gen 18's tree pattern — Gen 20's single int-unpacking bug caused a 0.00 score, confirming correctness is a binary gate.
