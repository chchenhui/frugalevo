# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Simple repetition-scored global column ordering + lexicographic row sorting matches the best multi-candidate approaches**: The current best program ("Prefix-Caching Column and Row Reordering", Gen 7, 0.72, 2.19s) uses a single global order scored by `sum(len(v)*count*(count-1))` with lexicographic row sorting, and ties or beats the more complex multi-candidate programs (Gen 3: 0.72 @ 11.33s; Gen 8: 0.71 @ 10.65s; Gen 9: 0.71 @ 7.07s; Gen 1: 0.71 @ 11.40s) — at ~5x less runtime.
- **Exact LCP scoring of a small candidate pool is reliable but plateaus**: Programs scoring candidates with sum-of-adjacent-LCPs of sorted serialized rows (Gen 1, 3, 8, 9) all cluster at 0.70–0.72, indicating the candidate-generation heuristic (frequency/length/repetition rankings) is the binding constraint, not the scoring method.
- **Deterministic tie-breaking and object dtype preserve correctness and reproducibility**: The best program's `astype(object)` output and deterministic sort keys (score desc, distinct count, avg length, column name) yield 100% run success and stable results across all runs.

## Ineffective Approaches

- **Typed DataFrame row assignment crashes on mixed data**: Gen 0 (score 0.00) failed via `result_df.loc[i] = reordered_row` into an int64 column receiving strings — dtype validation kills the whole run. The best program avoids this with object dtype throughout.
- **Dead/placeholder code causes total failure**: Gen 5 (score 0.00) crashed on a leftover placeholder loop and forward reference, despite a sound candidate-scoring design.
- **Heavy candidate enumeration with weak heuristic-objective coupling wastes runtime**: Gen 6 scored only 0.05 (hit rates 0.004–0.146) with 48.84s runtime — greedy metrics poorly correlated with true LCP reuse despite matching the objective nominally.
- **Purely global orderings miss structure on hard datasets**: The persistent ~0.44 hit rate on the same dataset (Gen 1, 3, 7, 8, 9 all show it) shows repetition/frequency heuristics cannot capture row-level conditional structure there; bounded partition trees (depth ≤10–12) did not fix it either.

## Implementation Insights

- **The best program's core loop is minimal and effective**: serialize cells once → score columns by length-weighted pair repetition → sort columns → sort rows by concatenated serialized string → return uniform per-row orderings. This achieves the same 0.72 as Gen 3's three-candidate conditional partition tree at 2.19s vs 11.33s.
- **Serialization must exactly match evaluator format**: successful programs serialize NaN/None to "" and non-strings via `str(v)`; the best program's `_serialize_cell`/`_serialize_rows` implement this with defensive try/except around `pd.isna`.
- **Per-row orderings add no measurable benefit over uniform orderings** when the heuristic is repetition-based: the best program returns `[list(order)] * n` and matches programs generating per-row conditional orders (Gen 3, 8, 9).
- **Score formula `len(v)*count*(count-1)` for column ranking is the dominant contributor** — echoed by Gen 2's feedback identifying score-based block-first ordering as its main driver.

## Performance Analysis

- **Score ceiling around 0.72**: All correct programs cluster at 0.69–0.72 (Gen 1: 0.71, Gen 2: 0.69, Gen 3: 0.72, Gen 4: 0.70, Gen 8: 0.71, Gen 9: 0.71, Gen 7 best: 0.72), with hit rates 0.44–0.84. - **Runtime varies 20x with no score gain**: the best program's 2.19s is far faster than 10–11s multi-candidate programs and 0.05s runtime margin over Gen 2's 1.88s at 0.69 — simplicity wins on speed without score loss.
- **Failure modes are binary**: dtype bugs (Gen 0) and dead code (Gen 5) yield 0.00 regardless of algorithm quality; correctness robustness (object dtype, no typed assignment) is prerequisite.
- **The ~0.44 dataset is the universal weakness**: no evaluated approach — conditional trees, multiple candidates, exact scoring — improved it, indicating the remaining gains require qualitatively different ordering search (e.g., local swaps), not deeper heuristics.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add a local-swap hill-climbing search over the column order, seeded by the current heuristic.** The 0.72 ceiling and the stuck ~0.44 dataset indicate heuristics have plateaued; a bounded search (e.g., try all adjacent-pair swaps, accept if the sum-of-adjacent-LCPs of the sorted serialized rows improves, repeat for ≤20 iterations within a ~5s budget) directly optimizes the true objective. Keep the existing lexicographic row sort fixed and only search the column permutation, since that pairing is the proven core.

2. **Add a second scoring candidate and pick by exact adjacent-LCP evaluation of the fully assembled output.** Generate 2–3 column orders (current score formula, plus pure `count*(count-1)` and pure length-weighted frequency), then for each: serialize, lexicographically sort rows, and compute actual sum of adjacent LCPs, returning the best. Gen 3/8/9 showed exact scoring works but their candidate generation was weak — reusing the best program's fast 2.19s core keeps this well under the ~11s of slower competitors.

3. **Cluster rows before sorting to exploit per-dataset structure.** Instead of one global lexicographic sort, group rows by the value of the top-scored column (or a cheap hash of the first 2–3 serialized cells), sort within each group, and concatenate groups ordered by their serialized prefixes. This targets datasets where global sorting interleaves structurally different rows — the likely cause of the persistent 0.44 hit rate — while remaining deterministic and fast.

4. **Use per-row column orderings only when a detectable conditional structure exists.** For each row, rank columns by how many other rows share that row's exact cell value (precompute value→count maps once); if this per-row order diverges substantially from the global order on enough rows, emit it, otherwise keep the uniform order. Since uniform orderings already match per-row programs in score, gate this behind a cheap similarity check to avoid regression risk.

5. **Explore pair-based column ordering via adjacent-LCP marginal gains.** Rather than scoring columns independently, greedily build the column order left-to-right: start with the best-scoring column, then at each step pick the column maximizing the gain in sum-of-adjacent-LCPs when appended (computed on serialized prefixes of the already-chosen prefix). This captures conditional dependencies between columns that the current independent `len(v)*count*(count-1)` scoring provably misses, and can be implemented in O(k²) LCP evaluations per dataset within the current runtime budget.
