# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **The current best program remains the strongest quality/runtime design.** The current **Constraint-Aware Prefix Cache Reorderer** achieved **0.72 combined score**, **1.00 successful-run rate**, and **2.53 s total runtime**. Its approach—two repetition-based global rankings, exact LCP/trie candidate scoring, and a bounded conditional candidate only when unconstrained—matches the best observed aggregate behavior. Its hit rates of **0.794, 0.624, 0.826, 0.444, and 0.834** show strong performance on four of five workloads without expensive search.

- **Frequency-based global orders plus exact candidate selection are consistently successful.** The current best evaluates both  
  `sum(len(value) * count * (count - 1))` and  
  `sum(len(value) * count * count)`  
  rank-derived orders, then chooses based on the actual serialized trie/LCP score. New correct implementations using closely related alternatives—Generation 10, 11, 13, 14, and 17—also reached **0.72**, confirming that repetition-weighted global ordering is a reliable high-scoring baseline.

- **Constraint-aware unit construction preserves correctness while retaining strong scores.** The current best converts merge requests into contiguous union-find units, ranks positions inside each unit, and applies dependencies through deterministic topological ordering. Generation 13 similarly uses contiguous merge units plus stable topological sorting and achieved **0.72** with full validation success. This supports the earlier finding that constraints should be integrated into candidate construction rather than repaired after unconstrained ordering.

- **Bounded conditional logic is useful when paired with cheap global fallbacks.** The current best’s conditional candidate is capped at **48 candidate columns**, **12 levels**, and **256 nodes**, yet it always compares that candidate against two legal global layouts. Generation 14 used natural, frequency-weighted, and bounded conditional candidates and also reached **0.72**, although at **2.85 s**, slightly slower than the current best. The pattern is that conditional ordering can improve selected cases, but exact comparison against robust global candidates is what maintains aggregate quality.

## Ineffective Approaches

- **More expensive conditional-search implementations did not improve score.** Generation 12, *Safe Conditional Serialization Reordering*, was correct but obtained only **0.67** while taking **57.60 s**—over **22×** the current best runtime. Generation 16 used a substantially larger bounded search configuration—**48 candidates, depth 12, 2,048 nodes**—but reached only **0.71** in **11.21 s**. The evaluation data shows that expanding conditional exploration did not break the score plateau around 0.71–0.72.

- **Limited conditional candidate sets can fail badly on certain distributions.** Generation 15, *Prefix-Optimized Row-Specific Column Reordering*, achieved **0.68**, with a low per-case hit rate of **0.290** despite reaching **0.841** elsewhere. This is materially weaker than the current best’s minimum of **0.444**. Its bounded conditional heuristic and limited global/conditional candidate set were correct but generalized poorly to at least one workload.

- **Persistent weak-case behavior is not solved merely by conditional partitioning.** The current best, Generations 10–14, 16, and 17 all exhibit a low hit rate near **0.444** on one evaluator case. This remains true across implementations with simple bounded trees, larger node budgets, different unit representations, and factorized values. The evidence indicates that the difficult workload reflects a shared limitation of the evaluated prefix-reuse heuristics, rather than insufficient search depth alone.

- **Candidate-construction indexing errors eliminate all value from otherwise plausible designs.** Generation 18, *Prefix-Cache Column Reordering*, received **0.00** and had `runs_successfully: 0.00` because of an `IndexError: list index out of range`. Unlike slower or lower-scoring correct variants, it never reached quality evaluation. This reinforces the prior evidence from failed Generations 0 and 2: safe positional handling, complete candidate permutations, and compatible data operations are prerequisites for optimization results.

## Implementation Insights

- **The current best cleanly separates optimization strings from output values.** It creates `strings_by_column` exclusively for frequency analysis, candidate serialization, and LCP scoring, while final output is reconstructed from `df.astype(object).values.tolist()`. The result uses original columns, `df.index.take(row_order)`, and `dtype=object`. This is a central correctness feature shared by the successful new programs, including Generations 10, 11, 13, 14, 16, and 17, all of which explicitly preserve raw values while serializing only for scoring.

- **The current best directly aligns scoring with final row sorting.** For every candidate, it concatenates values in that row’s candidate order, computes `_trie_score` after lexically sorting those strings, and then uses the selected strings to derive `row_order`. This avoids optimizing one representation and materializing another. Generation 13 follows the same broad pattern—evaluate candidate serialized orders, then sort rows by the selected representation—and also achieved **0.72**, though at **4.46 s**.

- **The current best’s constrained ordering code is economical.** `_constraint_units` unions merge-connected positions, maintains an order inside each merge unit based on rank, maps dependency edges between units, and performs deterministic topological emission. It avoids repeatedly repairing illegal per-row orderings. By contrast, Generation 16’s union-find and dependency-aware design was correct but considerably slower (**11.21 s**), suggesting the current best’s lean candidate count and smaller conditional budget are important to its **2.53 s** result.

- **Factorization is optional rather than inherently superior.** Generation 17 uses factorized string values and reached **0.72** in **4.59 s**, proving factorized representations can be correct and competitive. However, it was still about **1.8×** slower than the current best. The current implementation’s direct Python string counts and bounded LCP comparisons were sufficient for the evaluated workload and delivered the best runtime among all reported 0.72-score solutions.

## Performance Analysis

- **The current best is still the best demonstrated score/runtime tradeoff.** Several new programs matched its **0.72** combined score: Generation 10 (**5.92 s**), Generation 11 (**5.51 s**), Generation 13 (**4.46 s**), Generation 14 (**2.85 s**), and Generation 17 (**4.59 s**). None improved on the current best’s **2.53 s** runtime. Generation 14 came closest, but remained approximately **13% slower**.

- **Score equivalence across many implementations indicates a quality plateau.** The current best and Generations 10, 11, 13, 14, and 17 all cluster at **0.72**, while Generation 16 is **0.71**, Generation 15 is **0.68**, and Generation 12 is **0.67**. This suggests the central performance determinant is the shared combination of repetition-aware column ordering and LCP-based row sorting, while implementation variations mostly affect runtime and worst-case stability.

- **Runtime is strongly affected by search complexity, not proportional score gain.** The current best’s **2.53 s** runtime is followed by Generation 14 at **2.85 s**, Generation 13 at **4.46 s**, Generation 17 at **4.59 s**, and Generations 10–11 at roughly **5.5–5.9 s**. More elaborate variants are much slower: Generation 16 at **11.21 s**, Generation 15 at **12.14 s**, and Generation 12 at **57.60 s**. None exceeded the current best’s **0.72** score.

- **The repeated hit-rate pattern confirms broad effectiveness but a shared hard case.** High-performing systems repeatedly achieve roughly **0.79** on one case, **0.82–0.83** on another, and **0.83–0.84** on a fifth case. Meanwhile, the approximately **0.444** result persists in the same hard workload across the strongest implementations. Generation 15’s **0.290** minimum and Generation 12’s lower overall **0.67** show that weaker conditional designs can degrade this stability further, while the current best maintains the highest observed aggregate result without excessive runtime.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add two or three cheap repetition-based rank metrics, then retain exact candidate scoring.** In addition to the existing `count*(count-1)` and `count*count` ranks, construct constrained global orders from metrics such as `sum(len(v) * count for duplicated v)` and `sum(len(v) * count*(count-1) / distinct_count)`. Pass every rank vector through `_constraint_units` and choose solely by `_trie_score`; this preserves the proven “cheap global candidates plus exact selection” architecture while adding diversity at negligible runtime cost.

2. **Make serialization injective with cached length-delimited cell encodings.** Replace `"".join(...)` with a boundary-safe representation such as `f"{len(value)}:{value}"` for each serialized value, cached in `strings_by_column` or a parallel encoded matrix. This prevents collisions between different ordered sequences such as `["ab", "c"]` and `["a", "bc"]`, allowing trie scoring and final row sorting to optimize the actual ordered-cell sequence more faithfully without altering returned raw values.

3. **Implement a constraint-safe conditional candidate over merge units rather than disabling conditional ordering for all constrained inputs.** Treat each merge-connected group as an indivisible unit with its rank-derived internal order, and during prefix partitioning select only dependency-ready units whose predecessors have already been placed. Keep the current tight budgets—roughly 48 candidate units, depth 12, and 256 nodes—and compare this candidate against the two global constrained candidates; this specifically explores the persistent weak constrained case without adopting the costly search sizes that underperformed.

4. **Add a tightly bounded exact local-improvement candidate for each global constrained order.** After `_constraint_units` produces a legal unit sequence, examine a small fixed number of legal adjacent swaps or short insertion moves between incomparable units, materialize each resulting legal order, and retain only the best exact `_trie_score` result. Cap work aggressively, for example 16–32 proposed moves selected around the highest-rank units, since broader search has shown poor score/runtime returns while small candidate diversification remains consistent with the best design.

5. **Use an adaptive gate for conditional-order generation based on measurable remaining repetition mass.** Before invoking `_conditional_orders`, estimate the expected benefit from the first global order—for example, measure repeated-byte mass among columns beyond the first few highest-ranked columns or the fraction of rows sharing values in those columns. Skip conditional construction when that mass is low, but allow the normal bounded conditional candidate when substantial repeated structure remains; this protects the current 2.53-second runtime while concentrating search on inputs where global frequency ranking is most likely insufficient.
