# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Exact candidate selection using the evaluator-aligned trie/LCP objective is the strongest recurring pattern.** The current best, **Prefix-Cache Dataframe Reordering** (Generation 2, score **0.73**, runtime **7.36s**), builds global, alternate, and conditional layouts, then scores their fully serialized rows with `_score_strings` and chooses the actual best candidate. This outperformed constraint-aware variants that used broadly similar heuristics but scored **0.67–0.72**.

- **Combining inexpensive global frequency orders with a bounded conditional alternative performs well.** Generation 2 evaluates:
  1. `pair_rank = Σ len(v) * count(v) * (count(v)-1)`,
  2. a squared-length alternative rank, and
  3. a recursive conditional partition layout.
  
  Its **0.73** score was the best observed, narrowly ahead of Generations 1 and 7 at **0.72**. The hit rates also show this mixture is effective on several workloads: **0.7941, 0.6893, 0.8255, and 0.8428**.

- **Preserving original object values while separating serialization from output construction is essential for reliable optimization.** All successful implementations use normalized strings only for scoring and preserve source cells positionally. Generation 2 explicitly snapshots cells with `df.to_numpy(dtype=object, copy=True)` and emits `dtype=object`, avoiding the mixed-type assignment failure seen in Generation 0.

- **Bounded conditional ordering can help without making runtime prohibitive when carefully limited.** The current best caps recursive ordering to the top **24** ranked units and depth **12**, then fills remaining units using a ranked topological tail. This maintained full correctness and a practical **7.36s** runtime, much better than the more expensive related implementations in Generations 3 (**38.25s**), 5 (**57.43s**), 6 (**40.34s**), and 9 (**23.89s**).

## Ineffective Approaches

- **Constructing output under inherited DataFrame dtypes is unsafe for row-specific value movement.** Generation 0 scored **0.00** because it failed validation/execution: reordered timestamp-like integer and string values were assigned into an `int64` destination column, causing a `TypeError`. This confirms that output positions cannot retain source-column dtype assumptions when each row may use a different source-column permutation.

- **More complex constraint-aware or conditional implementations did not consistently improve score.** Generations 3, 5, 6, and 9 all retained correctness but scored only **0.67–0.70**, below the current best’s **0.73**, while taking **23.89–57.43s**. Their additional conditional/search or constraint machinery appears to have increased computational cost without producing more effective layouts under the evaluator.

- **Conditional heuristics alone do not solve the weakest benchmark.** Every successful program, including the current best, has a weak hit rate near **0.444** on one evaluator case. Generation 2’s fourth hit rate is **0.444443**, while the alternatives range roughly **0.444–0.4444** as well. This indicates that the shared repeated-value partition heuristic has a consistent blind spot rather than an isolated implementation defect.

- **Expanding heuristic variants without strong final discrimination has limited value.** Generation 4’s global/conditional approach scored **0.71** at **18.04s**, and Generation 8 scored **0.71** at **5.62s**. Both are valid, but neither exceeded Generation 2’s three-candidate exact-score selection. The evidence favors a small set of materially different candidates over heavier search.

## Implementation Insights

- **The current best safely separates three representations of the data:**
  - original cells: `source_values`,
  - evaluator-compatible scoring strings: `text_values`,
  - per-row source-column mappings: `best_orderings`.
  
  This directly supports validation requirements: values are preserved exactly, scoring can use string normalization, and ordering metadata accurately identifies each source column. This design is shared by successful implementations and fixes Generation 0’s dtype failure mode.

- **Generation 2 uses an exact, efficient enough proxy for serialized trie reuse.** `_score_strings` sorts complete serialized rows and sums pairwise LCP lengths. For a fixed string set, adjacent lexicographic strings capture trie prefix sharing, and the binary-search LCP implementation avoids explicit Python character-by-character scanning. This enables exact ranking of the three candidate constructions rather than trusting column-level ranks alone.

- **Merged columns and dependencies are implemented as ordering constraints rather than value transformations.** `_make_units` keeps merge groups contiguous; `_topological_order` chooses among dependency-available units according to heuristic rank. This preserves cells and label positions while enabling constraint-safe global orders. The deterministic fallback for dependency cycles avoids failures or dropped columns.

- **The conditional tree uses a practical hybrid strategy.** It selects an eligible unit only when the unit creates positive repeated-value score within the current row group, partitions rows by that unit’s serialized value, and then appends the rest through `tail_order`. That prevents costly exhaustive row-specific permutation search while still creating different leading layouts for different value partitions.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add a small number of additional globally ranked layouts, but retain exact `_score_strings` selection over all complete candidates.** In addition to the current pair-rank and squared-length rank, try ranks based on `len(value) * count(value)^2`, `len(value) * (count(value)-1)`, and a prefix-sensitive rank that rewards repeated short values more strongly. Keep the candidate set bounded—e.g., 5–7 total layouts—and choose only by the exact serialized-row LCP score, preserving the current program’s strongest design principle.

2. **Improve conditional splitting by evaluating one-step lookahead gain rather than only the immediate repeated-value score.** For each eligible unit in a row group, estimate the gain from its current partition score plus the best remaining-unit repetition score inside its child partitions; choose the unit with the best bounded two-level estimate. This directly extends the successful conditional layout while addressing its apparent blind spot: greedy local repeated-value selection may choose a good first partition that prevents stronger downstream prefix reuse.

3. **Construct a hybrid candidate that uses conditional prefixes only where they beat the best global order locally.** At each conditional tree leaf or partition, compare the serialized LCP contribution of its conditional unit prefix against the corresponding prefix from `global_units` and `alternate_units`; if the conditional choice has no estimated benefit, fall back to the better global ordering for that subset. This can reduce harmful row-specific variation while retaining conditional gains, and it remains compatible with final exact whole-candidate scoring.

4. **Add bounded local order mutations around the best global layout, especially swaps of adjacent independent units.** Starting from `global_units` and `alternate_units`, generate a few dependency-safe variants by swapping adjacent units with similar rank, moving one high-repeat unit forward by one or two positions, or reversing short independent blocks. Score every resulting complete layout exactly; this explores cases where coarse frequency ranks are nearly correct but miss serialized partial-prefix interactions that the evaluator rewards.

5. **Make candidate selection more targeted on the weak workload by adding a value-shape-aware layout family.** Detect columns or units with high uniqueness but shared textual prefixes—such as IDs, timestamps, paths, or numeric strings—and rank them using sampled pairwise/common-prefix statistics rather than only exact-value counts. The shared approximately `0.444` hit-rate floor suggests exact repeated-value partitioning is insufficient for at least one workload; a prefix-similarity rank can exploit common leading characters even when full unit values are mostly distinct.
