# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **The current best program’s three-candidate architecture remains the strongest score/runtime tradeoff.** It evaluates only: (1) identity column order, (2) a repetition-weighted global order, and (3) bounded row-conditional orders, then chooses using the exact sorted-string adjacent-LCP/trie score. This achieved **0.72 combined score**, **1.00 successful runs**, and **3.19 s**, outperforming the newer correct conditional implementations at **0.71**: Generation 10 (**9.26 s**), Generation 11 (**8.65 s**), Generation 13 (**13.53 s**), and Generation 16 (**9.70 s**).

- **Repeated-value-first global ranking is consistently productive when paired with exact candidate selection.** The current best scores each column unit using `len(value) * frequency * (frequency - 1)`, prioritizing long duplicated strings that can create reusable leading serialization text. Generation 14 used a closely related length-weighted duplicate-value score and also reached **0.72**, with **3.74 s** runtime, supporting the value of this scoring family.

- **Bounded conditional partitioning improves several workloads without harming correctness.** The current program’s conditional tree uses at most **12 levels**, **32 globally promising units**, and **512 nodes**, producing hit rates of **0.794**, **0.624**, **0.825**, and **0.838** on four workloads. The same global-plus-conditional concept was correct in Generations 10, 11, 13, and 16, whose upper hit rates reached approximately **0.835–0.841**.

- **Constraint-safe atomic units preserve validation reliability.** The current best builds merge groups as union-find-derived column units and applies dependencies at unit level before flattening them back into columns. Generation 14’s constraint-aware implementation and Generations 10–13/16 all passed validation, showing that contiguous merge handling and dependency-aware ordering are compatible with high prefix-cache scores when each row remains a complete source-column permutation.

## Ineffective Approaches

- **More conditional-search work did not exceed the 0.72 score ceiling and often made runtime much worse.** Generation 13’s bounded conditional DataFrame reordering reached only **0.71** but required **13.53 s**; Generation 17 reached **0.69** and required **30.87 s**. Earlier evidence likewise showed expensive variants at **0.68** taking over **42–54 s**. The evaluated results indicate that deeper or costlier conditional processing did not improve the benchmark’s observed best combined score beyond the current program’s compact search.

- **Incomplete conditional orders break constraint application.** Generation 18 failed completely (**0.00**, `runs_successfully: 0.00`) with `ValueError: 0 is not in list`. Its conditional leaves could omit columns outside the limited candidate set, but constraint repair assumed every source column existed in the proposed order. The current best avoids this by always forming a tail from all remaining global-order units, so every generated order is complete.

- **Inconsistent positional versus name-keyed row representations cause hard runtime failures.** Generation 15 also scored **0.00** and failed with `TypeError: list indices must be integers or slices, not str`, because it used row data as both lists and mappings. The current best uses positional integer column indices consistently in `cell_strings`, candidate construction, scoring, materialization, and `column_orderings`.

- **Additional global heuristics alone did not reliably improve results.** Generation 17 compared pair-score, simple-score, and conditional candidates but achieved **0.69**, below the current best’s **0.72**, while being almost ten times slower (**30.87 s** versus **3.19 s**). This suggests that extra global ranking formulations did not compensate for their implementation and evaluation cost on this evaluator.

## Implementation Insights

- **The current best cleanly separates optimization strings from preserved output values.** It converts only the scoring representation through `_string_value`, while retaining `df.to_numpy(dtype=object, copy=True)` for output materialization. Output cells are copied as `values[row, source_column]`, and the result is explicitly built with `dtype=object`. This is a central correctness mechanism behind its **100% success rate**, avoiding the dtype/coercion failure mode previously observed in typed-output approaches.

- **Its conditional order generator maintains the complete-permutation invariant.** In `_conditional_orders`, every leaf creates `prefix + tail`, where `tail` contains every remaining unit in global order, and then flattens all units into positional columns. This directly avoids the Generation 18 failure in which a bounded candidate subset left columns out of an order before constraints were applied.

- **Exact evaluation is restricted to three full layouts.** `_trie_score` lexicographically sorts candidate serialized strings and sums LCPs of adjacent strings, giving an exact reuse score for a fixed layout. The current best pays this exact evaluation cost only three times, unlike more expansive variants. Its **3.19 s** runtime is faster than Generation 14’s related **3.74 s** implementation and materially faster than the **8.65–13.53 s** correct conditional variants.

- **Deterministic ordering is integrated throughout the pipeline.** Stable score tie handling, sorted partition keys, stable dependency adjustment, and final row sorting by `(best_strings[row], row)` produce repeatable output. This is aligned with the flawless validation of the current best and the other successful `trie_safe_reorder` implementations, while still making the LCP locality represented by the selected serialized strings explicit in final row placement.

- **The current best is tied for the top observed combined score but is the fastest program at that score.** It scored **0.72 in 3.19 s**. Generation 14 also scored **0.72**, but took **3.74 s**. The newer Generation 12 global-only conservative design also reached **0.72**, but required **5.03 s**. Thus, the current best’s bounded conditional design has not imposed a runtime penalty relative to the top-scoring global-only alternative.

- **Correct programs cluster tightly in score but differ substantially in runtime.** Generations 10, 11, 13, and 16 all scored **0.71**, while Generation 17 scored **0.69**; all passed validation. Their runtimes range from **8.65 s** to **30.87 s**, compared with **3.19 s** for the current best. The principal observed differentiator is therefore efficiency of implementation and search bounding, not broad score separation among valid prefix-oriented heuristics.

- **The weak workload remains unresolved across all successful variants.** The current best has a **0.444443** hit rate on one workload. Generations 10–17 report essentially the same floor, around **0.444–0.4444**, including the top-scoring Generation 12 (**0.444–0.843**) and Generation 14 (**0.4444–0.8338**). This consistency shows that variations in repetition weighting, global candidate types, dependency handling, and bounded conditional construction have not materially changed performance on that evaluator case.

- **Conditional logic helps selected workloads, but its aggregate advantage over strong global ordering is narrow.** The current best’s high hit rates on several cases—especially **0.8255** and **0.8379**—support conditional refinement’s usefulness. The current best’s advantage is that it retains conditional capability while remaining faster than that global-only implementation.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add one fourth, fixed global-order candidate based on “shared-prefix potential after discrimination.”** Keep the current repetition score, but compute an alternative per-unit score such as `sum(len(v) * freq(v) * (n - freq(v)))`, optionally minus a small penalty for near-unique values. Exact-score this one additional complete layout alongside identity, repetition-ranked, and conditional layouts; this is a low-risk extension of the proven small-candidate architecture and directly targets cases where duplicated values alone are not the best leading fields.

2. **Create a dependency-safe hybrid candidate using a short original-order prefix and the ranked tail.** For example, generate candidates preserving the first one and first two atomic units in original unit order, then append all remaining units in `global_units` order before calling `_dependency_adjust`. This can capture schema-local prefix structure that identity ordering exploits while retaining the strong repeated-value-first behavior for the majority of columns, with only one or two additional exact layout evaluations.

3. **Add a bounded adjacent-swap refinement to the repetition-ranked global unit order.** After `_dependency_adjust`, consider deterministic swaps only within the first 12–16 units, retaining a swap when it improves `_trie_score` on the resulting full fixed-order serialization; cap testing to a small fixed number of pairs, such as adjacent pairs plus a few top-score/non-top-score exchanges. This preserves complete atomic units and dependency safety while allowing the algorithm to correct interactions that independent unit scores cannot model, without adopting the expensive broad searches that underperformed in runtime.

4. **Make conditional-node unit selection explicitly partition-aware while retaining the current caps.** When evaluating a candidate unit at a node, augment its duplicate-length score with a small score derived from its resulting partition sizes, for example `sum(len(key_text) * group_size * (group_size - 1))` over partitions or a bonus for fewer, larger non-singleton groups. Continue using the existing limits of depth 12, 32 candidate units, and 512 nodes; the change improves alignment with the actual sorted-string LCP objective while preserving the best program’s successful bounded conditional design.

5. **Use an adaptive early-stop rule inside the conditional tree based on expected remaining benefit.** Before expanding a node, compare the best local repeated-value score against a threshold relative to `len(rows)` and stop when the selected unit would mostly create singleton partitions or has negligible reusable text. This should reduce conditional overhead on weak or heterogeneous branches, while reserving the existing conditional capability for the workloads where it already produces strong hit rates near `0.825–0.838`; every stopped branch must continue to use the existing complete `prefix + global-order tail` construction.
