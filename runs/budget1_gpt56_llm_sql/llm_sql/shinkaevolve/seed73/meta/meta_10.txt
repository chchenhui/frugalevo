# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Preserving values positionally while carrying a per-row source-column mapping is the key correctness pattern.** The current best, **Generation 3 “Prefix-Aware Conditional Column Reorderer,”** reached **0.72 combined score**, **1.00 successful-run rate**, and **3.19 s runtime** by materializing each output row from `values[row, source_column]` while separately returning `column_orderings`. This avoids dtype-coercion and source/value misalignment problems seen in Generation 0.

- **Use a small candidate set and score candidates exactly.** Generation 3 evaluates exactly three alternatives: original order, globally frequency-ranked order, and bounded conditional orders. It selects the maximum exact sorted-string LCP score via `_trie_score`. This achieved the top observed score while keeping runtime low. The same overall design was also successful in Generation 1 and Generation 5, both at **0.72** with full validation success.

- **Global repetition-weighted ranking plus bounded conditional refinement is consistently effective.** In the current program, units are globally scored by  
  `len(value) * frequency * (frequency - 1)`, favoring long repeated strings that can create reusable serialized prefixes. The conditional tree then recomputes this score inside row partitions. This produced strong hit rates on four of five workloads: **0.794, 0.624, 0.825, and 0.838**, with only one weak case at **0.444**.

- **Constraint-aware atomic units are compatible with strong performance.** Generation 3 keeps merged columns consecutive through union-find-derived units and repairs one-way dependencies using stable movement of source units before targets. Similar merge/dependency-safe variants in Generations 1, 4, 5, and 9 all validated successfully and stayed near **0.71–0.72**, showing that constraint handling need not sacrifice the prefix-cache objective.

## Ineffective Approaches

- **Constructing a typed output DataFrame before row-specific reordering is unsafe for heterogeneous data.** Generation 0 scored **0.00** and failed validation because timestamp-like integers and strings were assigned into inferred `int64` columns. Its recursive reordering could move values from heterogeneous source columns into incompatible destination dtypes. The current best avoids this by extracting an object array and constructing the result with `dtype=object`.

- **Inconsistent internal representation of text rows causes total failure.** Generation 7 also scored **0.00** with `runs_successfully = 0.00` because text rows were stored as positional lists while another code path indexed them using string column names (`TypeError: list indices must be integers or slices, not str`). This confirms that positional column indices must be used consistently throughout scoring, serialization, and materialization.

- **More expensive conditional/trie logic did not improve the score ceiling.** Generation 6 reached only **0.68** despite correctness, but required **54.07 s**. Generation 8 likewise reached **0.68** with **42.23 s**. Their larger or more expensive bounded conditional processing and exact scoring did not beat the current best’s **0.72 at 3.19 s**, indicating that additional search overhead was not rewarded by corresponding hit-rate gains.

- **Heuristic sophistication alone does not solve the weak evaluator case.** Every successful prefix-oriented variant retained a low hit rate near **0.444** on one workload: Generation 3 had **0.444443**, Generation 5 had **0.444**, and Generations 1, 2, 4, 6, 8, and 9 reported the same approximate floor. Thus, changing naming, minor score weighting, merge implementation, or conditional-tree limits did not materially address that workload.

## Implementation Insights

- **The current best separates scoring representation from output representation.** It computes `cell_strings` only for ordering and LCP scoring, with `_string_value` normalizing scalar missing values to `""`. It retains `values = df.to_numpy(dtype=object, copy=True)` for output. This separation is directly aligned with its perfect validation rate: string normalization influences optimization only, while original objects, labels, and row identities are preserved.

- **The bounded conditional tree is a favorable performance/cost compromise.** Generation 3 caps conditional processing with `max_depth = 12`, at most `32` globally promising candidate units, and `max_nodes = 512`. This is likely a major reason it matched the best combined score at only **3.19 s**, versus **6.05 s** for Generation 2, **6.13 s** for Generation 9, **9.21 s** for Generation 4, and tens of seconds for Generations 6 and 8.

- **Exact objective evaluation is used only after aggressive candidate restriction.** `_trie_score` lexically sorts full candidate strings and sums adjacent LCPs, which exactly measures the stated reuse objective for a fixed candidate. The program avoids applying this expensive global evaluation to a large combinatorial order space: it compares only three full candidates. This combination produced the strongest score/runtime balance in the evaluated set.

- **Deterministic fallback behavior supports reliable validation.** The code uses stable ordering for score ties, deterministic partition-key traversal, dependency repair, and final `(best_strings[row], row)` row sorting. That deterministic behavior, plus explicit shape/order assertions, is consistent with the **100% successful execution** seen in Generation 3 and the other working `trie_safe_reorder` variants.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Keep the three-candidate architecture, but add one cheap alternative global ranking based on positional discriminativeness.** In addition to the existing repetition-weighted global order, construct a rank using a score such as `sum(len(v) * freq(v) * (n - freq(v)))` or an entropy/distinctness penalty, then exact-score it as a fourth candidate only if runtime permits. This directly preserves the successful “small candidate set plus exact `_trie_score` selection” pattern while targeting workloads where highly repeated values are not the best leading serialization fields, likely including the persistent ~0.444 case.

2. **Add a lightweight adjacent-unit local-search candidate after dependency repair.** Starting from `global_units`, try a bounded number of deterministic adjacent swaps—e.g., only among the top 12–16 units, accepting swaps that improve an inexpensive sampled or full `_trie_score`—then materialize one additional fixed-order candidate. This is a small, controlled extension of the proven global ranking approach and may recover gains missed by a purely per-unit independent score without the high cost of the larger searches that caused 42–54 second runtimes.

3. **Make conditional-unit selection prefix-aware by scoring the expected next serialized contribution, not only repeated cell length.** At each conditional-tree node, retain the current repeated-value score but add a small bonus for columns whose partition keys create fewer/larger groups, such as `sum(len(key_string) * group_size * (group_size - 1))` over multi-column unit keys. This builds on the already successful bounded partition tree while better aligning unit choice with the actual objective: creating long shared prefixes among rows that will be adjacent after lexical sorting.

4. **Introduce an adaptive conditional-tree budget based on data size and observed partition benefit.** Preserve the current safe caps as defaults, but allow modest expansion—for example, from depth 12/nodes 512 to depth 16/nodes 1024—only when early selected units have strong repeated-value scores and partitions remain large; otherwise terminate earlier. This keeps Generation 3’s strong runtime profile while allocating additional computation only to instances where conditional refinement is demonstrably likely to improve over the global order.

5. **Add a constraint-safe “original-prefix plus ranked-tail” candidate for heterogeneous or weakly repetitive data.** Generate one deterministic hybrid ordering that preserves the first one or two original atomic units, then appends remaining units in the existing global frequency-ranked order with `_dependency_adjust`; exact-score it against existing candidates. Because the original-order candidate already sometimes wins and the repeated-value ranking is strong elsewhere, this hybrid can capture evaluator distributions where early schema order carries useful prefix structure while later columns benefit from repetition-oriented reordering.
