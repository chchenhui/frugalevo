# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **The current best program, Multi-Start GPU KV Pressure Balancer, confirms that diversified pressure-aware construction plus lexicographic refinement is the leading pattern.** It achieved the top observed **26.23 combined score**, **25.23 max_kvpr**, **0.01 s**, and **100% success**. - **Projected global pressure scoring during greedy placement is consistently effective.** The current program evaluates the resulting *global maximum* `load / remaining_memory` after each potential addition, rather than selecting a GPU based only on local free space. Related multi-start programs using the same pressure-aligned greedy idea were also near the top: Generation 40’s *Multi-Start KV Cache Placement* and Generation 43’s *Multi-Start KV Cache Pressure Placement* both scored **26.21** with full correctness.

- **Strict lexicographic comparison of the full descending GPU-pressure vector is a key top-tier refinement mechanism.** In the current program, an action can be accepted even when it does not immediately reduce the scalar maximum, provided it reduces the ordered bottleneck profile. This avoids cycles and improves secondary tied bottlenecks. The earlier top Generation 32 used the same staged lexicographic approach and also reached **26.23**, strengthening the evidence that this is not an isolated result.

- **Staged compound moves effectively handle memory fragmentation without harming runtime.** The current best first searches relocations and swaps, then only considers one-for-two exchanges and bounded three-GPU ejection chains when ordinary improvements do not exist. This is more targeted than broad compound-neighborhood exploration. Generation 40 and 43 likewise used one-for-two and chain-style repairs and remained high at **26.21**, while the current program preserved the best quality at only **0.01 s**.

## Ineffective Approaches

- **Single-start construction remains weaker than diversified construction, even when the local-search neighborhood is broad.** Generation 41’s *Greedy KVPR Placement with Local Search* used greedy assignment plus moves, swaps, and three-GPU evict-and-move operations, but reached only **25.85**, trailing the current best by **0.38**. - **More seed orderings did not automatically outperform the current five-order, two-tie-policy design.** Generations 40 and 43 used **seven orderings** and two tie modes but scored **26.21**, slightly below the current program’s **26.23**. This narrow difference suggests that the specific ordering set and subsequent lexicographic local search matter more than simply increasing the number of starts.

- **Broader repair mechanisms have shown diminishing returns in the supplied evaluations.** Previous results found larger ejection-chain and destroy-and-repair variants in the **25.92–26.20** range, below the current best. The current implementation’s chains are bounded, attempted only after simpler neighborhoods fail, and restricted to bottleneck-source models, avoiding the quality/runtime tradeoff seen in less focused expansion.

- **The greedy constructor is objective-aligned and fragmentation-aware.** `projected_add_score` recalculates the candidate GPU’s post-add ratio while preserving the other GPUs’ ratios, selecting the placement with the lowest projected global maximum. # META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Choose the final multi-start result by the full lexicographic pressure vector, not only `candidate.score()`.** After each `improve(candidate)`, compute `candidate_key = tuple(sorted(ratio(candidate.loads[g], candidate.remaining[g]) for g in range(gpu_num), reverse=True))` and retain the candidate with the smallest key. This extends the current improvement criterion consistently across seeds, preserving lower secondary and tertiary bottlenecks when multiple constructions share the same maximum KV pressure.

2. **Add a bounded reverse two-for-one exchange after the existing one-for-two neighborhood fails.** Specifically, test replacing two models on a bottleneck GPU with one model from another GPU, with exact post-exchange memory checks and acceptance only when the resulting full pressure key improves. The existing one-for-two exchange already demonstrates that asymmetric exchanges overcome fragmentation; the reverse direction can handle cases where shedding multiple high-pressure models from a bottleneck is necessary to admit a larger, pressure-favorable replacement.

3. **Add a small number of targeted, objective-aware seed orderings while preserving the existing five-order/two-policy portfolio.** Promising additions are descending `(weight(m), -m.model_size)`, descending `weight(m) / max(GPU_MEM_SIZE - m.model_size, epsilon)`, and a bucketed large-to-small order that sorts by weight within size classes. Multi-start construction is a proven top-tier feature, but these should be limited to two or three additional orderings so the current 0.01-second advantage is retained.

4. **Prioritize compound-move enumeration using predicted bottleneck relief rather than iterating every eligible model pair.** For one-for-two, reverse two-for-one, and chain searches, rank source models on bottleneck GPUs by a combination of `weight(model)`, `weight(model) / model_size`, and the projected reduction in the source GPU ratio; inspect only a small top subset. This builds on the successful top-six pruning in the current ejection chain and should enable a richer neighborhood without broad exhaustive repair searches that previously showed diminishing returns.

5. **Extend the three-GPU chain with a targeted “direct-fit or eject” target ranking.** For each selected bottleneck model, rank target GPUs by the projected global pressure if the model were added, then only test ejection from the best few targets where a single displaced model creates sufficient capacity; rank destinations for that displaced model by their projected resulting pressure. The current staged chain is valuable precisely because it is delayed until simpler moves fail, and better target/destination ranking can improve its ability to escape fragmented layouts without turning it into an expensive unrestricted chain search.
