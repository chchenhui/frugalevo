# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Threshold-based transformed packing remains the top-performing pattern.** The current best program, **Binary-Search KV Pressure Model Packing**, achieved **26.23 combined score**, **25.23 max_kvpr**, **0.01 execution time**, and **1.00 success rate**. It directly transforms the target constraint  
  `load / (80 - used_memory) <= T`  
  into `load + T * model_size <= 80 * T`, so construction is aligned with the evaluator’s maximum-KVPR objective rather than merely balancing current loads greedily.

- **The best program combines threshold search with multiple packing orders rather than trusting a single greedy run.** At every candidate threshold it attempts transformed-resource-dominant, memory-first, and demand-first orderings. This is consistent with the earlier successful threshold-packing family—Generations **35, 37, and 39**, each at **26.23 / 25.23** with full correctness—and preserves feasibility under different memory-fragmentation patterns.

- **Bounded local exchange refinement is a reliable complement to construction.** The current best program polishes threshold-feasible placements through improving relocations, swaps, and one-for-two exchanges. This carries forward the successful refinement pattern from **Generation 42** (“add_pair_exchange_refinement”), which passed validation and reached **25.87 combined / 24.87 max_kvpr**, and from the stronger direct-placement programs **Generation 43** and **44**, which reached **26.20** and **26.21** combined score respectively.

- **Correct feasibility handling is more important than increasingly elaborate neighborhoods.** Generations **43** and **44** both achieved full correctness using multi-start placement plus local search, while the current threshold-guided approach improved quality slightly beyond them: **26.23** versus **26.20** and **26.21**. The incremental gain comes from targeting a minimax pressure bound during construction, not from substantially more expensive search.

## Ineffective Approaches

- **Threshold packing is not inherently sufficient; fragile feasibility decisions caused complete failures.** Generations **40**, **41**, and **45** all used threshold-dependent or binary-searched packing but scored **0.0** because they failed validation. Their feedback consistently identifies reliance on heuristic feasibility as the critical weakness: a greedy packing failure was effectively treated as inability to satisfy evaluator requirements, despite feasible placements potentially existing.

- **Overly complex heuristic components can introduce edge-case invalidity without improving score.** Generation **40** used residual-aware ordering, Generation **41** combined transformed threshold packing with multi-start local refinement, and Generation **45** added threshold polishing. All were incorrect. The evaluator feedback points to fragile behavior around infeasible-placement handling, zero remaining memory, and threshold/local-search interactions, showing that added search machinery did not compensate for insufficiently robust validity guarantees.

- **Object-identity-dependent bookkeeping is a correctness risk.** Generation **41** was specifically flagged for potential reliance on object `id` values for model weights. Such identity-based mappings can become inconsistent if placement operations, duplicate-like model instances, or reordered collections are involved. The current best program avoids this issue by consistently reading `model.model_size`, `model.req_rate`, and `model.slo` from the actual model objects during refinement.

## Implementation Insights

- **The current best program maintains dual feasibility conditions during packing.** For each GPU it tracks physical remaining memory and transformed usage. A model is accepted only when:
  - `new_remaining >= -EPS`,
  - `new_cost <= threshold * 80 + EPS`, and
  - a positive-demand GPU retains strictly positive KV-cache memory.  
  This prevents placements that are physically memory-valid but have infinite or undefined pressure because remaining cache capacity is zero.

- **Its lower/upper threshold handling is explicit and robust.** The program derives an initial lower bound from total demand divided by total residual memory, then strengthens it using each individual model’s unavoidable pressure `demand / (80 - size)`. It finds an upper bound by doubling until an actual packing is constructed, then runs **36 binary-search iterations**. This differs from failed threshold variants by retaining concrete feasible placement states rather than relying only on a scalar threshold conclusion.

- **Best-fit selection accounts for both dimensions of the transformed formulation.** Within each ordering, the chosen GPU maximizes a tightness key based on transformed-capacity utilization and physical-memory utilization. This attempts to fill constrained GPUs while preserving larger residual-memory regions for later models, addressing the fragmentation problem that multi-start memory-first variants such as Generations **42–44** also targeted through alternate orderings and exchanges.

- **The refinement phase is intentionally bounded and lexicographic.** The current best program compares sorted descending pressure profiles, so it minimizes the bottleneck pressure first and uses lower pressures as tie-breakers. # META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add several safe, difficulty-aware item orders to `pack_at_threshold`, while retaining the three current orders.** In particular, try descending `demand / max(80 - size, EPS)`, descending `(size / max(80 - size, EPS), demand, size)`, and descending `(size > 40, size, demand)`; these prioritize models that individually consume scarce KV-cache headroom or are likely to cause memory fragmentation. This directly extends the current best program’s successful multi-order threshold construction without altering its robust “return an actual feasible placement” validation behavior.

2. **Replace the construction-stage GPU tie-break with a projected-pressure-aware lexicographic key.** After checking physical and transformed feasibility, calculate each candidate GPU’s projected pressure `new_load / new_remaining` and rank candidates using a key such as `(projected_pressure, projected_global_max_pressure, transformed_fill, -new_remaining, gpu_id)`, selecting the tightest safe placement only after avoiding an unnecessary new bottleneck. The present transformed/physical best-fit key is fast and effective, but a pressure-aware tie-break more directly optimizes the evaluator objective and may improve the small remaining gap beyond the current 25.23 max-KVPR result.

3. **Add the reverse cardinality exchange neighborhood: move two models from one GPU in exchange for one model from another.** Implement it symmetrically to the existing one-for-two exchange, evaluate only final memory/load states, enforce positive residual memory for every positive-load GPU, and accept only a strictly lexicographically improved pressure profile. The current code already proves that variable-cardinality exchanges are safe and useful for fragmentation; the missing two-for-one direction can resolve cases where a bottleneck GPU needs to shed multiple high-pressure models but cannot accept either model independently.

4. **Prioritize local-search candidates around the current pressure bottleneck instead of exhaustively scanning all GPU pairs first.** Build a deterministic active GPU set containing the maximum-pressure GPU plus GPUs within, for example, `0.95 * current_profile[0]` or the top two/three pressure ranks, and first enumerate moves, swaps, and exchanges touching that set; optionally retain a full scan only if focused search finds no improvement. This preserves the best program’s bounded refinement correctness while allowing more promising move types, extra rounds, or larger exchange limits without losing the observed runtime advantage.

5. **Use a small deterministic perturb-and-repolish portfolio after strict local descent reaches a local optimum.** Generate a few capacity-safe alternate states through neutral-profile swaps, a bounded non-worsening relocation, or rebuilding at `upper * (1 + tiny_delta)` with a different packing order, then rerun the existing strict lexicographic move/swap/exchange descent and keep only solutions better than the original profile. This borrows the useful diversification idea from the successful multi-start local-search family, but keeps the threshold-feasible construction as the primary state and never risks returning an inferior or invalid placement.
