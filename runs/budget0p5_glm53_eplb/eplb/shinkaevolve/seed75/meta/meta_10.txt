# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns
- The current best program (Gen 0, hierarchical EPLB, combined 0.13) establishes the reliable baseline: three-stage hierarchical rebalancing (groups→nodes via balanced packing, intra-node expert replication, physical experts→GPUs), with a global fallback (num_groups=1, num_nodes=1) when groups don't divide by nodes. All correct variants (Gen 0, 2, 5, 6, 7, 8) using this structure score combined 0.13 with GPU balancedness 0.66 — this appears to be a ceiling for the greedy LPT + hierarchical design.
- Passing all validation tests while keeping the reference algorithm structure is essential: every correct program scored ≥0.13, while both crashed programs (Gen 1, Gen 4, Gen 10) scored 0.00. Small API mistakes are catastrophic.
- Early-exit optimization in `balanced_packing` for groups_per_pack==1 (identity pack_index, zero rank_in_pack) is a cheap correctness-preserving speedup present in the best program.

## Ineffective Approaches
- **`stable=True` misuse**: Gen 1 (all metrics 0.00) and Gen 10 (all 0.00) both crashed passing `stable` to `Tensor.argsort`/`Tensor.sort`, unsupported in the installed PyTorch. Fix is `torch.argsort(x, dim=-1, stable=True)` or an explicit tie-break key. Avoid novel tensor-op signatures; validate against installed PyTorch.
- **Vectorization attempts without index-safety**: Gen 4's vectorized packing crashed with an out-of-bounds index (~10^14, garbage/sentinel like -1) reaching a gather along the 256-wide expert dimension — vectorized index bookkeeping needs bounds validation.
- **"Vectorized" rewrites that still loop per item**: Gen 3 (NumPy, combined 0.03) and Gen 5/6/8 (masked_fill/argmin per iteration) keep a Python-level loop over item positions, delivering speed_score ≈ 0.00 and, in Gen 3's case, even degrading expert balancedness to 0.05. Gen 7's snake-deal rewrite also scored times_algorithm 0.00 — the reshape/flip/scatter path on CPU dominated rather than helped.
- **Changing the replication/packing heuristic without evidence**: Gen 3's incremental-ratio NumPy replication dropped expert balancedness from 0.25 to 0.05; the load/count-ratio greedy is weak (expert balancedness stuck at 0.25) but alternatives tried so far were worse.

## Implementation Insights
- The best program's `balanced_packing` uses batched greedy LPT: sort weights descending, iterate t over num_groups, mask full packs with `masked_fill(..., inf)`, `argmin(-1)` to pick least-loaded pack, then scatter updates via `layer_rows` indexing. This is correct across all layer rows simultaneously but the loop length (num_groups) caps speed.
- `replicate_experts` iterates from num_log to num_phy selecting max of `weight / logcnt`, updating rank and logcnt incrementally — the per-replica Python loop is the other identified hot spot (also flagged in Gen 0 feedback).
- Inverse permutation helper (`scatter_` with arange) and the fallback `rebalance_experts(weight, num_replicas, 1, 1, num_gpus)` for non-divisible group/node configs are structural elements common to all passing programs.
- CPU round-trips (`weight.float().cpu()`, `.tolist()` in Gen 2) add latency; all top programs operate on CPU tensors, which may be why vectorization gains don't materialize.

## Performance Analysis
- Score plateau at 0.13 across six correct programs (Gen 0, 2, 5, 6, 7, 8): GPU balancedness 0.66, expert balancedness 0.25, speed_score 0.00–0.01. The best program ties this plateau with times_inference 0.24 — slightly better inference timing than Gen 5 (0.24 vs. similar) — while remaining fully correct.
- Correlation: expert balancedness (0.25) is the dominant bottleneck relative to GPU balancedness (0.66), attributed by feedback to the hierarchical replication heuristic under-utilizing redundancy; no successful attempt has improved it.
- Speed scores are uniformly ~0.00–0.01 for all correct programs regardless of vectorization strategy (per-item loops, NumPy, torch vectorized, snake-deal), indicating runtime is dominated by something the current rewrites don't address (CPU execution, per-layer/per-item Python overhead) — Gen 7 proves that aggressive tensor-op rewrites can even regress times_algorithm to 0.00.
- Risk asymmetry: any change to the hot loops carries crash risk (3 of 10 programs failed with 0.00) with no observed speed reward; the two failed vectorization bugs (stable sort, out-of-bounds gather) are cheap to avoid with API checks and index clamping.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Vectorize `replicate_experts` using round-based threshold batching**: Replace the per-replica Python loop (currently `for i in range(num_log, num_phy)`) with a vectorized water-filling approach — compute `weight / logcnt` for all layers, but instead of one iteration per replica, batch replicas via a heap-free approach: repeatedly take the top-k argmax rows only where replicas remain. Since num_redundant is typically small, a semi-vectorized variant that assigns multiple replicas per iteration using `topk` on `weight/logcnt` with capacity clamping will cut Python-loop iterations while preserving the exact greedy semantics (and thus expert balancedness 0.25 without regression).

2. **Improve expert balancedness by replacing the load/count-ratio greedy in `replicate_experts` with a proper LPT over post-replication loads**: The feedback identifies expert balancedness (0.25) as the dominant bottleneck, and the naive ratio heuristic under-utilizes redundancy. Instead, sort logical experts by weight descending and assign each replica to minimize the current maximum replica load per layer (mirroring the proven `balanced_packing` LPT structure: `masked_fill` + `argmin` batched across all layers). This reuses the best program's validated masked-argmin pattern, minimizing crash risk, while directly targeting the weakest metric.

3. **Precompute loop-invariant tensors and hoist them out of `balanced_packing`'s loop**: The `layer_rows` advanced indexing inside the loop (`pack_index[layer_rows, group]`) creates per-iteration gather/scatter overhead. Instead, accumulate `pack` and `rank` assignments into flat index lists (`flat_idx = layer_rows * num_groups + group`) and perform one bulk `scatter_` after the loop; this preserves the argmin-based selection loop but consolidates memory writes, a safe refactor of proven-correct code.

4. **Try a rebalancing refinement pass after Step 2 that reassigns whole physical experts between GPUs within a node**: Since GPU balancedness is 0.66 and Step 3 already packs physical experts, add a cheap post-pass: compute per-GPU loads, and for the most-loaded GPU swap its heaviest physical expert with the least-loaded GPU's lightest expert when it reduces the max load (batched across layers, vectorized predicate masks). This greedy local-search extension builds directly on the existing correct map-construction plumbing (`inverse`, `gather`) without touching the risky hierarchical structure.

5. **Batch the two Python hot loops across layers using precomputed sort orders instead of per-item argmin**: In `balanced_packing`, replace the `masked_fill(..., inf) + argmin` per-iteration approach with a topological deal: since all layers share the same num_groups item positions, compute all layers' sorted indices once, then use `torch.argsort` on a stacked key (`pack_weight * scale + pack_fill`) to select destinations for all layers simultaneously in one shot per iteration, then verify with an assertion that pack capacities are respected before scattering (bounds validation, per the Gen 4 out-of-bounds lesson). Keep `stable` out of any sort signature — use explicit tie-break keys added to the sort key instead.
