vectorize_balanced_packing

<DESCRIPTION>
The dominant cost of the algorithm is `balanced_packing`: it sorts indices to CPU and then runs a pure-Python double loop over `num_layers × num_groups` items, doing a Python `min` over packs each iteration. This makes execution time scale with layers × experts and forces repeated small tensor indexing (very slow in Python).

Key observation: after sorting each layer's weights in descending order, the greedy LPT assignment is sequential only across items *within* a layer — it is independent across layers. So we can process item step `j` for **all layers simultaneously** with vectorized tensor ops: keep `pack_weights` and `pack_items` as `[num_layers, num_packs]` tensors, mask full packs with `inf`, take a batched `argmin`, and scatter-add. The Python loop shrinks from `num_layers * num_groups` iterations to just `num_groups` iterations of vectorized torch ops, each doing O(num_layers × num_packs) work in C.

Tie-breaking is preserved (argmin picks the lowest pack index, matching the previous `min(..., key=pack_weights.__getitem__)` behavior since packs were appended in index order), so the produced assignment is identical to the original algorithm — no change in balancedness, only a large drop in runtime (which directly lifts `times_algorithm` / `speed_score`, currently the weakest component of the combined score at 0.00).

Additionally, this removes the `.cpu()` sync per layer and the per-item `.item()`-style indexing overhead entirely.
