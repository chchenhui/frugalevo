# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns
- **All six correct programs plateau at combined 0.12–0.13**, sharing the same DeepSeek-derived three-stage hierarchical structure (groups→nodes, replication, physical→GPUs). Gens 0, 3, 4, 6, 8, 9 all score 0.12–0.13 with identical balancedness splits (GPU 0.66, expert ~0.24–0.25) — confirming hierarchical decomposition reliably yields good GPU-level balance (0.66) but the ceiling is the expert balancedness score.
- **Vectorizing `balanced_packing` across layers (batched greedy via argmin/scatter) is the proven performance pattern**: the current best program (Gen 4, "vectorize_balanced_packing") achieved times_algorithm 0.00 and times_inference 0.23 (best of all correct programs) by replacing per-layer Python loops with a single loop over `num_groups` timesteps applying `cand.argmin(-1)` + `scatter_add_` across all layers simultaneously.
- **Keeping computation on-device**: the current best avoids `.cpu()` round-trips inside packing, unlike Gen 0 (0.55 algorithm time) and Gen 6 which uses `weight.float().cpu()`, limiting runtime.
- **Capacity-aware greedy packing** (masking full packs with `INF` before `argmin`) preserves exact cardinality constraints (n/m objects per pack) while vectorizing — this correctness-preserving trick is why Gen 4 passes validation where riskier vectorizations (Gens 1, 5, 7) crash.

## Ineffective Approaches
- **Python heap/loop-based packing**: Gen 8 (`heapq` LPT per-layer) scored speed 0.00 — row-by-row Python loops dominate runtime despite correctness. Gen 0's per-layer loops similarly drove its runtime score to 0.55.
- **Runtime-crashing API misuse repeatedly zeroed out entire programs**: Gen 1 (`to(device=torch.int64, dtype=...)` keyword misuse), Gen 5 (`torch.repeat_interleave` with 2D repeats — "repeats must be 0-dim or 1-dim"), Gen 7 (`argsort(..., stable=True)` — unsupported keyword, should use `torch.sort(..., stable=True).indices` or composite-key sorting), Gen 2 (leftover `np.put_along_axis(None, None, None)` placeholder). Each scored 0.00 with no metrics measured.
- **Heuristic packing substitutions without load-optimality**: Gen 3's snake packing and Gen 9's serpentine packing vectorized well but *lowered* expert balancedness (0.25→0.24 in Gen 9, combined 0.13→0.12) by sacrificing greedy least-loaded pairing — the trade was not worth it.
- **Greedy replication by max weight/cnt (or weight/(logcnt+1)) is the confirmed weak point**: every correct program using it (Gens 0, 4, 6, 8, 9) is stuck at expert balancedness 0.24–0.25. Gen 5's water-filling binary-search replication was the only attempted alternative, but it never got measured due to the repeat_interleave crash.

## Implementation Insights
- **Current best program (Gen 4) structure**: (1) batched greedy `balanced_packing` sorting weights descending per layer, then iterating over sorted positions `t in range(num_groups)` with full-batch `argmin` over capacity-masked pack weights and `scatter_add_` updates; results scattered back via the sort permutation. (2) greedy replication using `weight/logcnt` marginal-load argmax. (3) hierarchical rebalance with `inverse()` permutation helper built from `scatter_`.
- The batched-greedy loop is O(num_groups) Python iterations (not O(num_layers × num_groups)), which is the key runtime win: 0.00 algorithm time vs 0.55 for per-layer loops (Gen 0).
- Deterministic tie-breaking matters for validation but must be implemented safely: Gen 7's failure shows `argsort(stable=True)` is illegal; the current best avoids the issue by relying on argmin's natural first-index tie-breaking.
- Scatter-based index inversion (`inv.scatter_(1, perm, arange)` in `inverse()`) is a compact, correct pattern reused across all three hierarchy stages and validated by all passing tests.

## Performance Analysis
- **Score ceiling analysis**: the 0.13 combined plateau across all correct programs is entirely attributable to expert balancedness 0.24–0.25; GPU balancedness is uniformly 0.66 and inference/algorithm times vary little among vectorized variants. Feedback from Gens 4, 6, 8, and 9 all independently conclude that replication strategy — not packing or runtime — is the dominant optimization target.
- **Speed vectorization is a necessary-but-insufficient gain**: vectorized packing moved times_algorithm from 0.55 (Gen 0) to 0.00–0.02 (Gens 4, 6, 8, 9), yet speed_score stayed 0.00–0.01 because it's weighted against inference time, which stays ~0.23–0.45 regardless. Current best (Gen 4) has the best inference time (0.23) among correct programs.
- **Risk correlation**: 4 of 10 generations (Gens 1, 2, 5, 7) scored 0.00 from single-line API errors — vectorization attempts that aren't carefully validated against PyTorch API signatures have a ~40% total-failure rate in this evaluation set.
- **Gen 9's marginal-gain replication (weight/(cnt·(cnt+1))) actually scored slightly worse** (expert 0.24 vs 0.25), indicating the replication marginal-gain formulation is not the deciding variable; the constraint is more fundamental — likely replication granularity constrained by the per-node grouping in the hierarchy.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Replace greedy replication with an optimal or water-filling replication strategy** — the single biggest lever. Every correct program is stuck at expert balancedness 0.24–0.25 because `replicate_experts` uses marginal-load argmax (`weight/logcnt`). Implement Gen 5's water-filling binary-search idea (safely this time): binary-search the threshold τ such that Σ⌈weight/τ⌉ = num_phy per row, or use a fully vectorized sorting-based approach — sort `weight` descending and repeatedly assign the next redundant replica to the globally largest `weight/cnt` candidate via top-k, avoiding the current O(num_redundant) Python loop entirely.

2. **Consider replication granularity as the real constraint**: Gen 9's refined marginal-gain (`weight/(cnt·(cnt+1))`) made things *worse*, suggesting the hierarchy's per-node replication (Step 2 runs on node-local expert subsets) caps achievable balance. Try replicating experts *globally* across the full num_physical_experts pool first, then distributing replicas to nodes via the existing `balanced_packing` — i.e., swap the order of Steps 1 and 2, or run Step 2 on the full logical set with only the GPU packing done per-node.

3. **Improve packing beyond greedy LPT without sacrificing vectorization**: the batched argmin/scatter_add loop is proven fast, but greedy LPT is only a 4/3-approximation. Try a *refinement pass* after packing: vectorized local swap search (for each layer, test swapping the largest item of the max-load pack with the smallest item of the min-load pack, iterating k times) — still O(k·num_groups) batched timesteps, so runtime stays at 0.00 algorithm time.

4. **Optimize inference time (0.23, best but still dominant in speed score)**: remove the `weight = weight.float().cpu()` round-trip in `rebalance_experts` (contradicting the insight that Gen 4 avoids `.cpu()` — the shown code still has it), keep all ops on-device with float32 casts done once. Also fuse the `replicate_experts` per-iteration scatter loop into a top-k batched formulation (e.g., iterate in blocks by repeatedly selecting top-k over `weight/logcnt`), cutting the O(num_redundant) loop to O(num_redundant/block) iterations.

5. **Mutate conservatively to preserve correctness — API-signature discipline**: 4 of 10 generations scored 0.00 from single-line PyTorch API errors. Any new vectorization must avoid `argsort(stable=True)`, `repeat_interleave` with 2D repeats, and mixed dtype/device kwargs; prefer the proven primitives from Gen 4: `torch.sort(...).indices`, `scatter_`/`scatter_add_`, `gather`, and `torch.where`-masking with `INF` for capacity constraints. Keep changes to one component per mutation so a crash isolates cleanly against the known-good Gen 4 baseline.
