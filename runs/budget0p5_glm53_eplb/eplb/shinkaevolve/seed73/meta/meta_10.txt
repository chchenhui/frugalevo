# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns

- **Vectorized snake/serpentine LPT packing** is the proven baseline pattern: the current best program (Vectorized Snake LPT EPLB, Gen 1) and Gen 2 (`vectorized_snake_packing`) both achieve combined 0.13 with GPU balancedness 0.66 and algorithm time ~0.00, using sort-descending + scatter-based index remapping with alternating snake direction per block. This is strictly better than the original DeepSeek-style CPU port (Gen 0), which also scored 0.13 but with speed score 0.00 due to Python greedy loops.
- **The three-stage hierarchical pipeline (groups→nodes, per-node replication, physical experts→GPUs) with a global-policy fallback when `num_groups % num_nodes != 0`** is validated as correct across every correct program (Gen 0, 1, 2, 4, 7, 8, 10) — the structure is sound; the differentiator is packing/replication internals.
- **Vectorized rank/pack construction via `scatter_` with precomputed offsets** (as in the current best's `balanced_packing`: compute `pack_sorted`/`rank_sorted` on a template, then scatter through sort indices) eliminates per-item Python loops while keeping balance quality near the heap-based reference.

## Ineffective Approaches

- **Greedy max weight/logcnt replication is the persistent weakness**: every correct program scores expert balancedness 0.25 (Gen 0, 1, 2, 4, 8, 10). Simply duplicating the argmax-load expert iteratively leaves per-expert replica counts poorly spread — this is the single largest untapped score dimension (all programs plateau at combined 0.13).
- **Python heap/list-based packing kills speed without quality gains**: Gen 4 (`heap_based_balanced_packing_speedup`), Gen 7 (`greedy_heap_vectorized_eplb`), and Gen 8 (`gpu_pack_local_search_refinement`) all use min-heap/`.tolist()` loops; Gen 8's algorithm time ballooned to 0.04 (vs 0.00 for vectorized) with speed score 0.00 and no balance improvement.
- **Local-search swap refinements caused crashes**: Gen 5 failed entirely (`TypeError: argsort() ... stable` — incompatible with the environment's PyTorch), and Gen 6 (`fast_heap_packing_with_swap_refinement`) failed with `index 256 is out of bounds` because swapping `rank_in_pack` across packs broke the invariant that downstream `phy2log * maxlogcnt + phyrank` scatter indices stay in range.
- **Zero-metric runs (Gen 3, Gen 7) show that correctness alone doesn't score** — several correct programs registered 0.00 across all metrics, indicating evaluation capture issues or non-competitive timing, not algorithmic failure.

## Implementation Insights

- The current best program's `balanced_packing` is fully tensorized: descending sort → snake offsets (`torch.where(rank_sorted % 2 == 0, offset, num_packs - 1 - offset)`) → dual `scatter_` calls; zero Python loops over items or layers. This delivers times_algorithm 0.00 vs 0.04 for the heap version (Gen 8).
- `replicate_experts` remains a Python loop over redundant slots (`for i in range(num_log, num_phy)`), even in the best program — a per-layer `weight / logcnt` argmax with incremental `logcnt` updates. It's the least-vectorized part of the best program and directly tied to the weak 0.25 expert balance.
- The `inverse` permutation helper via scatter, and the log2mlog→mlog2log/phy2pphy→pphy2phy index gymnastics, are delicate; Gen 6's crash shows that any refinement touching `rank_in_pack` must preserve pack-capacity and rank invariants before the final scatter.
- API compatibility matters: avoid newer signatures like `argsort(..., stable=True)`; use `torch.sort(..., stable=True)` or composed-key argsort (Gen 5's hard failure).

## Performance Analysis

- Every correct, scored program sits at exactly combined 0.13 (GPU 0.66 / expert 0.25), a plateau across Gens 0–2, 4, 8, 10 — vectorization moved speed from 0.00→0.01 but changed nothing in balance quality, and swap refinement (Gen 8) did not improve GPU balance either.
- Inference time is a secondary cost: vectorized programs run 0.23–0.24, while heap/loop-heavy variants (Gen 8: 0.46, Gen 10: 0.43) roughly double it. The current best's 0.23 inference is the best observed.
- The score breakdown implies the dominant headroom is expert-level balancedness (0.25 across all programs), which no packing change has touched — it is governed entirely by the `replicate_experts` heuristic.
- Correct-but-zero runs (Gen 3, Gen 7) versus identical-scoring correct runs suggest evaluation flakiness or timing capture failure; treat 0.00-metric runs cautiously rather than as evidence of regression.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Vectorize `replicate_experts` with a proportional-redundancy allocation**: The Python loop `(weight/logcnt).max(dim=-1)` is the sole source of the 0.25 expert balancedness plateau and the only remaining per-slot loop in the best program. Replace it with a closed-form allocation: compute each layer's target replica count as `torch.clamp(torch.round((num_redundant+num_log) * weight / weight.sum(-1, keepdim=True)), min=1)`, fix the total to `num_phy` via a single largest-remainder correction pass (tensorized diff vs. target sum, add/subtract 1 on extreme elements), then build `phy2log` with `torch.repeat_interleave` on the corrected counts. This keeps everything tensorized (preserving times_algorithm 0.00) while spreading replicas proportionally to load instead of concentrating on argmax experts.

2. **Cap max replica count and spread replicas via a rank-aware constraint**: If pure proportional allocation leaves the `maxlogcnt` dimension underutilized (most experts at 1, a few at many), cap counts at `maxlogcnt = num_redundant // 2 + 1` or similar and redistribute excess to next-highest-load experts. Evidence: the current greedy argmax loop produces extreme spreads (all programs stuck at expert balance 0.25), suggesting replica-count variance — not packing — is the limiter. Ensure any count adjustment never exceeds `maxlogcnt` or the final `phy2log * maxlogcnt + phyrank` scatter (the exact invariant Gen 6 broke) will go out of bounds.

3. **Jointly optimize replication and GPU packing by re-weighting `tokens_per_phy`**: Currently Step 3 packs replicas by `tokens_per_mlog / mlogcnt`, which is correct, but replication is chosen before packing without regard to how replicas land on GPUs. After computing proportional counts, run a single local refinement pass: for each layer, compute actual per-GPU loads from Step 3's `phy2pphy` (via `scatter_add` on `tokens_per_phy`), and if max-GPU-load exceeds mean by a threshold, move one replica count from the highest-contribution logical expert in the hottest pack to the lowest in the coldest pack — fully tensorized top-k selection, no loops. This is the safe form of Gen 8's swap idea: mutate `logcnt`/`phy2mlog` before packing, never `rank_in_pack` after.

4. **Try a balanced-pair (deterministic LPT) variant of the snake packing for Step 3**: The snake heuristic pairs heavy-then-light items per block; a complementary variant is to sort descending and assign item `k` to the pack with current minimum load via a tensorized approximation (e.g., repeated `argmin` over cumulative load computed with segment sums, or pairing sorted-first-half with reverse-sorted-second-half "greedy-matching"). Keep the same `scatter_` construction through `indices` so the packing remains loop-free. If GPU balance improves above 0.66 without speed regression, this generalizes the proven vectorized packing pattern; keep the current snake version as fallback since it is validated.

5. **Harden evaluation-timing reliability by keeping the entry point cheap and deterministic**: Insight from Gen 3/Gen 7 zero-metric runs: correctness alone scored 0.00, suggesting flaky timing capture. Keep `weight = weight.float().cpu()` as the first operation (as the best program does), avoid creating tensors on other devices mid-algorithm, and avoid `torch.argsort` with newer kwargs entirely (use `torch.sort(..., descending=...)` as now, or `torch.sort(..., stable=True)` if stability is ever needed — Gen 5's crash). When benchmarking variants, run the same program twice in the mutation if feasible and confirm identical metrics before interpreting a zero-metric run as an algorithmic regression.
